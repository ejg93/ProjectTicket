# 상태머신 카탈로그

> **ProjectShop 에서 이식한 문서다.** 예시·청크 번호(`2g`·`Q36` 등)·쇼핑 도메인(주문·셀러·정산)은 ProjectShop 것이다.
> 티켓 도메인과 Kotlin 에 맞추는 것은 `PLAN.md` 이식 청크 `P` 줄이 한다. 그 청크가 닫히면 이 머리말을 지운다.
> 그때까지는 **원칙은 믿고 예시는 안 믿는다.**

자원마다 어떤 상태가 있고 누가 그것을 옮기는지 정한다.

**전이표 자체는 코드에 선언한다.** ADR 0009 가 정했다. 이 문서는 상태 목록과 전이 주체와 자동 전이다.

**전이 조건의 단일 출처가 이 문서다.** 여기 없으면 다음 사람은 `OrderStatusService` 를 읽어야
조건을 알고, 그러면 이 문서를 읽을 이유가 없어진다 — 실제로 `V26`·`V29` 가 두 번 그렇게 갔다.

## 주문은 두 층이다

**한 주문에 셀러가 여럿일 수 있다.** 셀러 A 는 배송을 끝냈고 B 는 준비 중인 상황이 성립한다.
상태를 한 군데만 두면 이걸 표현할 수 없다.

```
order                        결제가 여기 붙는다
 ├ seller_order  (셀러 A)    배송·취소·반품이 여기 붙는다
 │   └ order_item
 └ seller_order  (셀러 B)
     └ order_item
```

| 층 | 무엇을 담나 | 왜 여기인가 |
|---|---|---|
| `order` | 결제 | 고객은 한 번 결제한다. 셀러별로 나눠 결제하지 않는다 |
| `seller_order` | 배송·취소·반품 | 셀러마다 따로 굴러간다. 배송비도 셀러별로 붙는다 |

**셀러 권한이 이 경계와 그대로 맞아떨어진다.** `scope=seller` 가 `seller_order` 를 자른다.
셀러가 남의 배송 정보를 볼 경로가 구조에서 사라진다.

주문 항목(`order_item`)에는 상태를 안 둔다. 항목 단위 부분 취소는 하지 않는다.
취소·반품의 최소 단위는 `seller_order` 다.

## `order` 상태 — 결제

| 상태 | 뜻 |
|---|---|
| `payment_pending` | 주문이 만들어졌고 재고를 잡았다. 결제를 기다린다 |
| `paid` | 결제가 끝났다 |
| `payment_expired` | 30분 안에 결제가 안 끝나 재고를 되돌렸다 |
| `payment_failed` | 결제가 거절됐다 |

### 재고는 결제 전에 잡는다

`payment_pending` 을 두는 이유다. 주문서를 띄워 둔 사이에 남이 채가는 것을 막는다.

```
주문 생성 → 재고 차감 → payment_pending
  결제 성공  → paid
  30분 초과  → payment_expired + 재고 복구
```

결제가 성공해야 주문을 만드는 방식도 있었다. 상태가 줄지만
**결제를 마치고 재고를 깎으려는 순간 품절이면 즉시 환불해야 한다.**
무통장입금 같은 지연 결제도 못 붙인다.

## `seller_order` 상태 — 배송

| 상태 | 뜻 |
|---|---|
| `preparing` | 셀러가 상품을 준비한다 |
| `shipping` | 배송이 시작됐다 |
| `delivered` | 배송이 끝났다. 청약철회 기간이 여기서 시작된다 |
| `confirmed` | 구매가 확정됐다. 정산 대상이 된다 |
| `cancelled` | 배송 전에 취소됐다 |
| `return_requested` | 배송 후에 반품이 접수됐다 |
| `returned` | 반품이 끝났다 |

취소와 반품을 가르는 것은 **배송완료 시각**이다. 용어 정의는 `glossary.md` 에 있다.

`delivered` 시점에 두 값을 박제한다(`D10`).

| 값 | 계산 |
|---|---|
| 청약철회 만료일 | 배송완료 다음날부터 7일, 말일이 쉬는 날이면 다음 영업일 |
| 자동 구매확정 예정일 | 배송완료 다음날부터 8일, 같은 규칙 |

**결제 승인 시점에도 하나 박제한다**(`V26`, `11-6`).

| 값 | 계산 |
|---|---|
| 발송 기한(`ship_due_at`) | 대금 지급일부터 `supply_lead_days` 영업일. 선지급식이라 기산점이 대금 지급일이다(전자상거래법 제15조제1항) |

**빈 채로 넘어가면 조용하다** — `seller_order_ship_overdue_idx` 가 `is not null` 로 걸러서
기한을 넘긴 묶음이 「지금 늦고 있는 것」 조회에서 사라진다. 그래서 `shop_order` 가 `paid` 로
갈 때 그 주문의 묶음이 다 채워졌는지를 지연 제약 트리거가 본다(`V30`, `Q2`).

### `delivered` → `return_requested` 는 사유로 갈린다

`seller_order.return_reason`(`V29`, `11-7`)이 **어느 조항으로 받는지**를 정한다.

| 사유 | 조항 | 기한 | 청약철회 제한 |
|---|---|---|---|
| `change_of_mind` | 제17조제1항 | 배송완료 기산 7일 | **걸린다** |
| `defect` | 제17조제3항 | 공급받은 날부터 3개월 | **안 걸린다** — 「제1항 및 제2항에도 불구하고」 |

제한이 실제로 걸리는지는 **주문 항목에 박제한 값**이 정한다(`V32`, `Q5`) —
상품의 지금 값을 읽으면 셀러가 나중에 제한을 켜서 지나간 주문까지 막는다.

## 누가 옮기나

| 전이 | 주체 |
|---|---|
| `payment_pending` → `paid` | 결제 모듈. 사람이 직접 못 옮긴다 |
| `payment_pending` → `payment_expired` | 배치 |
| `preparing` → `shipping` → `delivered` | 셀러 |
| `preparing` → `cancelled` | 고객 또는 셀러 |
| `delivered` → `return_requested` | 고객 |
| `return_requested` → `returned` | **관리자만**(청크 `43a-2`). 반품 승인이다 — 셀러는 입고(`received`)까지 하고 멈춘다. 아래 「판정은 셀러가 안 한다」 |
| `return_requested` → `delivered` | **관리자만**(청크 43). 반품 거절이다 — 셀러가 부르면 **배송완료를 되돌리는 셈**이고 아래 「배송 후에는 셀러도 못 고친다」가 그대로 뚫린다 |
| `confirmed` → `return_requested` | 고객(청크 43). **하자 반품만**이다 — 제17조제3항의 3개월. 사유를 가르는 것은 접수 입구다(`43a`) |
| `delivered` → `confirmed` | 고객 또는 배치 |
| 그 밖의 모든 전이 | 관리자만. 감사 로그를 남긴다 |

### 셀러는 자기 것만 옮긴다

`scope=seller` 가 판정한다. 판정 엔진은 이미 있고(청크 4), 상태 조건이 청크 11a 에서 붙는다.

**배송 후에는 셀러도 못 고친다.** `delivered` 를 지나면 셀러의 전이 권한이 닫힌다.
셀러가 배송완료를 되돌릴 수 있으면 청약철회 기산점을 조작할 수 있다.

### 판정은 셀러가 안 한다

**승인도 거절도 관리자다**(청크 `43a-2`, 사용자 선택). 그전에는 이 표가 승인을
「셀러」라고 적었는데, 제17조제5항이 훼손 책임의 **입증을 우리에게** 지운 것과 어긋난다 —
판정을 셀러에게 주면 입증책임이 우리에게 있다는 사실이 데이터에서 사라진다(`D2` R37).

| 무엇 | 누가 | 권한 |
|---|---|---|
| 입고 | 셀러 | `order:receive_return` |
| 승인 | 관리자 | `order:approve_return` |
| 거절 | 관리자 | `order:reject_return` |

**동작을 새로 세운 것이 강제 지점이다.** `order:update_status` 의 허용 상태에서
`return_requested` 를 뺐다 — 그전에는 셀러가 `DELIVER` 로 거절 복귀를 밀 수 있었고,
위 표가 「관리자만」이라고 말할 뿐 막는 것이 없었다.

**상태 축이 역할을 못 본다**(`permission-rules.md` 「상태 축」). 그래서 「셀러는 되고 관리자만 안 되고」를
한 동작 이름으로는 못 가른다 — 가르려면 동작을 나눠야 한다.

### 관리자 강제 전이

정상 전이표를 벗어나는 이동은 관리자만 한다. CS 처리에 필요하다.

**감사 로그가 필수다**(청크 4b). 강제 전이는 정상 경로가 아니라서
왜 그랬는지가 남지 않으면 나중에 데이터가 왜 이 모양인지 아무도 모른다.

### 상태 이력을 남긴다

ADR 0007 이 정한 이력 테이블에 전이가 쌓인다(`order_status_history`, `V18`).
현재 상태만 들고 있으면 "언제 배송됐나" 를 답할 수 없고, 청약철회 기간 분쟁에 근거가 없다.

**두 층을 한 테이블에 받는다.** `order_id` 와 `seller_order_id` 중 정확히 하나를 채우고,
상태 값 목록도 그 층을 보고 가른다. 소비자가 보는 것은 주문 하나의 생애 전체라서,
층마다 나누면 타임라인을 만들 때마다 이어 붙여야 하고 한쪽을 빠뜨리면 이력이 반만 보인다.

| 규칙 | 왜 |
|---|---|
| 사람이 옮긴 전이는 행위자가 남는다 | "누가 취소했나" 에 답하는 것이 이 테이블이다 |
| 배치·결제 모듈은 행위자가 없다 | 지목할 사람이 없다. `actor_type = 'system'` |
| 관리자 전이에는 사유가 필수다 | 정상 경로가 아니라서 사유가 없으면 왜 이 모양인지 아무도 모른다 |
| 남은 행은 못 고친다 | 고친 이력은 이력이 아니다. 잘못된 전이는 **반대 전이를 새 행으로** 남긴다 |

전이 규칙(무엇에서 무엇으로 갈 수 있나)은 이 테이블이 안 막는다. 코드에 선언한다(`ADR 0009`).

## 자동 전이 둘

| 전이 | 언제 | 도는 주기 |
|---|---|---|
| `payment_pending` → `payment_expired` | 생성 후 30분 | **5분마다** |
| `delivered` → `confirmed` | 자동확정 예정일 경과 | 매일 04:00 |

### 결제 만료는 `D10` 의 예외다

`D10` 은 배치를 04:00 에 돌린다. 결제 만료는 그 규칙에서 빠진다.

하루에 한 번 돌면 재고가 하루 종일 잡혀 있다. 만료 판정은 **경과 시간**이라
「전날 24시 기준」 같은 고정 기준이 필요 없고, 여러 번 돌아도 결과가 같다.

### 자동확정 8일

청약철회 7일 바로 다음날이다. 반품할 수 있는 주문이 확정되는 일이 없다.

**틈이 좁아서 경계를 정확히 해야 한다.** 청약철회 마감일에 접수된 반품과
다음날 새벽 확정 배치가 붙어 있다.

```
배송완료 8/6
  청약철회 만료   8/13 23:59:59
  자동확정 배치   8/14 04:00
```

배치는 `return_requested` 상태를 건드리지 않는다. 반품이 접수돼 있으면 확정 대상에서 빠진다.

**말일 보정이 둘을 같은 날로 붙일 수 있다.** 청약철회 말일이 쉬는 날이라 하루 밀리면
8일째와 겹친다. 그러면 청약철회가 살아 있는 날 자정에 확정 배치가 돈다.

```
배송완료 2026-08-10
  청약철회 만료  8/17 → 광복절 대체공휴일이라 8/18
  자동확정 8일째 8/18                              ← 같은 날
```

**자동확정은 청약철회 만료 다음날보다 앞설 수 없다.** 정한 것은 8일이라는 날수가 아니라
"청약철회 기간보다 짧으면 안 된다" 는 제약이고(`D10`), 겹치는 날은 그 제약이 이긴다.

### 상태 전이는 곁가지를 데리고 다닌다

전이마다 같이 일어나야 하는 것이 있다. **호출자에게 맡기면 한 군데서 빠뜨리고,
빠뜨린 것이 화면에 오류로 안 드러난다.**

| 전이 | 같이 일어나는 것 |
|---|---|
| → `delivered` | 청약철회 만료일·자동확정 예정일 박제 |
| → `confirmed`·`cancelled`·`returned` | `closed_at` — 파기 기산점(`D13`) |
| → `cancelled` | 재고 복구 |
| `payment_expired`·`payment_failed` | 그 주문의 `preparing` 인 셀러 주문을 전부 취소 |

**재고 복구는 취소 한 자리에서만 한다.** 결제 만료도 셀러 주문 취소를 거치므로
같은 코드를 지난다 — 두 자리에서 되돌리면 재고가 두 번 는다.


**반품(`returned`)은 재고를 안 되돌린다.** 물건이 돌아와 다시 팔 수 있는지는 검수 결과라
상태만으로 못 정한다. **그 판단이 `return_request.restock` 이다**(청크 43, `V63`) —
승인일 때만 값이 있고, 같은 `approved` 라도 단순 변심으로 돌아온 새 물건과 파손된 물건이 다르다.

## 반품 상태 — 진행

**묶음은 요약이고 반품 표가 진행이다**(청크 43, 사용자 선택). `seller_order` 는
「반품 중인가 / 끝났나」에만 답하고 수거·입고·검수·판정은 `return_request` 가 든다.

| 상태 | 뜻 |
|---|---|
| `requested` | 접수됐다. 아직 물건이 소비자에게 있다 |
| `picked_up` | 수거됐다 |
| `received` | 입고됐다. **환급 기산점이 여기다**(제18조제2항 1호 「재화등을 반환받은 날」) |
| `inspected` | 검수 소견이 나왔다. **판정은 아직이다** |
| `approved` | 반품으로 인정했다 |
| `rejected` | 인정 안 했다. 물건이 소비자에게 돌아간다 |

**`inspected` 를 따로 두는 이유가 법이다.** 제17조제5항이 훼손의 **입증을 우리에게** 지운다 —
셀러가 「훼손됐다」는 소견을 내도 그것으로 끝나지 않고 우리가 판정한다.
소견과 판정을 한 상태로 뭉치면 **셀러의 주장이 곧 결론**이 되고,
그 구조에서는 입증책임이 우리에게 있다는 사실이 데이터에서 사라진다.

**검수는 건너뛸 수 있고 입고는 못 건너뛴다.** 오배송처럼 다툴 것이 없는 건이 있지만,
입고 없이 승인하면 환급 기한을 셀 날이 없다.

**접수 취소가 없다.** 청크 `43a-2` 가 조문을 확인해 닫았다(사용자 선택) —
**소비자의 일방적 접수 취소권은 법에 없다.**

| 조문 | 문구 | |
|---|---|---|
| 전자상거래법 제17조제4항 | 「청약철회등을 서면으로 하는 경우에는 그 의사표시가 적힌 서면을 **발송한 날에 그 효력이 발생**한다」 | 발신주의. 접수한 순간 효력이 났다 |
| 민법 제543조제2항 | 해지·해제의 의사표시는 **철회하지 못한다** | 형성권이라 일방적으로 못 무른다 |

무르는 것은 상대방이 동의해 주는 **편의**지 권리가 아니다. 그래서 안 만든다.

**`rejected` 로 대신하면 안 된다.** `return_request_rejected_bearer_check`(`V63`)가
부담 주체를 `consumer` 로 강제하므로, 소비자가 스스로 무른 건이 **「우리가 하자가 아니라고
판정했고 소비자가 반환 비용을 문다」**는 기록이 된다 — 사실이 아닌 값이다
(`commerce-compliance.md` 「사실 아닌 값을 채워 넣게 만드는 제약」과 같은 자리).

편의를 주기로 하면 **종점 상태를 따로 세운다.** 그때 부담 주체·재고 복구·판정자 제약 넷이
같이 갈리므로 청크가 필요하다.

### 묶음 전이가 둘 늘었다

| 전이 | 언제 | 왜 |
|---|---|---|
| `return_requested` → `delivered` | 반품이 거절됐다 | 물건은 소비자에게 있고 거래는 살아 있다. **기산점은 안 움직인다** — `delivered` 로 갈 때 박제한 값이라 다시 안 센다 |
| `confirmed` → `return_requested` | 하자 반품 | 제17조제3항이 **공급받은 날부터 3개월**이라 구매확정으로 안 끝난다. 확정은 우리가 정한 기한이고 그쪽은 법이 준 기한이다 |

**단순 변심은 `confirmed` 에서 못 온다.** 그쪽은 제17조제1항의 7일이고 확정 시점에 이미 지났다 —
사유를 가르는 것은 접수 입구가 한다(`43a`).

### 어긋남은 트리거가 막되 상태를 안 옮긴다

지연 제약 트리거 둘이 **양방향**으로 본다(`V63`). 반품 행만 있고 묶음이 안 따라온 것,
묶음만 옮기고 반품 행이 없는 것 — 둘 다 커밋에서 막힌다.

**옮겨 주지는 않는다**(사용자 선택). 트리거가 상태를 고치면
`order_status_history` 없는 전이가 생기고 **「누가 옮겼나」에 답이 없어진다.**

**지연이라 롤백하는 테스트에서는 한 번도 안 돈다** — `set constraints all immediate` 를
불러야 밟힌다(`stack.md`). 그것을 모르면 **초록인데 안 도는 제약**이 된다.

## 셀러 상태

| 상태 | 뜻 |
|---|---|
| `pending` | 신원정보 확인 전. 상품을 못 판다 |
| `active` | 판매 중 |
| `suspended` | 정지됐다. 관리자가 되돌릴 수 있다 |

| 전이 | 주체 | 조건 |
|---|---|---|
| `pending` → `active` | 관리자 | **신원정보가 채워져 있어야 한다.** `check` 가 막는다 |
| `active` → `suspended` | 관리자 | |
| `suspended` → `active` | 관리자 | |

**`pending` 이 있는 이유가 법이다.** 전자상거래법 제20조② 가 중개자에게 중개의뢰자의 신원정보를
**청약 전까지 확인**하라고 하고, 제20조의2 가 안 했을 때 연대책임을 붙인다(`D2` R1).

확인 전과 후를 상태로 가르지 않으면 그 경계를 DB 가 막을 수 없다.
`app_user` 가 "살아 있으면 이메일이 있다" 를 `check` 로 적은 것과 같은 형태다(`D13`).

**폐업은 여기 없다.** `deleted_at` 이 따로 있다 — 정지는 풀리고 폐업은 안 풀린다(`D4`).

## 상품 상태

| 상태 | 뜻 |
|---|---|
| `draft` | 셀러가 작성 중이다. 노출되지 않는다 |
| `pending_review` | 검수를 기다린다 |
| `on_sale` | 판매 중이다 |
| `sold_out` | 재고가 없다 |
| `suspended` | 판매가 중지됐다 |

### 중지가 둘이다

`suspended` 는 **셀러가 쉬는 것**이고 `blocked` 는 **관리자가 막은 것**이다.

하나로 두면 관리자가 내린 상품을 셀러가 다시 올릴 수 있어서 **제재가 무의미해진다.**
상태로 가른 덕에 전이표가 그대로 규칙이 된다 — 셀러는 `product:review` 가 없어서 `blocked` 를 못 푼다.

제재 종류가 늘면 상태를 더 만들지 않고 `block_reason` 으로 쪼갠다.

### 전이

**표에 없는 전이는 막는다**(`ADR 0009`). 권한까지 표에 실어서 "누가 할 수 있나" 가 코드 분기로 안 흩어진다.

| from | to | 권한 | 뜻 |
|---|---|---|---|
| `draft` | `pending_review` | `product:update` | 셀러가 검수 신청 |
| `pending_review` | `on_sale` | `product:review` | 승인 |
| `pending_review` | `draft` | `product:review` | 반려. **사유를 적는다** |
| `on_sale` | `suspended` | `product:update` | 셀러가 쉰다 |
| `suspended` | `on_sale` | `product:update` | 셀러가 다시 판다 |
| `on_sale` | `blocked` | `product:review` | 관리자가 막는다. **사유를 적는다** |
| `suspended` | `blocked` | `product:review` | 쉬는 중에도 막는다 |
| `blocked` | `on_sale` | `product:review` | 오인이었다 |
| `blocked` | `draft` | `product:review` | 고쳐서 다시 받아라 |

`sold_out` 은 표에 없다. 사람이 옮기는 상태가 아니라 재고에서 파생된다 — 주문(10)이 깎을 때 바뀐다.

**`on_sale` → `draft` 가 없다.** 팔던 것을 준비 중으로 되돌리면 그 사이 주문이 무엇을 가리키는지 애매해진다.
고쳐야 하면 `blocked` 를 거친다.

### 승인이 끝이 아니다

`blocked` 가 있는 이유다. 위법 표시·위조품 신고·리콜은 **팔기 시작한 뒤에 드러난다.**
중개자가 알고도 방치하면 제20조의2 의 연대책임을 진다 — 사전 검수만으로는 그걸 못 면한다.

**쉬는 중에도 막을 수 있어야 한다.** 안 그러면 셀러가 먼저 내려서 제재를 피한다.

### 판매 개시에는 셀러 상태가 걸린다

`pending_review` → `on_sale` 은 **셀러가 `active` 일 때만** 된다.

전자상거래법 제20조② 가 중개자에게 셀러 신원정보를 **청약 전까지** 확인하라고 하고,
제20조의2 가 안 했을 때 연대책임을 붙인다(`D2` R1). `on_sale` 이 청약이 가능해지는 지점이다.

**`check` 제약으로 못 막는다** — 상품 행에서 셀러 테이블을 볼 수 없다.
그래서 두 겹이다. 앱이 422 로 이유를 알려주고, 트리거가 다른 입구를 막는다.
한 겹만 두면 실패 방식이 갈린다 — 트리거만 두면 이유가 500 으로 뭉개지고,
앱만 두면 새 입구가 생길 때 빠뜨린다.

검수는 청크 7c 다. 관리자가 승인해야 `on_sale` 이 된다.

`sold_out` 은 재고에서 파생되지만 상태로 둔다. 목록 조회에서 매번 재고를 세면 쿼리가 무거워진다.

**삭제는 여기 없다.** `deleted_at` 이 따로 있다(`domain-model.md`).

## 정산 지급 상태

**마감과 지급이 다른 사건이다**(청크 19·21). 지급액이 확정됐다고 돈이 나간 것이 아니고,
그 둘이 데이터로 안 갈리면 **두 번 지급해도 표가 아무 말을 안 한다.**

| 상태 | 뜻 |
|---|---|
| `pending` | 마감만 됐다. 아직 아무도 지급을 올리지 않았다 |
| `requested` | 누가 지급을 올렸다 |
| `paid` | 돈이 나갔다 |
| `rejected` | 반려됐다. 다시 올릴 수 있다 |

| 전이 | 주체 | 조건 |
|---|---|---|
| `pending` → `requested` | 관리자 | **지급액이 양수여야 한다.** `settlement_payout_amount_check` 가 막는다 |
| `rejected` → `requested` | 관리자 | 처리 칸(`payout_decided_*`)이 비워진다 |
| `requested` → `paid` | **다른** 관리자 | 자기가 올린 것은 자기가 승인 못 한다 |
| `requested` → `rejected` | **다른** 관리자 | |

**요청과 승인이 다른 권한이다**(`V57`). 하나로 두면 올리는 순간 승인이 같이 열리고,
그때 남는 것은 자기승인 제약뿐인데 **그것은 자기 것만 막는다** — 환불에서 같은 자리를
`V24` 가 이미 갈랐다.

**둘 다 관리자다.** 셀러가 올리게 하면 **셀러가 안 눌러서 지급이 밀리는 구조**가 되는데,
그건 `12a-5` 가 환불에서 고친 함정과 같은 모양이다.

**반려가 종점이 아니다.** 정산서는 `(셀러, 주기)` 당 하나라 환불처럼 새 행을 만들 수가 없어서,
다시 올리면 같은 행이 `requested` 로 돌아간다. 반려했다는 사실은 감사 로그가 든다.

**취소가 없다.** 지급액은 마감이 정한 값이라 반려한다고 사라지지 않는다.

## 문의 상태

| 상태 | 뜻 |
|---|---|
| `received` | 접수됐다 |
| `answered` | 답이 나갔다 |
| `blocked` | 게시가 중단됐다(정보통신망법 제50조의7, `D2` R34) |
| `withdrawn` | 낸 사람이 거뒀다 |

| 전이 | 주체 | 조건 |
|---|---|---|
| `received` → `answered` | 셀러(자기 상품)·관리자 | **답과 시각이 같이 찬다.** `inquiry_answer_check` 가 사슬로 묶는다 |
| `received`·`answered` → `blocked` | **관리자만** | 사유가 `advertisement`·`abuse` 중 하나여야 한다(`59-2`) |
| `received` → `withdrawn` | 낸 사람·관리자 | **답이 나간 것은 못 거둔다**(`59-1`) |

**`blocked` 는 종점이지만 `answered` 를 지나서도 온다.** 광고에 답을 달았다고 그 광고가 남을
이유가 없어서다 — `58` 이 답변 시각을 상태와 한 몸으로 묶어 뒀던 것을 `V58` 이 풀었다.
**`answered_at` 은 사건 시각이지 상태 표현이 아니다**: 「답이 나갔다」는 사실은 그 뒤에
무슨 상태가 되든 남아야 한다.

**차단은 관리자만이다.** 제50조의7 의 의무자가 운영자라 그 판단도 운영자가 한다 —
셀러에게 열면 **불리한 질문을 광고로 몰아 내리는 자리**가 같이 생기고, 구매 전 문의라
그 질문을 못 보게 되는 사람은 살까 말까 하는 사람이다.

**거두기가 공개 목록의 조건을 물었다**(`59-1`). `59` 는 공개 목록에서 `blocked` 만 뺐는데,
`withdrawn` 이 그때 **도달 불가능해서 안 드러났다** — 전이를 만드는 순간 **거둔 질문이 남에게
그대로 보이는 것**이 드러났다.

조건을 **「뺄 상태」에서 「보일 상태」로 뒤집었다**(`V60`). 「이 상태만 뺀다」로 쓰면 상태가 늘 때마다
그 자리를 고쳐야 하고 빠뜨리면 **안 보여야 할 것이 보이는 쪽으로 샌다.** 「이 상태만 보인다」면
새 상태의 기본이 **안 보이는 쪽**이다 — `is_public` 의 DB 기본값을 비공개로 둔 것과 같은 판단이다.

**계정에 붙는 요구는 셀러가 못 답한다**(`R25`·`R28`). 그 요구에는 셀러가 없어서
판정의 `seller` 스코프가 자연히 안 걸린다 — 규칙을 따로 안 적었다.

**내려간 글이 작성자에게는 보인다.** 제50조의7 은 게시 중단을 요구하지
작성자에게서 감추라고 하지 않는다.

## 안 다루는 것

| 항목 | 왜 |
|---|---|
| 항목 단위 부분 취소 | 최소 단위를 `seller_order` 로 정했다 |
| 교환 | 반품 후 재주문으로 대신한다. 전이가 두 배로 는다. **청크 `45` 를 이 근거로 닫았다**(2026-08-23 마무리) — 갈래가 반품·재고·정산·배송비 넷에 하나씩 붙는데 소비자가 얻는 것은 재주문과 같다 |
| 배송 추적 연동 | 택배사 API 가 없다. 셀러가 직접 `delivered` 로 옮긴다 |
| ~~정산·문의 상태머신~~ | **둘 다 섰다**(2026-08-23). 정산 지급은 아래 「정산 지급 상태」(`21`), 문의는 「문의 상태」(`58`·`59`) 다. **알림은 여전히 상태머신이 안 됐다** — `54a` 가 상태를 `check` 셋으로 닫았고 전이가 한 방향이라 표를 안 판다 |

## 이 문서를 고칠 때

새 상태를 넣기 전에 **그게 업무 상태인지 수명인지** 먼저 가른다(`domain-model.md`).
전이를 추가하면 주체를 위 표에 같이 적는다. 주체가 안 정해진 전이는 결국 관리자만 하게 된다.
