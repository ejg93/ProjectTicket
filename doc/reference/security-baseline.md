# 보안 기준

> **ProjectShop 에서 이식한 문서다.** 예시·청크 번호(`2g`·`Q36` 등)·쇼핑 도메인(주문·셀러·정산)은 ProjectShop 것이다.
> 티켓 도메인과 Kotlin 에 맞추는 것은 `PLAN.md` 이식 청크 `P` 줄이 한다. 그 청크가 닫히면 이 머리말을 지운다.
> 그때까지는 **원칙은 믿고 예시는 안 믿는다.**

무엇이 위험한지를 OWASP Top 10 항목으로 훑고, 각 항목을 이 프로젝트의 어느 청크가 막는지 잇는다.

## 기준

**OWASP Top 10 2025 판.** ASVS 는 요구사항이 수백 개라 미뤘다 — `external-references.md` 에 근거가 있다.

**2021 판으로 적어 뒀던 것을 점검 E 가 뒤집었다**(`D14-1`). 2025 판이 2026-01 에 확정됐고
항목 이름을 원문에서 다시 가져왔다. 개정에서 우리에게 걸린 것이 셋이다.

| 무엇이 바뀌었나 | 우리에게 |
|---|---|
| **`A10` 이 SSRF → 예외 상황 처리 미흡**으로 통째로 바뀜 | **새 숙제다.** 아래 표 참조 |
| `A03` 이 **공급망 실패**로 승격(옛 `A06` 을 흡수·확장) | 의존성 검증 절차가 없다 |
| `A09` 에 **경보(Alerting)** 가 이름으로 들어옴 | 사람에게 닿는 경로가 없다 |

SSRF 는 `A01` 로 흡수됐다. 웹훅의 사설 IP 차단은 없어진 요구가 아니라 **자리가 옮은 것**이다.

### A10 — 예외 상황 처리 미흡

2025 판에서 새로 들어온 항목이다. **실패했을 때 무슨 일이 나는가**를 묻는다.

우리 코드에서 걸리는 자리가 넷이고, 셋은 이미 답이 있다.

## 인증

### 비밀번호 해시 — bcrypt

Spring Security 의 `DelegatingPasswordEncoder` 를 그대로 쓴다. 저장값에 `{bcrypt}` 접두사가 붙는다.

```
{bcrypt}$2a$10$N9qo8uLOickgx2ZMRZo...
```

접두사가 알고리즘을 저장값 안에 들고 있어서, 나중에 argon2id 로 갈아탈 때
새 비밀번호만 새 알고리즘으로 저장하고 옛 해시는 그대로 검증된다. 일괄 재해시가 필요 없다.

cost 는 Spring 기본값 10 을 쓴다.

### bcrypt 의 72바이트 절단

**bcrypt 는 입력이 72바이트를 넘으면 넘는 부분을 조용히 버린다.**
버려지면 앞 72바이트가 같은 서로 다른 비밀번호가 같은 해시가 된다.

한글은 UTF-8 에서 글자당 3바이트라 24자에서 72바이트에 닿는다.
아래 문자 집합 제한이 이 구간을 아예 안 만든다 — ASCII 는 글자당 1바이트라 64자가 64바이트다.

### 비밀번호에 쓸 수 있는 문자 — ASCII 출력 가능 문자

한글을 포함한 비 ASCII 문자를 막는다. bcrypt 때문이 아니라 입력이 환경마다 갈려서다.

| 왜 막나 | 무엇이 생기나 |
|---|---|
| 입력 칸이 가려져 있다 | 한/영 상태를 사용자가 확인할 방법이 없다. 실패가 는다 |
| IME 가 환경마다 다르다 | 모바일 키보드와 데스크톱 IME 가 넘기는 문자열이 갈릴 수 있다 |
| 인코딩이 갈린다 | UTF-8 이 아닌 경로를 타면 같은 비밀번호가 다른 바이트가 된다 |

공백과 기호는 허용한다. 막는 것은 ASCII 바깥이다.

### 비밀번호 규칙 — 길이만 본다

기준은 **NIST SP 800-63B Revision 4** 다(2025년 개정판, 점검 E 가 원문 대조).

| 규칙 | 값 | 표준 등급 | 지키나 |
|---|---|---|---|
| 최소 길이 | **15자** | `SHALL` | **지킨다**(`D14-1` 이 8자에서 올렸다) |
| 최대 길이 | 64자 이상 | `SHOULD` | 지킨다 |
| 문자 집합 | ASCII 출력 가능 문자 + 공백 | `SHOULD` | 지킨다 |
| 유니코드 | 허용 | `SHOULD` | **안 지킨다** — 아래 근거 |
| 문자 조합 | 강제 금지 | `SHALL NOT` | 지킨다 |
| 블록리스트 대조 | 필수 | **`SHALL`** | **안 지킨다** — `D14-2` |
| 주기적 변경 | 강제 금지 | — | 지킨다 |

**15자인 이유는 우리에게 MFA 가 없어서다.** 개정판은 8자를 **다인수 인증의 일부일 때만** 허용하고,
비밀번호가 **단독 인증수단**이면 15자를 요구한다. MFA 를 붙이는 날 이 값을 다시 볼 수 있다.

조합을 강제하면 사용자가 `Password1!` 같은 예측 가능한 변형을 만들고 그걸 적어 둔다.
주기적 변경을 강제하면 끝의 숫자만 올린다. 둘 다 규칙을 지키면서 안전해지지 않는 방식이라
**표준도 `SHALL NOT`** 이다.

유니코드를 안 받는 것은 bcrypt 의 72바이트 절단 구간을 아예 안 만들려는 것이다(위 절).
`SHOULD` 라 근거를 대고 벗어난다.

**블록리스트는 열려 있는 위반이다.** 개정판이 `SHALL` 로 올렸는데 우리는 안 한다 —
목록 출처(내려받은 파일이냐 외부 API 냐), 검사 시점, 그리고 **바깥을 부르면 그 장애가 우리 장애가
되는가**(아래 캡차 절과 같은 물음)를 먼저 정해야 해서 `D14-2` 로 뺐다.
「값이 작아서 안 한다」로 적어 뒀던 것을 뒤집는다 — 그때는 `SHOULD` 였다.

### 세션 — 서버 메모리

Spring 기본값이다. 설정을 안 넣는다.

| 항목 | 값 |
|---|---|
| 무활동 만료 | 30분 |
| 절대 만료 | 12시간 |
| 로그인 성공 시 | 세션 ID 를 다시 발급한다 |

세션 ID 재발급은 세션 고정 공격을 막는다. 공격자가 미리 심어 둔 세션 ID 로 피해자가 로그인하면
그 ID 가 그대로 인증된 세션이 된다. 로그인 시점에 ID 를 갈면 심어 둔 값이 죽는다.

**메모리 세션의 대가가 둘 있다.**

앱을 재기동하면 전원이 로그아웃된다. 로컬 전용이라 재기동이 잦지만 개발 중에는 오히려 상태가 깨끗하다.

역할을 회수해도 그 사람의 로그인은 유지된다. 4a 의 캐시 무효화는 판정을 다시 하게 만들 뿐
세션을 끊지 못한다. 들어와 있지만 아무것도 못 하는 상태가 된다.
권한은 요청마다 다시 판정하므로 뚫리지는 않는다.

세션 자체를 끊어야 할 일이 생기면 **한 번에 DB 로 가지 않는다.**

| 단계 | 강제 로그아웃 | 재기동 버팀 | 서버 여러 대 | 비용 |
|---|---|---|---|---|
| 지금 | ✗ | ✗ | ✗ | 없음 |
| `SessionRegistry` 추가 | ✓ | ✗ | ✗ | `HttpSessionEventPublisher` 등록 |
| Spring Session JDBC | ✓ | ✓ | ✓ | 마이그레이션 2개, 요청마다 DB 조회 |

**탈퇴(5g)가 이 계단을 한 칸 올린다.** `ADR 0010` 이 그 결정이다.
JDBC 로 옮기는 것은 재기동을 버텨야 하거나 서버가 둘 이상이 될 때고, 로컬 전용이라 전제상 안 온다.

### 계정이 죽었는데 세션이 살아 있는 구간

로그인할 때만 계정 상태를 보면 **이미 로그인한 다른 기기가 안 막힌다.**
권한은 요청마다 다시 판정하지만 탈퇴해도 `user_role` 행은 그대로라 판정이 통과한다.

두 겹으로 막는다(`ADR 0010`).

| 겹 | 무엇 | 청크 |
|---|---|---|
| 생존 확인 | 인증 필터가 `deleted_at is null` 을 본다. `4a` 캐시에 얹고 탈퇴 시 `evict` | 5h |
| 세션 만료 | 탈퇴 시 그 사람의 세션을 전부 만료 | 5g |

한 겹씩만 두면 실패 방식이 갈린다. 세션 만료만 두면 **탈퇴 경로가 늘 때 등록을 빠뜨리는 순간 조용히 뚫리고**,
생존 확인만 두면 아무것도 못 하는 로그인 상태가 화면에 남는다.

### 쿠키 속성

| 속성 | 값 | 왜 |
|---|---|---|
| `HttpOnly` | 켠다 | 스크립트가 세션 쿠키를 못 읽는다 |
| `SameSite` | `Lax` | 남의 사이트에서 쏜 POST 에 쿠키가 안 붙는다 |
| `Secure` | **끈다** | 로컬이 http 라 켜면 쿠키가 아예 안 실린다 |

`Secure` 를 끈 것은 로컬 전용이라는 전제에 붙은 결정이다.
전제가 깨지는 순간 세션 쿠키가 평문으로 흐른다. 설정 파일에 이 줄을 주석으로 남긴다.

**`SecuritySettingsCheck` 가 기동에서 막는다**(`Q44`). **「지금이 운영인가」를 묻지 않는다** —
`Q37` 이 프로필로 안 가르기로 정했기 때문이다. 대신 **어느 환경에서도 정당한 이유가 없는 조합**만 본다.

| 막는 것 | 왜 어느 환경에서도 안 되나 |
|---|---|
| 신뢰 프록시가 **아무 주소나** 문다 | 백엔드를 직접 부르는 누구나 `X-Forwarded-For` 로 IP 를 속인다 — 신뢰한다는 말의 뜻이 사라진다 |
| 프록시가 **루프백 밖**인데 쿠키가 평문 | 요청이 망을 지나므로 그 구간에서 쿠키를 주우면 남의 세션으로 들어간다 |

**글자가 아니라 동작으로 잰다** — `.*` 같은 모양을 찾으면 같은 뜻의 다른 표기를 놓친다.
정규식에 **실제 주소를 넣어 본다**: 공인 IP 를 물면 전부 신뢰하는 것이고, 사설 IP 를 물면
프록시가 다른 기계에 있는 것이다. **로컬 기본값(루프백)은 둘 다 해당하지 않아 안 걸린다.**

`SameSite=Lax` 는 CSRF 방어와 겹치지만 대체하지 않는다. 토큰 방식은 청크 5b 가 따로 붙인다.

### 로그인 실패 제한 — (계정, IP) 5회 / 15분

| 항목 | 값 |
|---|---|
| 세는 단위 | 계정과 IP 의 조합 |
| 한도 | 5회 |
| 차단 시간 | 15분. 지나면 저절로 풀린다 |
| 성공하면 | 카운터를 0 으로 되돌린다 |
| 저장 위치 | **Redis**(청크 38). `INCR` + `EXPIRE` 로 끝나고 만료를 Redis 가 알아서 한다 |

Redis 에 둔 이유는 **카운터 하나로 완결되는 값이고 날아가도 손해가 작아서**다 —
차단이 풀릴 뿐이고 공격자는 5회를 더 시도한다. 멱등키(청크 10-0)를 Postgres 에 둔 것과
정반대 이유고, 그쪽은 유실이 곧 중복 주문이다.

**만료는 첫 실패에만 건다.** 실패마다 다시 걸면 계속 틀리는 동안 창이 밀려서
15분이 "마지막 실패로부터 15분" 이 된다. 여기서 정한 것은 차단 시간이지 무활동 시간이 아니다.

계정만 보고 잠그면 남의 계정에 일부러 틀려서 잠그는 공격이 열린다.
IP 를 같이 묶으면 공격자가 자기 IP 만 막게 된다.

**여러 IP 로 나눠 던지는 공격은 이 방식으로 못 막는다.** 아래 캡차와 청크 71 의 요청 제한이 그 자리다.

관리자 해제 화면을 안 만든다. 시간이 지나면 풀리므로 해제할 것이 없다.

### Redis 가 죽으면 로그인은 받고 세는 자리를 옮긴다

| 상황 | 어떻게 |
|---|---|
| Redis 정상 | Redis 카운터로 센다 |
| Redis 장애 | **프로세스 로컬 카운터**로 세고 한도·차단 시간은 그대로 5회 / 15분 |
| 장애 중 로그인 | 받는다. 비밀번호 대조는 Redis 와 무관하게 돈다 |
| 장애 복구 | Redis 카운터만 본다. 장애 중에 센 값은 안 합친다 |

셋 중에 고른 것이고 나머지 둘을 버린 이유가 있다.

**막는 쪽**(fail-close)은 Redis 장애가 곧 로그인 전면 정지다.
캐시 한 대를 내리면 서비스가 멈추므로 공격자에게 정지 버튼을 주는 것과 같다.

**그냥 통과시키는 쪽**(캡차와 같은 순수 fail-open)은 장애 동안 남는 방어가 비밀번호 해시뿐이다.
캡차 fail-open 의 근거는 *"남의 장애가 내 서비스 장애가 된다"* 인데 **Redis 는 남이 아니다** —
같은 `docker compose` 안에 있고, 캡차가 죽어도 살아 있다고 위에 적어 둔 방어가 바로 이 카운터다.
최후 방어층에는 그 논거가 안 걸린다.

로컬 카운터가 Redis 를 거의 그대로 대신한다. 이 앱은 인스턴스가 하나라 **덮는 범위가 같다.**
잃는 것은 둘이고 크기가 작다.

| 잃는 것 | 크기 |
|---|---|
| 재시작하면 카운터가 사라진다 | 공격자가 5회를 더 얻는다 |
| 복구 시점에 카운터가 갈아엎힌다 | 같다 |

**복구 뒤에 두 카운터를 합치지 않는다.** 합치면 장애 중에 몇 번 틀린 정상 사용자가
복구 직후 첫 실패에서 잠긴다. 남은 로컬 값은 15분이면 스스로 만료된다.

**로그인 성공은 두 카운터를 같이 지운다.** 로컬 값을 남겨 두면 다음 장애 때 그 사용자가
이미 차 있는 카운터에서 시작한다.

강등을 `WARN` 으로 남기는 것은 청크 2b 뒤다. 로그 형식이 정해지기 전에 찍으면 그 줄이 형식이 된다.

**법이 요구하는 것이 여기 걸린다.** 「개인정보의 안전성 확보조치 기준」은 비밀번호를 일정 횟수
이상 틀리면 접근을 제한하라고 한다. 순수 fail-open 은 장애 시간 동안 그 조치를 없앤다.
NIST SP 800-63B 5.2.2 와 OWASP `A07` 도 인증 시도 제한을 요구한다.

### 캡차 — reCAPTCHA v3

(계정, IP) 차단은 **여러 IP 로 나눠 던지는 공격을 못 막는다.** 캡차가 그 자리를 맡는다.

v3 는 점수제라 사용자에게 퍼즐을 보여주지 않는다. 화면 흐름이 안 바뀐다.

| 항목 | 값 |
|---|---|
| 요구하는 곳 | 로그인, 회원가입, 비밀번호 재설정 요청 |
| 통과 기준 | 점수 0.5 이상 |
| `action` | 요청한 동작과 응답의 `action` 이 같아야 한다 |
| 토큰 | 1회용. 유효 시간이 짧다 |
| 검증 타임아웃 | 3초 |
| 키 | `.env`. 비밀 키는 서버만 갖는다 |

`action` 을 검증하는 이유가 있다. 안 보면 **공격자가 다른 페이지에서 받은 토큰을 로그인에 갖다 쓴다.**
점수만 보고 통과시키면 캡차가 붙은 의미가 없어진다.

### 캡차가 실패하면 통과시킨다

구글이 응답을 안 하거나 3초를 넘기면 **로그인을 그대로 진행한다.** `WARN` 으로 남긴다.

막지 않는 이유는 캡차가 유일한 문지기가 아니어서다.

```
캡차가 죽어도 살아 있는 방어
  비밀번호 해시
  (계정, IP) 5회 / 15분 차단
```

반대로 막으면 **남의 장애가 내 서비스 장애가 된다.** 캡차를 우회하려고 일부러 검증 서버를
막는 공격도 성립한다.

점수가 기준에 못 미치면 그때는 거부한다. 이건 검증이 성공한 결과라 다르다.
사람인데 점수가 낮게 나오는 경우가 있는데, 실서비스라면 v2 퍼즐로 넘겨주는 길을 둔다.
여기는 그 경로를 안 만들고 임계값을 낮게 잡는 쪽으로 간다.

### 캡차가 만드는 외부 의존

**이 프로젝트의 첫 외부 호출이다.** 지금까지는 Docker 만 뜨면 전부 돌았다.

| 걸리는 것 | 어떻게 |
|---|---|
| 테스트가 외부를 타면 안 된다 | `CaptchaVerifier` 인터페이스 뒤에 둔다. 테스트는 항상 통과하는 구현을 쓴다 |
| 인터넷이 없으면 | fail-open 이라 로그인이 된다 |
| 사용자 데이터가 구글로 간다 | 개인정보처리방침에 제3자 제공을 적는다(청크 13a) |

### 응답 문구는 계정 존재 여부를 안 흘린다

| 상황 | 응답 |
|---|---|
| 없는 계정 | 아이디 또는 비밀번호가 맞지 않는다 |
| 비밀번호 틀림 | 같은 문구 |
| 차단 중 | 같은 문구 |
| 비밀번호 재설정 요청 | 가입된 주소면 메일을 보냈다 |

문구가 갈리면 가입 여부를 물어보는 도구가 된다. 응답 시간도 갈리지 않게 한다.

## 입력과 출력

**검증은 서버에서 한다.** 프론트 검증은 사용자 편의고 방어가 아니다. 요청은 브라우저를 거치지 않고도 온다.

| 자리 | 방식 |
|---|---|
| 요청 본문 | Bean Validation. 실패는 RFC 9457 형식으로 떨어뜨린다(청크 7b). **`@RequestBody` 에 `@Valid` 가 없으면 `ArchitectureTest` 가 빨갛다**(`Q32`) — 빠지면 record 의 검증이 조용히 안 돈다 |
| SQL | 이름 바인딩만. 문자열을 이어 붙인 SQL 을 안 쓴다 |
| 정렬·필터 컬럼명 | 바인딩이 안 되는 자리다. 허용 목록으로 받는다 |
| HTML 출력 | React 가 기본으로 이스케이프한다. `dangerouslySetInnerHTML` 을 안 쓴다 — **`react/no-danger` 가 막는다**(`Q34`) |

파일 업로드 검증은 `D17` 이 정한다. 청크 26 이 멀어서 지금 정하면 무엇을 정하는지 모른다.

## 노출면

기능이 아니라 **설정으로 새는 것**을 여기 모은다. OWASP A05(보안 설정 오류)에 걸린다.

| 자리 | 규칙 | 왜 |
|---|---|---|
| `/actuator/health` | 상세는 인증된 요청에만(`show-details: when-authorized`) | 공개 경로라서 `always` 면 아무나 DB·디스크·컴포넌트 목록을 본다. 살아 있나만 보는 데는 상세가 필요 없다 |
| 액추에이터 노출 목록 | `health` 하나 | 늘릴 때마다 그것이 무엇을 흘리는지 본다 |
| `/api/docs`(`2a`) | 스펙만 연다. **Swagger UI 를 안 들인다** | 흘리는 것은 <b>경로·요청/응답 스키마</b>다 — 계약이라 비밀이 아니고 프론트가 읽어야 한다. UI 는 정적 자원과 경로를 더 열어서 노출면만 넓힌다 |
| 세션 속 principal | 비밀번호 해시를 안 들고 있는다 | 아래 |

### principal 에서 인증정보를 지운다

로그인이 끝나면 `UserDetails` 가 세션에 principal 로 앉는다. 그대로 두면
**세션이 사는 내내 bcrypt 해시가 메모리에 남는다.** 인증이 끝난 뒤로는 쓸 데가 없는 값이다.

Spring 은 그러라고 `CredentialsContainer` 를 두고 `ProviderManager` 가 인증 직후
`eraseCredentials()` 를 부른다. **`record` 로 만들면 그 요청에 응답할 수 없다** — 불변이라 지울 방법이 없다.
`ShopUser` 를 클래스로 둔 이유가 이것이다(`D23` 의 "상태를 들고 도는 것만 class").

`equals` 는 **id 로만** 본다. 해시까지 비교하면 지워진 뒤에 `SessionRegistry` 에서
같은 사람을 못 찾아서 **탈퇴가 세션을 못 끊는다**(`ADR 0010`).

### 프록시 뒤의 클라이언트 IP

`server.forward-headers-strategy: native` 다. Tomcat `RemoteIpValve` 를 쓴다.

`framework`(`ForwardedHeaderFilter`)는 **`X-Forwarded-For` 를 보낸 것이 누구든 믿는다.**
프록시가 없으면 아무나 헤더 한 줄로 자기 IP 를 속일 수 있다.
`native` 는 바로 앞 상대가 신뢰 대역(사설·루프백)일 때만 헤더를 본다.

안 켜면 `getRemoteAddr()` 이 프록시 IP 를 준다. `user_consent.acted_ip` 는 동의 입증용이라
그 값이 프록시 IP 면 **틀린 개인정보를 쌓는 것**이고(개인정보법 제3조③ 정확성) 입증에도 못 쓴다.

**신뢰 대역을 프록시 주소로 좁히는 것은 청크 13 이다.** 그전까지는 로컬만 도는 상태라
기본값(사설·루프백)이 그대로 안전하다.
