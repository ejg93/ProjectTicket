# 정산 규약

회차 하나가 끝나면 기획사에 얼마를 주나. **값은 표에 두고 정산서는 항목의 합으로 만든다** — 요율·귀속·주기가 바뀌어도 코드가 안 바뀐다(ADR 0003 갱신, 2026-09-15 사용자 선택).

## 왜 이 모양인가

수수료 모델은 실무마다 다르다 — 오픈마켓은 정률 판매수수료, 예매처는 관객이 내는 정액 예매수수료를 얹고, 취소 수수료의 귀속도 계약마다 갈린다.
**어느 모델이 맞는지 지금 모른다.** 그래서 모델을 코드에 박지 않고, 무엇으로 바꿔도 표 구조가 안 바뀌게 만든다.

| 바꾸는 일 | 어떻게 | 코드 변경 |
|---|---|---|
| 요율 10% → 8% | `settlement_policy` 에 행 하나 | 없음 |
| 취소 수수료 귀속 기획사 전부 → 7:3 | 같은 표의 `cancel_fee_share` | 없음 |
| D+7 → D+14 | 같은 표의 `payout_delay_days` | 없음 |
| 관객 부담 예매수수료 추가 | `settlement_line.kind` 에 `booking_fee` 추가 | 항목 만드는 자리 하나 |
| 회차 취소 위약금 | `adjustment` 항목에 음수 | 항목 만드는 자리 하나 |

## 정책 표 `settlement_policy`

| 열 | 뜻 | 시작값 |
|---|---|---|
| `organizer_id` | 기획사. **null 이면 기본 정책** | null |
| `effective_at` | 이 행이 효력을 갖는 시각 | 저장소 시작일 |
| `commission_rate` | 플랫폼 판매수수료. 매출의 비율 | `0.10` |
| `cancel_fee_share` | 취소 수수료 중 **기획사** 몫의 비율. 나머지는 플랫폼 | `1.00` |
| `payout_delay_days` | 회차 종료 뒤 며칠 뒤에 정산서를 만드나 | `7` |

**고르는 규칙**: 그 기획사의 행 중 `effective_at <= 지금` 인 최신 → 없으면 기본 행 중 최신. 개정하면 새 행을 넣고 옛 행은 남긴다 — 「그때 어느 정책이었나」가 남아야 한다.

**회차를 열 때 정책을 박제한다** — `performance.settlement_policy_id`. 가격을 오픈 때 박제한 것과 같은 논리다(`D7` 「계산한 기한은 박제한다」).
정책을 나중에 고쳐도 이미 열린 회차의 정산은 안 흔들리고, 새 정책은 다음 회차부터다.

## 정산서 `settlement` — 회차당 한 장

| 열 | 뜻 |
|---|---|
| `performance_id` | **유일.** 회차당 정산서는 하나다 |
| `settlement_policy_id` | 회차에 박제된 것을 그대로 |
| `amount` | 기획사 지급액 = Σ 항목. **0 이상**(check) |
| `status` | `pending → confirmed → paid` |
| `settled_at` | 만든 시각 |

### 항목 `settlement_line`

| `kind` | 부호 | 계산 | 근거 |
|---|---|---|---|
| `sale` | + | Σ `reservation_seat.price` — 상태가 `reserved` 인 예매의 좌석 | 판매된 것 |
| `platform_fee` | − | round(`sale` × `commission_rate`) | 플랫폼 몫 |
| `cancel_fee` | + | Σ `refund.fee_amount` × `cancel_fee_share` — 그 회차의 관객 취소 | 자리를 비운 손해의 보전(`D6`) |
| `adjustment` | ± | 지금은 안 만든다. 위약금·보정이 생기면 여기 | 새 항목 종류 없이 받는 자리 |

**반올림은 항목마다 한 번, 원 단위, 반올림(half-up).** 좌석마다 반올림하면 합이 안 맞는다.

```
sale          +49,280,000   (320석)
platform_fee   −4,928,000   (10%)
cancel_fee     +1,232,000   (취소 12건의 수수료, 기획사 전부)
adjustment              0
amount         45,584,000
```

### 불변식

| 등식 | 어디서 |
|---|---|
| `settlement.amount = Σ settlement_line.amount` | 지연 제약 트리거(`D14` 「불변식」). 항목이 정산서보다 늦게 들어오므로 커밋 시점에 대조 |
| `amount >= 0` | check. 음수 정산서는 안 만든다(아래) |
| 회차당 정산서 하나 | 유일 제약 |
| `sale` 항목 = 그 회차 `reserved` 예매의 좌석 가격 합 | `SettlementAggregateTest`(27) — 두 표를 잇는 조건이라 트리거로 못 건다 |

## 언제 만드나

```
회차 closed ──(payout_delay_days)──> 정산서 생성 (pending)
                                      └ 관리자 확인 ──> confirmed ──> paid (모의 지급)
```

**회차 단위·종료 뒤 D+7 인 이유**: 취소는 관람일 당일에 못 한다(ADR 0003). 회차가 끝난 뒤에는 취소도 회차 취소(17a)도 없으므로,
**D+7 정산서가 보는 상태가 최종이다.** 「정산 확정 뒤 환불이 들어오면 어떻게 깎나」는 구조에서 사라진다.

월 정산이 필요해지면 **그 달 회차 정산서의 합**이다 — 위에 얹을 수 있고 반대는 안 된다.

만드는 것은 아웃박스 소비자(27)다 — `performance.closed` 사건을 받아 `payout_delay_days` 뒤에 만든다.
두 번 받아도 유일 제약이 둘째를 막는다(멱등).

## 회차 취소

관객 전액 환불(`D6`), 취소 수수료 0. 정산서는 **만들되 항목이 전부 0** 이다 — 회차당 한 장이라는 규칙을 지키고, 「이 회차는 취소돼서 0 이다」가 기록으로 남는다.
플랫폼 수수료도 안 받는다(사용자 선택) — 위약금을 받기로 하면 `adjustment` 에 음수를 넣고 `amount >= 0` check 를 그때 다시 본다.

## 누가 보나

| 누가 | 무엇 | 청크 |
|---|---|---|
| 기획사 | 자기 정산서 목록·항목 | 27·45 |
| 관리자 | `confirmed`·`paid` 전이 | 27 |
| 관객 | 못 본다 | |

## 지금 안 하는 것

| 항목 | 왜 |
|---|---|
| 음수 정산·상계 | 위약금 결정이 없다(ADR 0003) |
| 원장(실시간 잔액) | 보여줄 화면이 없다. 항목 구조가 원장만큼 유연하다 |
| 세금계산서·부가세 분리 | 가격이 부가세 포함이고 모의 지급이다 |
| 관객 부담 예매수수료 | 결제액 = 티켓가 로 층을 하나로 뒀다. 필요하면 `booking_fee` 항목 |

## 이 문서를 고칠 때

**항목 종류를 더하면 부호·계산·근거를 표에 같이 적는다.** 값을 바꾸는 것은 `settlement_policy` 행이고 이 문서는 안 바뀐다.
