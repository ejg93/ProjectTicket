# 코딩 규약

> **ProjectShop 에서 이식한 문서다.** 예시·청크 번호(`2g`·`Q36` 등)·쇼핑 도메인(주문·셀러·정산)은 ProjectShop 것이다.
> 티켓 도메인과 Kotlin 에 맞추는 것은 `PLAN.md` 이식 청크 `P` 줄이 한다. 그 청크가 닫히면 이 머리말을 지운다.
> 그때까지는 **원칙은 믿고 예시는 안 믿는다.**

청크를 실행할 때마다 지키는 것. **명명은 `naming-rules.md`(D22)가 따로 다룬다.**

이 문서는 바깥 표준을 베낀 것이 아니라 **이미 코드에 성립한 관례를 뽑아낸 것**이다.
관례가 문서에 없으면 다음 세션이 다르게 짜고, 검토할 기준도 없다.

## 계층

```
Controller  →  Service  →  JdbcClient
   HTTP를 안다    도메인을 안다    SQL만 안다
```

| 규칙 | 왜 |
|---|---|
| 컨트롤러는 서비스만 부른다 | DB 접근이 컨트롤러에 섞이면 같은 조회가 화면마다 복제된다 |
| 서비스가 트랜잭션 경계다 | 컨트롤러에 걸면 요청 하나가 통째로 한 트랜잭션이 되고, 밖에서 부를 때 경계가 사라진다 |
| 판정은 서비스에서 부른다 | 컨트롤러에서 부르면 다른 입구가 생겼을 때 빠뜨린다 |

**이 표와 아래 「예외」·「의존」은 `ArchitectureTest` 가 지킨다**(`2n`). 문서(5위)에서 테스트(4위)로 내렸다.
컨트롤러가 `*Query` 를 부르는 것은 허용이다 — 그 클래스들은 `@Service` 고 읽기 쪽 서비스다.
규칙이 막는 것은 컨트롤러가 `JdbcClient` 를 직접 드는 것이다.

**예외 하나.** `HealthController` 는 `JdbcClient` 를 직접 쓴다.
DB에 질의가 실제로 나가는지가 그 엔드포인트의 목적이라, 서비스를 거치면 검사할 것이 사라진다.

## 예외

**서비스는 도메인 예외를 던지고, HTTP 로 바꾸는 것은 한 군데서 한다.**

```java
// 서비스 — 무엇이 잘못됐는지만 말한다
throw new RequiredConsentException(itemCode);

// @RestControllerAdvice — 그것이 몇 번인지 정한다
```

서비스가 `ResponseStatusException` 을 던지면 웹을 알게 된다. 배치나 다른 입구에서 같은 서비스를
재사용할 때 어색해지고, 상태 코드가 코드 전체에 흩어져 규약(`D5`)과 대조할 수 없다.

**청크 7b 가 옮겼다.** 서비스는 `ShopException` 만 던지고 `ApiExceptionHandler` 가 번역한다.

예외 클래스를 종류마다 만들지 않았다. **오류 목록이 `ErrorCode` 한 화면에 있어야
`D5` 의 403/404 표와 눈으로 대조된다.** 클래스로 흩으면 "우리가 몇 가지 오류를 내나" 에
답하려고 패키지를 뒤져야 한다.

**`type` 은 계약이다.** `D5` 가 "프론트는 `type` 으로 분기한다" 고 정했으므로
슬러그를 바꾸면 화면이 깨진다. 문구(`title`)는 다듬어도 된다.

## 값

**DTO·요청·응답·조회 결과는 `record`.** 상태를 들고 도는 것만 `class`.

record 가 불변이라 만든 뒤에 바뀌지 않고, `equals`·`toString` 이 공짜다.
DB 에서 읽은 행을 `Map<String, Object>` 로 들고 다니지 않는다 — 키 오타가 실행할 때만 드러난다.

**시각 컬럼은 RowMapper 로 읽는다.** `query().singleRow()` 는 `timestamptz` 를
`java.sql.Timestamp` 로 주고, `OffsetDateTime` 캐스팅이 실행 중에 터진다.

## SQL

| 규칙 | 왜 |
|---|---|
| 이름 바인딩만 쓴다 | 값을 이어 붙이면 인젝션이다(`D14`) |
| `select *` 를 안 쓴다 | 컬럼이 늘면 응답이 조용히 바뀐다 |
| 조건이 선택적이면 `cast(:param as 타입) is null or ...` | null 을 `is null` 비교에만 쓰면 Postgres 가 타입을 못 정한다 |
| 정렬 컬럼을 요청에서 받으면 허용 목록으로 거른다 | 바인딩이 안 되는 자리다(`D14`) |

**정렬 컬럼만은 문자열로 붙는다.** 컬럼명은 값이 아니라 식별자라 바인딩이 안 된다 —
`order by ?` 는 문법 오류다. 결합이 강제되므로 **들어올 수 있는 값을 우리가 정한다.**

```java
private static final Map<String, String> SORTABLE = Map.of(
        "created_at", "p.created_at",
        "name", "p.name");
```

요청 문자열은 **키를 고르는 데만** 쓰이고 SQL 에 닿는 것은 표의 값뿐이다.
공통 처리는 `ListQuery.orderBy` 에 있다(청크 8).

**`SET` 도 바인딩이 안 되는 자리다**(`K1`). `set local lock_timeout = ?` 는 문법 오류라
상수를 결합한다(`IdempotencyService`). 정렬 컬럼과 같은 조건이 걸린다 —
**들어갈 값을 우리가 정하고 요청이 안 닿는다.**

**이 둘 말고는 예외가 없다.** 값이 결합되는 자리를 새로 만들려면 여기에 줄을 더하고,
왜 바인딩이 안 되는지와 값을 누가 정하는지를 같이 적는다.

**`SqlTextTest` 가 막는다.** `select *`·`order by` 결합·`set local` 셋을 `main` 소스에서 글자로 잰다.
예외를 더하려면 **그 줄 바로 위에 마커**를 단다 — `// sql-exception: <사유> — 왜 바인딩이 안 되나`.

| 무엇 | 왜 |
|---|---|
| 사유는 `identifier`·`set-statement` 둘뿐 | 위 표가 인정한 예외가 그 둘이다. 다른 값을 쓰려면 테스트의 상수를 고쳐야 하고 그 줄이 diff 에 뜬다 |
| **다음 줄에 실제 위반이 없으면 빨갛다** | 미리 뿌려 두는 것과 위반을 없앤 뒤 마커만 남는 것을 같이 막는다 |
| **마커 총 개수를 테스트에 박았다** | 하나 늘면 그 숫자를 같이 고쳐야 해서, 예외가 느는 것 자체가 리뷰에 걸린다 |
| `select *` 는 어떤 마커로도 안 꺼진다 | 인정된 예외 둘이 다 식별자 결합이라 사유 목록에 없다 |

**마커가 끄는 것은 이 테스트 하나뿐이다.** 요청 값이 SQL 에 닿는 진짜 주입은 CodeQL 이 따로 보고
(`JdbcClient.sql` 이 싱크 목록에 있다), 주석으로 그쪽을 못 끈다.

### 이 규칙이 어디까지 걸리나

**main 에 건다.** `select *` 를 막는 이유가 「컬럼이 늘면 **응답이** 조용히 바뀐다」라,
응답을 만들지 않는 코드에는 그 위험이 없다.

**테스트에는 안 건다**(`K2`). `AuditLogTest.latest()` 가 `select *` 와 `listOfRows()` 로
행을 통째로 받는데, 그 헬퍼가 하는 일이 「무슨 컬럼이 있든 그중 몇 개를 단언한다」라
컬럼이 늘어도 아무것도 안 바뀐다. 이름을 박으면 오히려 그 테스트가 스키마를 따라다니게 된다.

**적용 범위를 안 적었던 것이 문제였다.** `checkpoint-3` 이 「`Map` 으로 행 받기 0건」이라고
적었는데 실제로는 테스트에 하나 있었다 — **그 점검이 main 만 봤다는 뜻**이고,
범위가 문서에 없으면 점검마다 다른 답이 나온다.

## 주석

**무엇을 하는지가 아니라 왜 그렇게 했는지를 적는다.**

코드를 읽으면 무엇을 하는지는 보인다. 안 보이는 것은 **고르지 않은 다른 길**과
**그렇게 안 하면 무엇이 깨지는지**다.

```java
// 나쁨: 이메일 중복을 확인한다
// 좋음: 미리 조회하지 않는다. 조회와 삽입 사이에 남이 끼어들 수 있어서
//       어차피 유니크 인덱스가 최종 판단이고, 둘 다 두면 같은 규칙이 두 군데가 된다
```

**알고 남기는 구멍은 반드시 적는다.** 나중에 발견한 사람이 버그로 오해하고 고치다가
그 구멍을 막던 다른 것을 깬다.

## 테스트

`D15` 가 층을 정했다. 여기서는 쓰는 방식만 적는다.

| 규칙 | 왜 |
|---|---|
| `@DisplayName` 은 한글 평서형 | 실패 목록이 그대로 명세가 된다 |
| **깨진 이유가 안 드러나는** 단언에 `.as("왜 이게 문제인가")` 를 붙인다 | 깨졌을 때 무엇을 잃는지가 메시지에 있어야 한다 |
| 알려진 구멍은 통과하는 테스트로 고정한다 | `staleWithoutEvict` 처럼, 구멍이 닫히면 그 테스트가 깨져서 알려 준다 |
| 정리는 베이스 클래스에 둔다 | 빠뜨리면 **남의 클래스가 깨진다.** 원인을 찾을 실마리가 없다 |

**`@DisplayName` 은 `TestConventionTest` 가 막는다.** 한글이 있나, 존댓말 넷(`습니다`·`합니다`·`하세요`·`입니다`)이
인용 밖에 있나를 잰다. `@ArchTest` 는 필드라 안 센다 — 한글 필드명이 실패 목록에 그대로 뜬다.

`.as()` 를 모든 단언에 붙이지 않는다. `status().isOk()` 처럼 이름만으로 뜻이 서는 단언에 붙이면
노이즈만 는다. 붙일 자리는 **그 단언이 무엇을 막고 있는지가 코드에 안 보이는 곳**이다.

```java
assertThat(stillGranted)
        .as("계약이 끝났는데 동의가 유효한 채로 남으면 안 된다")
        .isEmpty();
```

## 패키지

### 자원 단위로 판다. 관객 단위로 안 판다

**한 테이블 묶음 = 한 패키지**다. 같은 자원을 누가 보느냐(공개·셀러·관리자)는
**같은 패키지 안에서 클래스로 가른다.**

```
product/  ProductController          공개·셀러 공용 입구
          SellerProductController    같은 자원, 다른 관객
seller/   SellerController           다른 자원이라 패키지가 다르다
```

관객으로 패키지를 파면 `public/`·`seller/`·`admin/` 이 되는데, 그러면
**한 테이블을 읽는 SQL 이 세 패키지에 흩어진다.** 컬럼 하나를 고칠 때 셋을 다 찾아야 한다.

**패키지 이름은 자원 이름이다**(`D22`). 자원이 없는데 패키지를 파지 않는다 —
`support/`·`error/` 처럼 자원이 아닌 것은 이미 있는 그것들을 쓴다.

### 경로가 관객이어도 패키지는 자원이다

`/api/me` 처럼 **경로가 관객으로 묶이는 자리**가 있다. 그때도 패키지는 자원을 따른다.

`me/` 패키지가 그 반례였다(`5l`). 이름은 관객인데 안에 자원이 둘이었고,
`ConsentItemController` 는 **로그인 전에 부르는 공개 조회**라 「나」와 맞지도 않았다.
`account/`(`app_user`)와 `consent/`(`consent_item`·`user_consent`)로 갈랐다.

**관례도 같은 쪽이다**(축 1의 4위라 근거는 아니고 세어 본 것이다). Magento·Shopware·Sylius·
Medusa·Spree·Saleor 가 전부 **모듈은 자원 이름**이고 관객은 그 안의 클래스·하위 경로로 가른다.
`me` 를 모듈로 판 곳은 없다 — 거기서도 `me` 는 **경로 이름**이거나 쿼리 이름이다.

남는 것은 `MeController` 하나다. **입구는 경로를 따라가므로 자원이 둘이어도 한 클래스다** —
가르면 `/api/me` 를 그리는 코드가 두 패키지로 흩어지고, 그건 이 절이 막으려는 것과 같은 모양이다.

### 입구 이름은 그 입구가 다루는 것을 말한다

| 무엇을 내리나 | 이름 | 예 |
|---|---|---|
| 자원 하나 | `<자원>Controller` | `ProductController` |
| 같은 자원, 다른 관객 | `<관객><자원>Controller` | `SellerProductController` |
| 한 관객에게 여러 자원 | **그 경로의 이름** | `MeController` (`/api/me`) |

셋째가 `MeController` 다. 아홉 경로 중 다섯이 `app_user` 가 아니라(동의 넷·권한 하나)
`AccountController` 로 부르면 **이름이 실제보다 좁게 말한다.** 그리고 그 이름은
청크 16 의 `GET /api/users/{id}` 가 쓸 자리다 — 거기가 진짜 자원 입구다.

### 남의 자원 표를 언제 직접 만지나

**가르는 것은 「도메인 규칙을 드나」**다. 테이블을 건드린다는 사실만으로는 안 가른다.

| 무엇을 아는 코드냐 | 어디에 | 예 |
|---|---|---|
| **그 자원의 규칙** | 그 패키지로 옮긴다 | 「철회란 무엇인가」 — append-only, 종속 항목, 필수 처리 |
| **보존 기간·기준 시각** | 부르는 쪽에 남는다 | 파기 배치의 `graceEnd`·`consentEnd`(`D13`) |

`5m` 이 그 선을 그은 자리다. `WithdrawalService` 의 동의 철회는 **철회의 정의를 들고 있어서**
`ConsentService.revokeAll` 로 옮겼다 — 두 곳에 있으면 한쪽 규칙을 고치는 사람이 다른 쪽을 못 본다.

반대로 `AccountPurgeService` 의 `user_consent` 손질은 **안 옮겼다.** 조건이 전부
`app_user.deleted_at` 이라 옮기면 `consent` 가 `app_user` 를 읽게 돼서 **방향만 뒤집힌다.**
파기는 개인정보를 든 모든 표에 걸리는 일이라 어느 한 자원의 것이 아니다.

### 자원이 아닌데 패키지를 파는 경우

위에서 "자원이 아닌 것은 `support/`·`error/` 를 쓴다" 고 했는데, **그 자리에 넣으면 순환이 되는 코드**가 있다.
그때만 판다.

`demo/` 가 그것이다(`6b-2`). 데모 시더가 `cart`·`order`·`payment` 를 다 부르는데,
`support/` 는 `order` 가 이미 부르는 곳이라(`BusinessCalendar`) 넣으면 `order` ↔ `support` 다.
아래 「의존」이 허용해 둔 순환은 하나뿐이고 이건 **자리를 옮기면 사라지는 것**이라 거기 안 든다.

조건이 셋이고 **셋을 다 만족해야 판다.**

| 조건 | 왜 |
|---|---|
| 자원이 아니다 | 자원이면 위 절대로 자원 이름을 쓴다 |
| 기존 비자원 패키지에 넣으면 순환이 된다 | 순환이 안 생기면 팔 이유가 없다 |
| **들어오는 의존이 0 이다** | 아무도 안 부르는 잎이라야 순환이 다시 안 생긴다 |

셋째가 이 절이 걸어 둔 자물쇠다. 잎이 아닌 것을 여기 넣으면 **같은 순환을 이름만 바꿔서 만든다.**

이름은 자원이 아니므로 **그 코드가 하는 일**을 말한다. `demo` 는 데모 데이터를 만든다.

### 의존

**순환이 셋이다**(`2n` 이 세었다). 셋 다 **업무가 두 자원에 걸쳐 있어서** 난 것이고,
어느 쪽이 부르든 한 방향은 남는다.

| 순환 | 무엇이 걸쳐 있나 |
|---|---|
| `auth` ↔ `audit` | 권한 거부를 판정 안에서 자동 기록하고(`4b`), 그 로그 조회도 권한을 탄다(`4b-1`). 기록을 호출자에게 맡기면 빠뜨린다 |
| `auth` ↔ `cart` | **로그인 그 순간에 비회원 장바구니를 계정으로 옮긴다.** `AuthController` 가 `CartService.mergeIntoAccount` 와 쿠키 이름을 부르고 `CartController` 는 인증을 본다 |
| `order` ↔ `payment` | **결제가 주문 상태를 옮기고 주문 조회가 결제 상태를 보인다.** `PaymentService` 가 `OrderStatusService`·`IdempotencyService` 를, `OrderQuery` 가 결제·환불 열거형 넷을 쓴다 |

단일 모듈이라 지금은 문제가 안 된다. **모듈을 쪼개게 되면 여기부터 막힌다** —
그때는 걸친 것을 공용 인터페이스로 빼는 것이 답이고, 이 문서를 그때 고친다.

**넷째가 생기면 예외로 넣기 전에 멈춘다.** 셋은 도메인이 그렇게 생겨서 난 것이고,
넷째는 대개 「부를 자리가 없어서 아무 데나 부른 것」이다. `ArchitectureTest` 가 그때 빨개진다.

## 설정과 상수

매직 넘버를 코드에 박지 않는다. 이름 있는 상수로 뽑고 **그 값을 고른 이유를 옆에 적는다.**

```java
/** 목록 하나로 전체를 긁어 가지 못하게 막는다(`D5`). */
private static final int MAX_SIZE = 100;
```

값이 규약 문서에서 온 것이면 그 문서 번호를 적는다. 문서가 바뀔 때 같이 고칠 자리가 드러난다.

**대상은 우리가 고른 값이다.** 바깥에서 채번돼 내려온 식별자는 "왜 이 값이냐" 에 답이 없어서
여기 안 걸린다 — 그런 값은 아래 「열거값을 어디에 두나」가 다룬다.

## 열거값을 어디에 두나

값 목록이 정해진 컬럼을 만날 때마다 나오는 물음이다. **표에 둘까, 코드에 둘까.**

### 가르는 물음

> **값이 하나 늘었을 때, 코드를 안 고쳐도 그게 동작하나?**

"바뀌나 안 바뀌나" 로 묻지 않는다. 그건 예측이라 틀린다 — 표준도 개정되고(RFC 9110 이 422 의
이름을 바꿔서 청크 `2d` 가 그걸 치웠다) 법도 개정된다. **바뀔 때 어차피 코드를 고쳐야 하는지**가 기준이다.

| 답 | 어디 | 왜 |
|---|---|---|
| **아니다** (코드가 값마다 분기한다) | **`check` 제약 + Java `enum`** | 표에 행만 넣으면 **도달 불가능한 값**이 된다. 전이표·정책표·화면 문구가 안 따라오므로 어차피 배포한다 |
| **그렇다** (존재만 묻거나 화면에 뿌린다) | **표** | 행 하나가 실제로 동작을 바꾼다 |

### 지금 어디에 있나

| 값 | 분기하나 | 어디 |
|---|---|---|
| 주문 결제·배송 상태, 상품·SKU 상태 | 한다 — 전이표·상태 축·곁가지 | `check` + enum |
| `scope`·`effect`·`actor_type` | 한다 — `switch` 로 갈린다 | `check` + enum |
| 청약철회 제한 사유 | 한다 — 법이 인정한 셋만(`D2` R4) | `check` |
| 공휴일 | **안 한다** — 그 날짜가 있나만 묻는다 | 표(`holiday`, `ADR 0009`) |
| 권한·역할·부여 | **안 한다** — 판정 엔진이 규칙을 그대로 읽는다 | 표(`ADR 0003`) |
| 필드 그룹 | **한다** — 코드가 그 이름으로 응답을 조립한다 | 표 + enum(`4g`) |
| 셀러 상태 | **안 한다** — Java 도 화면도 안 읽는다. `active` 를 묻는 자리가 SQL 안에만 둘이다 | `check` 만(`43a-22`) |

**마지막 줄이 둘을 겸한다.** 판정 엔진은 그룹 이름을 안 보고 규칙을 그대로 읽으므로 표가 맞는데,
응답을 조립하는 코드는 그룹마다 분기하므로 enum 도 필요하다. **어긋남은 표와 대조해서 막는다**
(`FieldGroupTest`) — `check` 가 아니라 표가 출처인 첫 대조다.

### 열거형으로 분기할 때 `default` 를 안 둔다

값마다 답이 다른 `switch` 에 `default` 를 두면 **값이 하나 늘 때 컴파일이 통과한다.**
그 값은 `default` 가 정한 답을 받는데, 그건 「아직 안 정했다」가 아니라 **정해진 오답**이다.

```java
// 안 한다 — 새 범위가 "아무것도 안 덮는다" 를 조용히 받는다
case "seller" -> ...;
default -> false;

// 한다 — 새 범위를 안 다루면 컴파일이 안 된다
case SELLER -> ...;
```

`43a-20` 이 그 자리였다. `scope` 가 문자열이던 시절 `covers` 의 `default -> false` 와
`scopeWidth` 의 `default -> 0` 이 짝이라, 범위를 하나 더하면 **권한을 준 사람은 줬다고 믿는데
아무도 안 통과하고 오류도 로그도 안 남았다.** 값 목록이 닫혀 있을 때만 되는 방법이라
「가르는 물음」이 enum 을 가리킨 자리와 같은 자리다.

**`default` 가 진짜 필요한 자리**는 값마다가 아니라 **몇몇만 특별한** 경우다. 그때는
`default` 가 오답이 아니라 다수의 정답이라, 값이 늘어도 그 답이 맞다.

### 표로 옮기고 싶어질 때

압력은 대개 셋 중 하나고, **둘은 값 목록 문제가 아니다.**

| 요구 | 진짜 필요한 것 | 값 목록을 옮기나 |
|---|---|---|
| 「배송중」을 「배송 중」으로 고치고 싶다 | 화면 문구 | **아니다** — `D20` 이 다룬다 |
| 다국어 | 라벨 | **아니다** |
| 상태를 화면에서 더 잘게 나누고 싶다 | **세부 상태라는 별도 축** | 축을 하나 더 판다 |

셋째가 오면 **`check` 를 헐지 말고 축을 판다.** 코드가 분기하는 축과 운영이 세분하고 싶은 축이
애초에 다른 축이다 — Magento 가 `state`(코드 상수)와 `status`(표)를 갈라 둔 것이 그 예다.

### 되돌리기 비용이 비대칭이다

헷갈리면 **`check` 쪽을 고른다.** 틀렸을 때 값이 싸다.

| 방향 | 대가 |
|---|---|
| `check` → 표 | 마이그레이션 하나. **오염이 없다** — 빡빡한 쪽에서 느슨한 쪽으로 간다 |
| 표 → `check` | **`check` 가 없던 기간이 곧 오염 구간**이다. 그동안 들어간 행은 안 돌아온다 |

`check` 를 `references` 로 바꾸면 촘촘함도 잃는다. `check` 는 "이 컬럼은 이 일곱 중 하나" 인데
공통코드 표를 가리키는 외래키는 "그 표에 있는 아무 값" 이라, 그룹까지 강제하려면
복합 외래키나 트리거를 다시 얹는다.

### Java 표현

**enum 으로 둔다. 생 문자열을 쓰지 않는다.** 강제 지점을 1위(타입)까지 올리는 자리다(아래 「축 2」).

```java
enum Shipment {
    PREPARING, SHIPPING, DELIVERED, ...;

    /** 저장값. DB 는 소문자고 응답은 대문자다(`D5` 「형식」) */
    String code() { return name().toLowerCase(); }

    /** 모르는 값이면 터진다. 조용히 통과하면 그 뒤가 전부 어긋난다 */
    static Shipment of(String code) { ... }
}
```

문자열로 두면 셋을 잃는다 — **오타를 컴파일러가 못 잡고**, 이름을 바꿀 때 IDE 가 못 따라가고,
"이 값이 어디서 쓰이나" 를 못 묻는다. 같은 글자가 다른 컬럼에도 있으면(`product.status` 와
`sku.status` 가 둘 다 `on_sale` 을 쓴다) 검색으로도 안 갈린다 — **목록이 다르면 enum 도 둘이다.**

DB 에서 읽어 응답으로 내보내는 자리도 enum 을 지난다. 문자열을 그냥 대문자로 올리면
**모르는 값이 그대로 실려 나가서** 화면이 처음 보는 값을 받는다.

**그 자리는 `EnumValue` 하나다**(`43a-10`). 부르는 쪽이 어느 enum 인지 적는다.

```java
EnumValue.of(rs.getString("status"), OrderTransitions.Payment::of)
```

한 곳으로 모은 이유가 **null 가드**다. 그전에는 `code == null ? null : X.of(code).name()` 이
**여섯 파일에 열여덟 벌** 있었고, 사본이 그만큼이면 **한 벌이 패턴을 안 따라도 아무도 모른다** —
`SellerOrderQuery` 의 `return_reason` 한 칸이 실제로 그렇게 새어 나갔다(`43a-6`).

**타입 이름이 호출부에 드러나는 것이 덤이다.** 같은 글자의 다른 값이 그 자리에서 갈린다 —
`shop_order.status`(주문이 어디까지 왔나)와 `payment.status`(승인 시도 한 건의 결과)가
둘 다 `paymentStatus` 라는 헬퍼 이름을 쓰다가 **컴파일이 막아서** 발견됐다(`43a-9`).

### 목록이 둘로 갈리는 것을 테스트가 막는다

`check` 와 enum 이 두 사본이라 어긋날 수 있다. **어긋나는 방향마다 증상이 다르고 둘 다 늦게 드러난다.**

| 어긋남 | 증상 |
|---|---|
| DB 에만 있다 | 그 값을 읽는 순간 `of()` 가 터진다. 조회 하나가 통째로 500 |
| 코드에만 있다 | `update` 가 `check` 에 걸린다. 표에는 있는데 **절대 성공하지 않는 전이** |

그래서 **제약 정의를 읽어 enum 과 대조하는 테스트를 둔다**(`EnumConstraintTest`).
목록을 테스트에 손으로 또 적지 않는다 — 그러면 세 번째 사본이 생긴다.

**대조는 한 파일에 모으고, 빠진 것을 같은 파일이 감시한다**(`43a-19`).
열거형마다 옆에 두면 **새 열거형이 대조를 안 받는 것을 막는 것이 아무것도 없다** —
이 규칙이 여기 적혀 있던 동안 적용은 **열여덟 중 일곱**이었고, 그것을 찾은 것은
이 문서를 읽은 사람이 아니라 `점검 H` 였다. `everyEnumIsAccountedFor` 가 `main` 의
열거형을 전부 걷어서 **대조하든(`PAIRS`·`GENERATED`) 안 하든(`EXEMPT`) 적히지 않으면
빌드를 세운다.** 안 하기로 정한 것은 **이유를 같이 적는다** — 안 적으면 다음 사람이
빠뜨린 것과 못 가른다.

**`check` 가 아닌 출처도 있다.** 값 목록이 생성 열의 식 안에 있으면
(`settlement_item.supplier`) 제약이 아니라 `generation_expression` 에서 뽑고,
표의 행이 출처면 그 표와 대조한다(`FieldGroupTest`).

**제약 정의를 뽑는 헬퍼는 한 벌이다** — `test` 쪽 `support/ConstraintValues`(`11-5`).
두 벌이던 시절 **정규식이 서로 달랐다**: 한쪽은 소문자만 훑어서 `under_50_transactions` 의
`50` 을 놓쳤다. **좁은 쪽을 베끼면 그 값이 조용히 빠지고, 빠진 채로 테스트가 통과한다** —
이 절이 막으려는 것과 같은 모양의 사본이었다.

**정의 안이 여러 갈래인 제약은 갈래마다 대조한다.** `order_status_history_status_check` 가
`case` 로 층마다 다른 목록을 적는데, 통째로 뽑아 합집합만 보면
**배송 값이 결제 갈래에 섞인 것을 못 잡는다** — 합치면 어차피 같은 집합이라 통과한다.

### 길이 상한은 앱과 DB 양쪽에 둔다

**한쪽만 두면 역할 하나가 통째로 빈다.** 둘이 다른 일을 한다.

| 어디 | 무엇을 하나 | 없으면 |
|---|---|---|
| `@Size(max = N)` | 400 과 **어느 칸인지**를 내준다 | 제약 위반이 `DataIntegrityViolationException` 으로 올라와 **500 이 나간다** |
| `check (length(...))` | 앱을 안 지나는 입구를 막는다 | 배치·시드·`psql` 에 **상한이 사실상 없다** |

**그래서 숫자가 두 곳에 산다.** 갈리는 것은 `LengthConstraintTest` 가 막는다 —
제약 정의를 **DB 에서** 읽고 요청 record 의 `@Size` 와 대조한다. 마이그레이션 파일을 훑으면
**적힌 것**을 보게 되는데 물어야 하는 것은 **지금 도는 스키마**다.

**빠뜨릴 자리가 없다**(`Q28`). 제약 이름을 `pg_constraint` 에서 **전부 걷어**,
하나하나가 **대조되거나 안 하는 이유가 적혀 있어야** 한다 — 둘 다 아니면 빌드가 선다.
`EnumConstraintTest` 의 열거값 회계와 같은 틀이다.

**양방향으로 잰다.** 없어진 제약이 목록에 남는 것도 실패다 — 그러면 그 목록이 무엇을 덮는지
아무도 모르게 된다.

**안 대조하는 것 여덟**은 값을 **바깥이나 우리 코드가 채우는 자리**(결제 대행사가 준 값, 배치가 쓴 실패
사유, 헤더로 받은 멱등 키)와, **아직 쓰는 코드가 없는 컬럼 둘**(`return_note` 의 접수 사유·검수 소견 —
그 입구가 `43a` 다)이다.

**사유 컬럼 넷은 `Q46` 이 이었다.** 서비스가 요청의 사유를 옮겨 담는 자리라 호출 사슬을 따라가야
찾아진다. **`order_status_history_note.reason` 은 입구가 넷**이고 넷을 다 적었다 — 하나만 이으면
나머지 셋이 갈려도 안 걸린다.

**갈렸던 적이 있다**(`점검 L`). 같은 이메일을 가입이 254 로, 변경이 320 으로 재고 있었다.

**`@Size` 는 record component 에 안 남는다.** 그 애너테이션의 `@Target` 에
`RECORD_COMPONENT` 가 없어서 컴파일러가 필드로 보낸다 — `RecordComponent.getAnnotation`
만 보면 **열 칸이 「없다」로 나오고 대조가 통째로 헛돈다**(`stack.md`).

**빈 문자열 허용 여부를 앱과 맞춘다.** `@NotBlank` 가 붙은 칸은 `between 1 and N`,
안 붙은 칸은 `<= N` 이다. 갈리면 **앱이 받은 것을 DB 가 거부해서 그 요청이 500 이 된다.**

**수마다 출처를 제약 옆에 적는다.** 표준에서 온 값과 우리가 찍은 값이 코드에서 안 갈린다 —
제약은 한 번 들어가면 `alter` 로만 고쳐지므로 그때는 이미 관례가 되어 있다.

```sql
-- 254 는 RFC 5321 §4.5.3.1.3 에서 온다(표준, 2순위)
-- 100 은 관례다(4순위). 스마트스토어 100 · Shopify 255
-- 200 은 근거 없이 정한 값이다. 택배 연동이 붙으면 그 규격이 상한을 정한다
```

### SQL 텍스트 안의 리터럴은 안 바꿨다

`where p.status = 'on_sale'` 같은 조회 조건은 그대로 뒀다. **자바 식별자가 아니라 그 쿼리의
조건 자체**라서고, `:status` 로 빼면 쿼리만 봐서는 무엇을 거르는지 안 보인다.

대신 위험이 남는 것을 안다 — **읽기 쪽 오타는 0건을 조용히 돌려준다.** 쓰기 쪽은 `check` 가 잡는다.
읽기 쪽은 그 조회의 테스트가 유일한 방벽이라, 공개 목록처럼 조건이 중요한 자리는
**0건이 아님을 단언하는 테스트**를 같이 둔다.

### 운영이 늘리는 코드가 생기면

택배사·상품 카테고리처럼 **운영자가 행을 넣는 표**가 오면 그때 정한다. 지금은 하나도 없어서
"정할 근거가 실제로 생겼다"(`CLAUDE.md`)가 안 찼다. 정할 때 이 둘을 먼저 센다.

- **코드가 이름으로 부르는 값이 몇 개냐.** 표에 200개가 있어도 코드가 아는 것은 서너 개다
- 서넛이면 **그 몇 개만 손으로 enum 에 쓰고, 표에 살아 있는지 테스트가 확인**한다.
  쉰이 넘으면 그때 생성기가 값을 한다

생성기로 간다면 **빌드가 DB 에 묶이지 않게** 한다(사용자 선택) — 생성물을 커밋하고
생성 태스크는 따로 돌린다. 그러면 평소 빌드는 DB 없이 돌고, 어긋남은 diff 로 드러난다.
그리고 상수명이 되는 컬럼에 **넷을 같이 건다**: 식별자 형식 `check`, 유니크, 수정 금지, 물리 삭제 금지.
운영자가 그 값을 고치거나 지우면 **소스가 컴파일되지 않는다.**

## 규칙의 우선순위

규칙이 서로 어긋날 때 무엇이 이기나. **축이 둘이고 섞으면 안 된다.**

### 축 1 — 출처. 충돌하면 무엇이 이기나

| 순위 | 출처 | 어기면 | 우리가 고칠 수 있나 |
|---|---|---|---|
| 1 | **법·규정** | 과태료·형사·계약 무효 | 못 고친다 |
| 2 | **표준·규격** | 남의 시스템과 안 붙는다 | 못 고친다 |
| 3 | **프로젝트 규약** | 아무 일도 안 난다 | 고친다 — 단 문서를 먼저 |
| 4 | **업계 관례** | 아무 일도 안 난다 | 근거만 대면 버린다 |

생성형 도구가 들고 오는 기본값도 4번이다. `design-taste-frontend` 스킬의 스택 선택이 그 예고,
우리 결정(3번)이 이긴다(`D20`).

4번을 버린 예가 `D22` 다. SQL Style Guide 의 복수형 테이블을 버렸고 같은 가이드의
"`id` 를 기본 식별자로 쓰지 말라" 는 따랐다. **가이드를 통째로 받거나 버리는 게 아니라 항목마다 근거를 댄다.**

### 플랫폼 사실은 순위 다툼에 안 들어온다

Postgres 가 마이크로초 아래를 올린다든가, Next 가 `cookies()` 를 쓴 라우트를 dynamic 으로
돌린다든가 하는 것들이다. **법도 표준도 규약도 관례도 아니다.**

순위표에 자리가 없는 이유는 **어길 수가 없어서**다. 위 넷은 "어기면 무슨 일이 나나" 로 줄을 세우는데
플랫폼 사실은 어기는 것이 아니라 **모르면 틀리는 것**이다.

| | 출처 넷 | 플랫폼 사실 |
|---|---|---|
| 성격 | 지킬지 말지를 고른다 | **전제다.** 고를 것이 없다 |
| 어긋나면 | 위 순위로 이긴 쪽을 따른다 | **규약이 진다.** 규약을 고친다 |
| 어디에 적나 | 이 문서와 D 문서들 | `stack.md` |

**규약이 플랫폼 사실과 어긋나면 규약을 고친다.** 그 반대는 불가능하다.

강제 지점(아래 축 2)도 대개 못 내린다 — 타입으로도 제약으로도 못 막고 **테스트가 유일한 방벽**인
경우가 많다. 그래서 `stack.md` 가 "기억으로 쓰면 틀리는 자리" 를 모으는 문서다.

### 축 2 — 강제 지점. 어디에 걸어야 실제로 막히나

| 순위 | 지점 | 언제 걸리나 |
|---|---|---|
| 1 | **타입·스키마 구조** | 컴파일·설계 시점. 어길 방법이 없다 |
| 2 | **DB 제약** | 쿼리 실행 순간 |
| 3 | **앱 검증** | 요청 처리 중. **새 입구가 생기면 빠뜨린다** |
| 4 | **테스트** | 돌릴 때만 |
| 5 | **주석·문서** | 사람이 읽을 때만 |

**DB 제약은 출처가 아니라 강제 지점이다.** 우리가 만든 것이라 출처로는 3번(프로젝트 규약)인데,
막는 즉시성은 법보다 세다. 법은 5년 뒤에 걸리고 제약은 0.1초 뒤에 걸린다.

### 안 나가게 하는 것도 강제 지점이 있다

위 표는 **잘못 들어오는 것**을 막는 순서다. **잘못 나가는 것**은 순서가 따로다.

| 순위 | 지점 | 언제 걸리나 |
|---|---|---|
| 1 | **계약에 칸이 없다** | 응답 record 에 필드를 안 만든다. 실을 방법이 없다 |
| 2 | **마스킹 규칙** | 요청 처리 중. **새 컬럼을 더할 때 빠뜨린다** |
| 3 | **테스트** | 돌릴 때만 |

### 어느 쪽을 언제 쓰나

**보는 사람에 따라 갈리느냐**가 가른다.

| 상황 | 어디 | 예 |
|---|---|---|
| 누구에게도 안 나간다 | **계약에서 뺀다** | 셀러 신원 응답의 수수료율·기본 배송비(`14a`). 우리와 셀러 사이의 조건이라 사는 사람이 볼 것이 아니다 |
| 같은 자원인데 사람마다 갈린다 | **마스킹** | 주문의 `payment` 필드 그룹(`4d`). 본인은 보고 셀러·감사자는 못 본다 |

**갈리지 않는데 마스킹을 걸지 않는다.** 규칙이 하나 늘고, 새 컬럼을 더할 때 그 규칙에
넣는 것을 빠뜨리면 조용히 샌다. 아예 record 를 둘로 두면 그 실수가 성립하지 않는다.

`ProductQuery` 가 공개용과 셀러용 record 를 가른 것이 같은 판단이다.

### 두 축을 합치면

**출처가 위일수록 반드시 지키고, 지키는 자리는 가능한 한 아래로 내린다.**

```
전자상거래법 제17조제2항  (출처 1위)
  → D2 R4 요건표          (문서 — 강제 지점 5위)
    → product_withdrawal_reason_check  (강제 지점 2위)
```

문서에만 적힌 법은 안 지켜진다. **내릴 수 있는 데까지 내린 다음, 못 내린 것만 문서에 남긴다.**

## `public` 에는 근거가 있어야 한다

**패키지 밖에서 안 쓰는 것을 열어 두지 않는다**(`43a-27`). 아무도 안 쓰는 `public` 은 다음 사람에게
「여기로 들어와도 된다」는 신호라, 계층을 지나 부르는 코드가 그 자리로 들어온다.

**가르는 것은 하나다 — 패키지 밖에서 실제로 쓰나.** `43a-20` 이 `Scope` 를 열고 `43a-25` 가
`NotificationTemplates.Version` 을 좁힌 것이 같은 물음의 반대 답이었고, 그 물음이 이 규칙이다.

| 무엇 | 열어 두나 | 왜 |
|---|---|---|
| 스프링이 부르는 것(`@Component` 메타 표시) | **본다 안 한다** | 컨테이너가 부르므로 밖에서 안 쓰는 것이 정상이다 |
| 다른 패키지의 테스트가 쓰는 것 | **연다** | 테스트도 소비자다 — `FieldGroupTest` 가 `auth` 에서 `account.UserFields` 를 대조한다 |
| 그 밖에 밖에서 안 쓰는 것 | **좁힌다** | 좁히면 잘못 쓰는 코드가 컴파일이 안 된다(1위) |

**`PublicSurfaceTest` 가 지킨다.** `ArchitectureTest` 와 파일이 갈린 이유는 읽는 범위다 —
저쪽은 `main` 만 보고 이쪽은 테스트도 센다. 한 파일에서 범위만 바꾸면 저쪽 순환 규칙이 가짜 순환을 문다.

## 접근성

**화면을 만드는 모든 청크에 걸린다.** 출처는 법이다 — 장애인차별금지법 제20조·제21조가
정보 접근에서의 차별을 금지하고, 기술 기준은 국가표준 **KWCAG 2.2** 다(WCAG 2.1 기반).

민간 사업자도 의무 대상이다. 단계적 적용이 2015년에 끝났다.

### 왜 나중에 하면 안 되나

다른 규칙과 다른 점이 하나 있다. **고치는 것이 아니라 다시 짜는 것이 된다.**

| 항목 | 나중에 붙이면 |
|---|---|
| 시맨틱 마크업 | 마크업을 다시 짠다 |
| 키보드 조작 순서 | 컴포넌트 구조가 바뀐다 |
| 대비비 | 색 팔레트를 다시 고른다 |
| 폼 레이블·오류 안내 | 입력이 있는 모든 화면을 고친다 |

`13-0`(디자인 취향 스킬)을 화면 전에 까는 것과 같은 이유다.

**화면 기준은 `screen-rules.md`(D20)가 정한다.** 여기서는 "언제 보나" 만 정한다 —
**마크업을 쓰는 청크는 예외 없이 본다.**

## 불변식

**절대 깨지면 안 되는 등식**을 뜻한다. 계산 방법이 아니라 **계산이 틀렸는지 아는 방법**이다.

`D3` 가 지급액 공식을 적어 뒀지만 그건 어떻게 구하나이고,
구한 값이 맞는지는 답하지 않는다. **정산은 1원만 어긋나도 사고다.**

### 어디에 거나

「강제 지점」 순서를 그대로 따른다. 위에서부터 되는 것을 고른다.

| 지점 | 쓸 수 있는 경우 | 예 |
|---|---|---|
| `check` 제약 | 한 행 안에서 끝난다 | `on_hand >= 0`, `price >= 0` |
| 트리거 | 다른 행·테이블을 봐야 한다 | 주문 금액 = 항목 합 |
| 테스트 | 위 둘로 못 건다 | 정산 지급액 공식 |

**한 행 안에서 끝나는 것을 테스트로 검증하지 않는다.** 테스트는 돌릴 때만 막고 제약은 언제나 막는다.

### 새 불변식을 찾는 자리

**합계를 저장하는 순간**이다. 합계는 원본과 어긋날 수 있는 유일한 종류의 값이다.
저장하는 합계마다 "무엇의 합인가" 를 등식으로 적고, 그 등식을 어디서 강제할지 정한다.

## 라이선스

**의존성과 인용 자료 둘 다 본다.**

| 대상 | 언제 보나 | 무엇을 |
|---|---|---|
| 의존성 | `build.gradle.kts` 에 줄을 추가할 때 | 라이선스 종류. GPL 계열이면 그 자리에서 멈추고 판단한다 |
| 인용 자료 | 기준 문서에 바깥 자료를 근거로 삼을 때 | 저작자·라이선스를 `external-references.md` 에 같이 적는다 |

두 번째가 실제로 걸려 있다. `D22` 가 기준으로 삼은 **SQL Style Guide 는 CC BY-SA 4.0** 이다.
**인용은 자유롭고 파생물은 같은 라이선스로 전파된다.** 우리 문서는 규칙을 골라 쓰고 벗어난 것을
따로 적은 것이라 인용에 가깝지만, **판단한 적 없는 것과 판단해서 괜찮은 것은 다르다.**

**저장소는 공개고 Apache-2.0 이다**(`2l`, 2026-09-06). 루트의 `LICENSE` 가 원문이다.

조건이 이미 차 있었다 — 이 절은 「공개하기로 하면 먼저 다시 본다」고 적어 뒀는데,
`gh api` 로 재 보니 저장소가 벌써 `public` 이었다. **공개인데 라이선스가 없으면
저작권법 기본값(모든 권리 유보)이라 읽을 수는 있고 쓸 수는 없다.**

**그래서 인용 자료의 판단이 미룰 수 없는 것이 됐다.** 디자인 스킬의 MIT 고지는 `2l-1` 이,
`D22` 의 SQL 절 표시는 `2l-2` 가 맡는다.

## 빈 값에 뜻을 싣지 않는다

**빈 집합·null 에 "제한 없음" 같은 뜻을 실으면 그 뜻이 주석에만 남는다.**
읽는 사람이 주석을 봐야 안 틀리므로 가장 약한 강제 지점이다(위 「규칙의 우선순위」).

권한에서 이 모양이 계속 나온다. `own`·`seller` 는 값으로 표현되지만
`all` 은 **"제한이 없다"** 라서 넣을 값이 없다.

```java
// 안 한다 — 빈 집합이 "아무것도 없음" 과 "전부" 를 겸한다
Set<Long> visibleSellers

// 한다 — switch 가 두 경우를 다 안 다루면 컴파일이 안 된다
Allowed<Long> visibleSellers
```

`Allowed<T>` 가 그 자리다(청크 4e). **새로 "전부/일부" 를 다루게 되면 이걸 쓴다.**

### SQL 에서는 조건의 부재가 값이 아니다

같은 문제가 쿼리에도 온다. `all` 은 **조건 자체가 없어야 하는데** `?` 자리에 "없음" 을 못 넣는다.

```sql
and (:seesEverything or p.seller_id = any(:sellers))
```

**지우는 대신 무력화한다.** 조건을 빼려고 SQL 을 분기하면 쿼리가 두 벌이 되고 한쪽만 고치는 날이 온다.

대가는 플래너가 `or` 를 못 풀 때 인덱스를 안 타는 것이다. **측정한 뒤에 손본다**(청크 42).

### 바깥 조인 쪽 숫자는 `getObject` 로 받는다

`ResultSet.getLong` 은 **null 을 0 으로 준다.** 기본형이라 null 을 담을 자리가 없어서고,
`wasNull()` 을 따로 묻지 않으면 **틀렸다는 신호가 없다.** 0 은 식별자로도 금액으로도
그럴듯한 값이라 화면까지 조용히 내려간다.

```java
// 안 한다 — 조합이 없는 SKU 가 0 번 선택지를 가리킨다
rs.getLong("product_option_value_id")

// 한다 — 없으면 null 이고, 부르는 쪽이 거를지 말지를 고른다
rs.getObject("product_option_value_id", Long.class)
```

**걸리는 자리는 둘이다** — `left join` 의 바깥 쪽 컬럼, 그리고 `null` 을 허용하는 컬럼.
안쪽 조인이거나 `coalesce` 가 씌워져 있으면 `getLong` 이 맞다 — 그쪽은 null 이 안 온다.
같은 이유로 시각·문자열은 이미 `getObject`·`getString` 이라 안 걸린다.

## 마이그레이션

**접었다**(`Q36`, 2026-09-14) — `add column` 스물넷을 표의 `create` 일곱 파일로 옮겼다.
`pg_dump --schema-only` 전후 diff 가 0 이었다(다른 것은 pg_dump 가 실행마다 새로 만드는 토큰 두 줄뿐).
**배포가 나가면 다시는 못 한다** — 그 뒤로는 `alter` 가 영구다.

**재사용 컨테이너를 지워야 한다.** 적용된 마이그레이션을 고치면 Flyway 체크섬이 깨지는데,
Testcontainers 가 컨테이너를 재사용해서 **옛 이력이 남는다** — `docker rm -f $(docker ps -aq --filter label=org.testcontainers=true)`.

**배포 전엔 `alter` 를 쌓아도 된다. 배포 직전에 한 번 `create` 로 접는다**(사용자 결정 2026-09-13, `Q36`).

처음 규칙은 「쌓지 않고 그때그때 `create` 를 고친다」였는데 **`V25` 부터 열다섯 파일이 `add column` 24개를 쌓았다** —
청크마다 옛 파일을 고치는 비용을 아무도 안 냈고, 규칙은 문서에만 남았다. 접는 것은 **한 번이면 된다**:
빈 DB 에서 처음부터 올리는 한 `create` 로 접은 스키마와 `alter` 로 쌓은 스키마는 **같은 구조**라 기능이 안 바뀐다.
그래서 접기를 마지막 청크 하나(`Q36`)로 미루고, 닫힘은 `pg_dump --schema-only` 전후 diff 가 0 인 것으로 잰다.

```sql
-- 지금: 쌓는다. 파일 하나에 컬럼 하나가 와도 된다
alter table seller add column commission_bp int not null default 1000;

-- 접을 때(Q36): V4 의 create table seller 로 옮기고 이 줄을 지운다
```

**치르는 값은 그때까지 사람이 읽는 비용이다.** `alter` 를 쌓으면 **테이블의 최종 모양을 알려면 마이그레이션을 전부 읽어야 한다.**
컬럼 하나가 어디서 왔는지, `not null` 이 언제 풀렸는지가 파일 여럿에 흩어진다. 테스트는 도는 스키마를 읽어서 영향이 없다.

접은 뒤에는 **DB 를 재생성한다**(`docker compose down -v`). Flyway 체크섬이 깨져서 그것 말고는 방법이 없다.
테스트는 컨테이너를 매번 새로 띄우므로 영향이 없다.

### 이 방법을 못 쓰는 순간

**배포가 한 번이라도 나가면 끝난다.** 남이 이미 그 마이그레이션을 돌렸으면 되돌릴 방법이 없다.
그때부터는 `alter` 를 새 파일로 쌓는 것이 유일한 길이다 — 접기(`Q36`)는 **그 전에** 한 번 해야 한다.

지금 쓸 수 있는 이유는 로컬 전용이고 배포한 적이 없어서다. 청크 `3e`·`5i` 가 그때그때 접는 방식으로 갔고, 그 뒤로는 쌓았다.

### 어느 파일을 고치나

접을 때 컬럼이 갈 곳이다. **그 테이블이 의존하는 것이 이미 선 파일.** 컬럼이 남의 테이블을 참조하면 그 테이블보다 먼저 못 온다.

`user_role` 이 그 예다. 권한 스키마(`V2`)의 일부처럼 보이지만 부여가 셀러를 가리켜서
`seller` 가 서는 `V4` 에 `create` 가 있다. `V2` 에서 만들고 `V4` 에서 컬럼을 붙이면
**한 테이블의 모양이 두 파일로 흩어진다** — 그게 이 절이 막으려는 것이다.

`create` 를 옮기면 되는 자리에서 `alter` 를 쓰지 않는다. 파일 순서가 곧 의존 순서다.

## 법·규정에서 온 것

`D2` 의 요건(R번호)이 코드에 닿을 때 지킨다. **법은 어겨도 컴파일이 통과하고 테스트도 초록이다** —
사람이 보는 것 말고 걸릴 자리가 없어서, 걸릴 자리를 만드는 것이 이 절의 목적이다.

### 가장 낮은 층에 건다

같은 요건을 걸 수 있는 자리가 여럿이면 아래쪽을 고른다.

```
타입·스키마 구조  >  DB 제약(check·not null·references)  >  앱 검증  >  주석
```

내려갈수록 안 지킬 방법이 사라진다. 앱 검증은 새 입구가 생기면 빠뜨리고, 주석은 아무것도 안 막는다.

R4(청약철회 제한)가 `product_withdrawal_reason_check` 로 내려간 것이 그 예다.
R6(거래기록 5년)은 한 칸 더 내려가서 **`order` 에 `deleted_at` 을 안 두는 것**으로 끝났다 —
지우지 말자는 약속이 아니라 지울 컬럼이 없는 구조다.

### 법이 인정한 목록은 닫는다

법이 사유·유형을 열거하면 그 값만 들어가게 막는다. 자유 텍스트로 두면
**법이 인정하지 않는 값이 화면에 나간다.**

```sql
check (withdrawal_restriction_reason in ('copyable_media', 'made_to_order'))
```

열거된 것 전부가 데이터로 표현되는 건 아니다. R4 의 다섯 중 셋은 받은 물건의 상태 판단이라
상품 속성이 아니다. **조문을 통째로 옮기지 말고 데이터가 되는 것만 고른다.**

### 개인정보 컬럼은 셋을 같이 채운다

새로 만들 때 아래 셋이 다 있어야 한다. 하나라도 비면 그 컬럼을 안 만든다.

| 채울 곳 | 무엇을 |
|---|---|
| 동의 항목(`consent_item`) | 수집 항목에 그 컬럼이 있나 |
| `D13` 데이터 수명 | 보유기간이 정해졌나 |
| 파기 코드 | 그 기간이 지나면 실제로 지우는 자리가 있나 |

**수집하는 코드가 파기하는 코드보다 먼저 나오면 그 사이가 위반 구간이다.**
`user_consent.acted_ip` 가 그렇게 됐다 — 5-0 이 받기 시작했는데 파기는 `5i` 다.

### cascade 를 파기 수단으로 쓰지 않는다

수명 컬럼(`deleted_at`)을 쓰는 자원은 **물리 삭제가 안 일어난다.** 탈퇴는 `update` 라
`on delete cascade` 가 안 걸린다. 파기는 파기 배치가 명시적으로 지운다.

외래키의 cascade 는 개발 중 정리와 파기 배치가 행을 지울 때만 쓰인다(`domain-model.md`).

### 법에서 온 값에는 요건 번호를 적는다

```java
/** 청약철회 기간. 전자상거래법 제17조(`D2` R3). */
private static final int WITHDRAWAL_DAYS = 7;
```

개정되면 이 번호로 찾는다. 번호가 없으면 어느 상수가 법에서 온 것인지 코드에서 안 갈린다.
「설정과 상수」의 규칙과 같은 이유고, 출처가 법이면 더 세게 걸린다.

### 지켜지는지는 위에서 내려가며 확인한다

**다른 규칙과 점검 방향이 반대다.**

| 규칙 | 어긋난 것이 | 어떻게 찾나 |
|---|---|---|
| 코딩 규약 | **코드에 있다** | 코드를 훑는다. `select *` 를 찾는 식 |
| **법 요건** | **코드에 없다** | **요건표에서 내려간다.** 코드를 훑으면 안 보인다 |

`R1` 이 그 예다. **셀러 신원 표시가 코드에 흔적이 0이었다** — 컬럼은 있는데 내리는 경로가 없었고,
어느 파일을 열어도 빠진 것이 안 드러난다. `D2` 를 읽고 "이 요건을 누가 채웠나" 를 물어야 나왔다.

그래서 `D2` 의 「강제 지점」 칸에 **검사할 수 있는 이름**을 적는다.
없는 것을 찾으려면 **있어야 할 것의 목록**이 먼저 있어야 한다.

### 안 넣은 것도 근거를 남긴다

규칙을 **일부러 안 넣은 것**은 빠뜨린 것과 코드에서 구분이 안 된다.
근거가 없으면 다음 사람이 채워 넣는다.

`D14` 가 비밀번호 주기 변경과 복잡도 조합 강제를 안 쓴다. NIST SP 800-63B 가 근거고
그 문서에 적혀 있다. 안 적어 두면 "보안 강화" 로 다시 들어온다.

## 이 문서를 고칠 때

**청크를 하다가 이 규약과 다르게 짜야 할 이유가 생기면, 코드를 먼저 바꾸지 말고 여기를 고친다.**
문서에 없는 방식이 코드에 먼저 들어가면 다음 사람이 그것을 관례로 본다.
