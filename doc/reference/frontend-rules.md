# 프론트 계층 규약

화면 코드가 **어디서 돌고 서버를 어떻게 부르나**. `D14` 가 백엔드의 계층을 정했고 여기서는 프론트의 계층을 정한다.

**무엇을 보여주나는 `screen-rules.md`(D17)가 정한다.** 이 문서는 그것을 어느 층에서 그리나만 다룬다.

## 기준

| 대상 | 기준 자료 |
|---|---|
| 프레임워크 | Next 16 App Router(`stack.md` 버전표). 판을 올리면 아래 「캐시」 절부터 다시 본다 |
| 판마다 갈리는 것 | **번들된 문서** `frontend/node_modules/next/dist/docs/` — 웹 문서는 최신 판을 보여줘서 우리 판과 다를 수 있다 |

**기억으로 쓰면 틀린다.** Next 는 판마다 캐시 기본값과 API 가 갈렸고, 「캐시」 절은 번들된 문서를 읽고 확인한 것이다.

## 계층

```
서버 컴포넌트  →  api.ts  →  백엔드
   그린다         부른다      판정한다

클라이언트 컴포넌트  →  api.ts  →  백엔드
   누른다·입력한다
```

| 규칙 | 왜 |
|---|---|
| 서버를 부르는 곳은 `api.ts`·`api-session.ts` 둘뿐이다 | CSRF·오류 변환·세션 운반이 거기에만 있다. 우회하면 어떤 응답만 변환을 안 거친 채 화면에 닿는다. **eslint 가 막는다**(`no-restricted-globals`·`no-restricted-imports`, `39`) |
| **표기를 안 바꾼다** | 서버 JSON 이 snake_case 고 화면은 받은 그대로 읽는다(`D5`). 화면의 타입도 `account_id`·`held_until` 그대로다 — 변환 층을 두면 같은 필드에 이름이 둘 생긴다. 이식 원본은 카멜로 바꿨는데 그쪽은 응답 규약이 달랐다 |
| 화면은 역할 이름을 모른다 | `/api/me` 의 `role` 로 분기하지 않는다. 판정이 두 벌이 된다(`D17` 「권한 없는 것은 숨긴다」) |
| 화면은 동작↔경로 표를 안 든다 | 오류는 `type` 의 슬러그로, 이동은 응답의 식별자로. 표를 들면 한쪽만 고쳐진다 |
| 입력칸 상한은 서버와 같다 | 요청 `@Size(max)` 가 있는 칸은 `Field` 에 같은 `maxLength` 를 **리터럴로** 준다. 갈리면 화면이 받아 준 글자를 서버가 400 으로 돌려보낸다 — `ScreenLengthTest`(`G9`)가 폼 글자와 DTO 를 대조한다 |

## 서버 컴포넌트가 기본이다

**`"use client"` 를 안 붙인 것이 기본값이고, 붙이는 쪽이 근거를 댄다.**

기본을 반대로 두면 안 되는 이유가 `D14` 의 「기본이 열림이면 안 된다」와 같다 — **아무 생각 없이 지나간 화면이 느린 쪽으로 떨어진다.**

### 클라이언트로 내리는 경우

아래 넷 중 하나가 필요할 때만 내린다.

| 필요한 것 | 우리 화면의 예 |
|---|---|
| 입력을 받는다 | 로그인·가입·카드번호 폼 |
| 상태를 들고 있는다 | 고른 좌석(`SeatMap`), 쥐고 있는 멱등키(`HoldForm`·`CheckoutForm`) |
| 사용자 조작에 반응한다 | 제출 버튼의 잠김(`SubmitButton`) |
| 브라우저 API 를 쓴다 | `document.cookie`(`api.ts`), 시계(`Countdown`) |

**경계를 잎사귀로 내린다.** 페이지 통째로 `"use client"` 를 붙이지 않고 입력이 있는 조각만 뗀다.
`/login` 이 그 모양이다 — 페이지는 서버 컴포넌트고 폼만 클라이언트다. `/performances/[performanceId]` 도 같다: 좌석 현황은 서버가 읽고 고르는 것만 `HoldForm` 이다.

### 읽기는 서버, 쓰기는 클라이언트

서버 입구 둘은 **읽기 전용**이다. 쓰기(선점·결제·가입)는 클라이언트 컴포넌트에서 브라우저 입구로 한다 —
CSRF 토큰이 브라우저 쿠키에 있고, 멱등키를 쥐고 재시도하는 것도 그쪽이다(`D4`).

## 서버를 부르는 입구가 셋이다

| 입구 | 어디서 도나 | 쿠키 | CSRF | 파일 |
|---|---|---|---|---|
| `api()` | 클라이언트 컴포넌트 | 브라우저가 자동으로 붙인다 | 붙인다 | `api.ts` |
| `apiPublic()` | 서버 컴포넌트 | **안 싣는다.** 누구에게나 같은 데이터 | 필요 없다 | `api.ts` |
| `apiSession()` | 서버 컴포넌트 | **손으로 싣는다**(아래) | 필요 없다 | `api-session.ts` |

**서버 입구를 둘로 가른 것은 캐시 때문이다.** 공개 데이터는 캐시를 켤 수 있고 사람마다 다른 것은 못 켠다.
한 함수에 옵션으로 두면 그 옵션을 빠뜨린 화면이 **남의 예매를 캐시한다.**

**`apiSession()` 만 파일이 다르다.** `next/headers` 를 쓰는데 그것을 `api.ts` 에 들이면 그 파일을 가져다 쓰는 클라이언트 컴포넌트가 전부 빌드에서 깨진다.
오류 변환(`toApiError`)은 `api.ts` 것을 가져다 쓴다 — 두 벌이면 어떤 응답만 다르게 읽힌다.

**주소가 다르다.** 브라우저 입구는 `/api/...` 상대경로라 `next.config.ts` 의 rewrite 프록시를 지나고, 서버 입구는 Next 서버가 백엔드에 직접 붙어서 `BACKEND_ORIGIN` 절대 주소를 쓴다.
**그 rewrite 는 `next build` 때 굳는다** — 시작할 때 주는 env 로는 안 바뀐다(`stack.md`).

**CSRF 토큰은 `api.ts` 가 채운다.** 서버는 토큰을 읽을 때 쿠키를 심으므로 화면만 띄우고 바로 누르면 쿠키가 없다 — 그때 `/api/health` 를 한 번 두드린다.

## 인증이 필요한 데이터

`/me`·`/reservations/[reservationId]` 처럼 로그인해야 보는 화면도 **서버 컴포넌트로 그린다.** 서버 입구가 세션 쿠키를 손으로 실어 보낸다.

```
브라우저 → [Next 서버]  cookies() 로 TICKETSESSION 을 꺼내 헤더에 싣는다 → 백엔드
```

**첫 그림이 비지 않는다.** 내 예매는 사람마다 달라서 캐시가 안 걸린다. 클라이언트에서 부르면 `HTML → JS → 요청 → 데이터` 를 거쳐 들어갈 때마다 빈 뼈대를 먼저 본다.
**화면군마다 다시 판단하지 않는다** — 「공개는 서버, 인증은 클라이언트」로 가르면 섞인 화면이 오는 순간 답이 없다.

### 프론트가 세션을 해석하는 것이 아니다

| 무엇 | 누가 |
|---|---|
| 쿠키 문자열을 헤더에 얹는다 | 브라우저·Next 서버 |
| **그 값이 누구인지 판정한다** | **백엔드만** |

세션은 서버 쪽(Redis, `20a`)에 있고 쿠키에 든 것은 뜻 없는 식별자다. 프론트가 열어도 나오는 것이 없다.

### 401 은 입구가 잡는다

세션이 없거나 끊기면 입구가 **그 자리에서 로그인 화면으로 보낸다.** 예외로 올려서 화면마다 잡게 하면 한 화면이 빠뜨렸을 때 **그 화면만 조용히 빈 목록**이 된다.

**왜 나왔는지를 알린다**(`D17` 「401 은 조용히 보내지 않는다」). 다만 **입구에 따라 말할 수 있는 것이 다르다** — 마무리 9차가 가른 자리다.

| 입구 | 보내는 표시 | 왜 |
|---|---|---|
| `apiSession()` | 쿠키가 있었으면 `session-expired`, 없었으면 `login-required` | 서버 컴포넌트는 쿠키를 읽을 수 있어 둘을 가른다 |
| `api()` | 언제나 `login-required` | 세션 쿠키가 HttpOnly 라 **로그인한 적이 있었는지를 모른다.** 한 번도 로그인 안 한 사람에게 「만료됐다」고 하면 사실이 아닌 것을 말하는 것이다 |

**로그인·가입 경로와 `login-failed` 는 뺀다.** 거기서 나는 401 은 「세션이 없다」가 아니라 「이번 시도가 틀렸다」다 — 그 폼이 어느 칸도 지목하지 않는 오류로 그린다. `login-failed` 는 경로 밖에서도 난다 — 탈퇴가 비밀번호를 다시 받는다(`44c`). 그래서 `api()` 는 401 의 `type` 을 읽고 가른다.

**공개 화면 위의 로그인 필수 조작은 누를 때 보낸다.** 좌석 현황은 로그인 전에 보고(`10`) 선점 버튼을 누르면 401 → 로그인이다.
대가는 **고른 좌석을 잃는 것**인데, 좌석 상태는 초 단위로 바뀌어 돌아오면 어차피 현황을 다시 받아야 하므로 받아들인다.
로그인해야만 뜻이 있는 화면(`/me`·`/reservations/[reservationId]`)은 반대다 — 서버 컴포넌트가 첫 요청에서 막는다.

### 그래서 운반을 한 군데에 가둔다

우리 코드가 쿠키를 만지기 시작하면 실수 셋이 새로 가능해진다 — 세션 값을 로그에 찍는다(`D10` 이 금지), 결과가 캐시된다(남의 예매가 보인다), 백엔드 아닌 곳에 싣는다.
셋 다 **만지는 자리가 여럿일 때** 나는 사고라 서버 입구 하나에만 둔다.

**막는 자리가 둘이다.** `next/headers` 를 다른 파일이 들면 eslint(`no-restricted-imports`)가 물고, `api-session.ts` 를 클라이언트 컴포넌트가 들면 `next build` 가 선다. 빌드가 막는 것을 또 막으면 규칙이 두 벌이라 `server-only` 표식은 안 얹는다.

**나르는 쿠키를 목록으로 가둔다.** 지금은 `TICKETSESSION` 하나다. 요청에 온 것을 통째로 넘기면 나중에 프론트가 자기 쿠키를 만들었을 때 그것까지 백엔드로 샌다.

## 폼이 제출 중인지를 손으로 들지 않는다

**`<form action={fn}>` 은 `fn` 을 전환 안에서 돌리고, `fn` 이 끝날 때까지 그 안의 상태 갱신을 커밋하지 않는다.**
그래서 액션 첫 줄의 `setPending(true)` 가 화면에 못 닿는다 — 버튼이 안 잠기고, 비행 중에 세 번 누르면 세 번 다 나간다.

| 하지 않는다 | 한다 |
|---|---|
| `useState` 로 폼이 pending 을 직접 든다 | `components/submit-button.tsx` 를 쓴다 |
| 액션 안에서 `setPending(true/false)` | 아무것도 안 한다 — React 가 준다 |

`SubmitButton` 이 `useFormStatus()` 로 그 값을 React 에게서 직접 받는다. **폼의 자식이어야 읽힌다** — 같은 컴포넌트에서 부르면 언제나 `false` 다.

**`onSubmit={fn}` 폼은 반대다.** `useFormStatus` 는 `action` 이 건 제출만 알아서 거기에 `SubmitButton` 을 끼우면 한 번도 안 잠긴다. 그 꼴은 `useState` 로 드는 것이 맞다.
지금 이 저장소의 폼은 전부 `action=` 이고 `onSubmit` 폼은 0개다 — 생기면 이 표가 갈린다.

**React 는 액션이 끝나면 폼을 비운다.** 다시 낼 때 사용자는 같은 값을 다시 친다 — 멱등키를 「같은 입력이면 같은 키」로 쥐는 쪽(`CheckoutForm`)이 그것을 전제한다(`42`).

**`frontend/src/test/form-pending.test.ts` 가 잰다**(`39-2`) — `action=` 폼 파일의 pending `useState`, `onSubmit` 폼 파일의 `SubmitButton`. 린트는 「한 파일에 둘이 같이」를 못 적어서 시험이다.

## 캐시 — 실수하면 남의 것이 보인다

**이 절은 번들된 Next 문서를 읽고 쓴 것이다**(Next 16.3.5, `stack.md`). 아래 셋이 근거다.

| 사실 | 어디 |
|---|---|
| `cookies()` 는 Request-time API 라 그 라우트를 **dynamic 으로 만든다** | `01-app/03-api-reference/04-functions/cookies.md` |
| `cacheComponents` 를 안 켜면 **`fetch` 는 기본이 캐시 안 됨** | `01-app/02-guides/caching-without-cache-components.md` |
| **`dynamic = 'force-static'` 은 `cookies()` 가 빈 값을 돌려주게 만든다** | 같은 문서 |

셋째가 위험하다. **세션이 사라지는데 오류가 안 난다** — 그냥 비로그인으로 그려진다.

| 규칙 | 왜 |
|---|---|
| 인증 데이터를 그리는 라우트에 `dynamic = 'force-static'` 을 안 건다 | 세션이 조용히 빈 값이 된다 |
| 같은 라우트에 `fetchCache = '*-cache'` 를 안 건다 | 사람마다 다른 응답이 공유된다 |
| **인증 요청에는 `cache: 'no-store'` 를 명시한다** | 같은 문서 안에서 기본값 서술이 갈린다 — 어느 쪽이 맞든 명시하면 안전하다 |
| 캐시를 켜는 것은 **공개 데이터에만** | 공연 목록·좌석 현황은 누구에게나 같다. 지금은 그것도 `no-store` 다 — 켜는 날 그 라우트가 정한다 |

`cacheComponents` 플래그를 켜기로 하면 **이 절을 통째로 다시 본다.** 켜는 순간 기본 동작이 바뀐다.

## 상태는 주소에 둔다

목록의 쪽 번호·필터·정렬은 **URL 검색 문자열**에 둔다(`/events?page=`). 컴포넌트 상태로 들지 않는다.
**주소가 곧 상태**라야 뒤로 가기·새로고침·링크 공유가 저절로 되고, 서버 컴포넌트가 그 값을 읽어서 그린다.

**주소는 사람이 고칠 수 있다.** 숫자가 아닌 `page` 는 첫 쪽으로 본다 — 그대로 서버에 넘기면 400 을 받고 화면이 선다(`40b`).

**클라이언트 상태는 화면 안에서만 사는 것에 쓴다.** 고른 좌석, 열린 대화상자, 입력 중인 값.

## 오류를 어느 층이 잡나

**어디에 보여주나는 `D17` 이 정했다.** 여기서는 잡는 층만 정한다.

| 오류 | 어디서 잡나 |
|---|---|
| 입력값이 규칙에 안 맞음 | 그 폼의 클라이언트 컴포넌트. `slug` 를 보고 문구를 고른다 |
| 401 | **입구.** 로그인 화면으로 보낸다 — 서버 입구든 브라우저 입구든 같다 |
| 403·404 | 그 화면의 서버 컴포넌트. `event-not-found`·`performance-not-found`·`reservation-not-found` 는 `notFound()` 로 보낸다 — **그 슬러그만이다.** 5xx 를 404 로 바꾸면 고장이 「없는 주소」로 보인다 |
| 5xx·못 잡은 예외 | `app/error.tsx` |

**`type` 으로 갈린다. 상태 코드나 `detail` 문자열로 안 갈린다**(`D5`). **화면은 `type` 전체가 아니라 `ApiError.slug` 를 본다** — 접두어는 `api.ts` 만 안다.

**결과와 오류를 가른다.** 결제 거절·무응답은 예외가 아니라 응답 본문의 `status` 다(`D5`) — **잡는 층이 없다.** 그리는 자리는 `D17` 「결과는 오류가 아니다」다.

### 오류 경계는 `app/error.tsx` 다

이 파일이 없으면 Next 기본 오류 화면이 뜨는데 우리 셸도 없고 문구도 존댓말이 아니다(`40b` 가 세웠다).
**원인을 화면에 안 적는다** — `error.message` 에는 서버 문구나 스택이 들어올 수 있다(`D9`). 되짚을 값은 `digest` 고 그 값이 서버 로그와 짝이 맞는다.
`src/app`·`src/components` 의 `.message` 읽기는 eslint `no-restricted-syntax` 가 막는다(`G7c`) — 변수 이름으로 안 가린다.
`global-error.tsx` 는 안 만든다 — 루트 레이아웃이 터졌을 때만 쓰이는데 우리 레이아웃은 데이터를 안 부른다.

## 이 문서를 고칠 때

화면을 만들다가 여기 없는 상황이 나오면 **그 상황을 여기 먼저 추가한다.** 청크마다 다르게 정하면 화면 수만큼 규칙이 생긴다.
**Next 판을 올릴 때 「캐시」 절을 먼저 확인한다.** 그 절만 판에 묶여 있다.
