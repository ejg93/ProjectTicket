# 대기열 설계

오픈 순간에 몰리는 사람을 줄 세워 **좌석 선점 요청이 DB 에 닿는 속도의 상한**을 만든다. 그것이 대기열의 존재 이유고,
다른 것(공정성·순번 표시)은 그 위에 얹는다.

**항상 켠다**(ADR 0003). 활성 정원이 미달이면 진입 즉시 토큰이 나가서 줄이 없는 것처럼 보이고, 코드 경로는 하나다.

## 무엇을 지키나 — 등식

```
DB 가 받는 선점 요청률  ≤  입장 속도 R
R = 100명 / 5초 = 20명/초                                  (ADR 0003 시작값)

DB 가 감당하는 상한   =  커넥션 풀 / 선점 트랜잭션 지연
                     =  10 / 20ms  =  500 트랜잭션/초       (측정 전 추정, 31 이 잰다)
```

R 이 상한의 4% 다. **대기열이 막는 것은 처리량이 아니라 순간 폭발**이다 — 오픈 초에 1만 명이 동시에 선점을 누르면
Tomcat 스레드 200 이 차고 그 뒤 9,800 명이 커넥션 대기에서 죽는다. 줄이 있으면 초당 20명씩 들어와 대기 없이 처리된다.
남는 여유는 31 이 재서 R 을 올린다.

## 자료구조 — 전부 Redis, 회차 단위

| 키 | 타입 | 무엇 | 만료 |
|---|---|---|---|
| `queue:{performanceId}` | ZSET | 대기 줄. **member = accountId**, score = 진입 시각(ms) | 회차 종료 때 삭제 |
| `queue:{performanceId}:seen` | HASH | accountId → 마지막 하트비트(ms) | 위와 같이 |
| `queue:{performanceId}:active` | ZSET | 활성 토큰. member = token, score = 만료 시각(ms) | 위와 같이 |
| `admit:{token}` | STRING(JSON) | `{account_id, performance_id, issued_at}` | 10분(ADR 0003) |
| `admit:by-account:{performanceId}:{accountId}` | STRING | 그 계정의 현재 토큰 | 10분 |

**member 가 계정이라 한 사람이 줄에 두 번 못 선다.** 봇이 진입을 만 번 눌러도 `ZADD NX` 가 첫 자리를 지킨다.
로그인 없이는 줄에 못 선다 — 계정이 없으면 member 가 없다.

**좌석 상태는 여기 없다.** 좌석은 `performance_seat` 가 진실이고(`D2`), Redis 가 죽어도 팔린 좌석은 그대로다.

## 흐름

```
관객 ─POST /api/queue/{perf}─> ZADD NX  ──> {rank, eta}      ① 진입·재진입 (순번 유지)
관객 ─GET  /api/queue/{perf}─> ZRANK    ──> {rank, eta, token?}   ② 폴링 2초 (43)
                                 + HSET seen                    ③ 하트비트는 폴링이 겸한다
스케줄러 ─5초마다─> Lua: 만료 정리 → 빈자리 = C - 활성 → 앞에서 min(빈자리, 100) 을 ZPOPMIN → 토큰 발급
관객 ─POST /api/reservations + X-Admission-Token─> 관문 → 선점(13) → 성공하면 토큰 삭제(정원 반납)
```

### 진입과 재진입

`ZADD NX queue:{perf} <now> <accountId>` — 이미 있으면 score 를 안 바꾼다. **새로고침해도 순번이 그대로**인 이유가 이 한 글자다.
응답은 `{rank, eta_seconds}`. 이미 입장했으면(`admit:by-account` 가 있으면) 토큰을 다시 준다 — 브라우저를 껐다 켜도 자리를 안 잃는다.

### 순번과 예상 대기

`rank = ZRANK + 1`, `eta = rank / R`. R 이 설정값이라 예상은 근사다. 화면은 「약 N분」으로 보인다(`D17`).

### 입장 — 스케줄러가 5초마다

Lua 스크립트 하나로 원자적으로 한다:

```
1. ZREMRANGEBYSCORE active -inf now          -- 만료된 토큰을 정원에서 뺀다
2. free = C - ZCARD active                   -- 빈자리
3. n = min(free, 100)                        -- 이번에 들일 수
4. members = ZPOPMIN queue n                 -- 줄 앞에서 뺀다
5. 각 member 에 토큰 발급, active 에 ZADD(만료 시각), admit:{token}·by-account 저장
```

**Lua 라서 인스턴스 셋이 같이 돌아도 같은 사람을 두 번 안 들인다** — `ZPOPMIN` 이 원자다. 두 대가 돌면 5초에 200명이 들어가는 것이지
한 명이 두 번 들어가는 것이 아니다. 그래도 33 은 Redis 락으로 하나만 돌린다 — 속도가 설정값과 같아야 31 의 측정이 뜻을 갖는다.

**정원 C 는 2,000 이 시작값이다.** R × TTL 이 12,000 이라 C 가 먼저 찬다 — 즉 평소에는 정원이 아니라 속도가 줄을 정한다.
C 가 막는 것은 「입장했는데 안 사는 사람」이 쌓여서 활성 집합이 무한히 커지는 것이다. 31 이 조정한다.

### 토큰

| 항목 | 값 | 왜 |
|---|---|---|
| 형식 | 무작위 32바이트, base64url | 서명 토큰(JWT)을 안 쓴다 — **반납할 수 있어야** 해서다. 서명 토큰은 만료 전에 못 죽인다 |
| 묶음 | 계정 + 회차 | 관문이 셋을 대조한다. 토큰 하나로 남의 계정·다른 회차를 못 산다 |
| 전달 | `X-Admission-Token` 헤더 | 쿠키에 두면 회차 여럿에 동시에 줄 선 사람의 것이 섞인다 |
| 수명 | 10분 = 선점 5분 + 결제 여유 | TTL 이 선점보다 짧으면 좌석을 잡은 채로 토큰이 죽는다(ADR 0003) |
| 반납 | 선점 성공 시 즉시 삭제 | 좌석을 잡았으면 문지기는 볼일이 끝났다. 결제는 관문 밖이다(ADR 0004) |

**선점이 실패하면 토큰은 남는다.** 남이 먼저 잡은 좌석을 골랐을 뿐이라 다른 좌석을 고를 수 있어야 한다. TTL 안에서 몇 번이고 시도한다.

### 관문 — 선점만 막는다

`QueueGateFilter`(23)는 **`POST /api/reservations` 에만** 걸린다(ADR 0004).

| 검사 | 실패 시 |
|---|---|
| 헤더가 있다 | 429 `admission-required`, 본문에 `rank`·`eta` |
| `admit:{token}` 이 있다(만료 안 됨) | 429 `admission-required` |
| 토큰의 `account_id` = 세션의 계정 | 403 `forbidden` |
| 토큰의 `performance_id` = 요청의 회차 | 403 `forbidden` |

429 인 이유: 「지금은 안 되지만 나중엔 된다」의 뜻이 429 다. 403 은 「너는 안 된다」고, 줄을 안 선 사람은 후자가 아니다.
결제·취소·조회는 관문을 안 지난다 — 결제는 이미 좌석을 쥔 사람이고, 조회는 읽기 모델(`D20`)이 받는다.

### 이탈과 정리

| 무엇 | 언제 | 어떻게 |
|---|---|---|
| 하트비트 | 폴링(2초)이 겸한다. 따로 안 보낸다 | `HSET seen accountId now` |
| 줄에서 제거 | 90초 하트비트 없음(ADR 0003) | 스케줄러가 `seen` 을 훑어 `ZREM`. 뒷사람이 당겨진다 |
| 명시적 이탈 | `DELETE /api/queue/{perf}` | `ZREM` + 토큰 있으면 삭제 |
| 토큰 만료 | 10분 | Redis TTL 이 지운다. `active` ZSET 은 다음 입장 때 1 단계가 정리 |
| 회차 종료 | `closed`·`cancelled` 전이(16a·17a) | 키 다섯을 통째로 삭제. 줄에 남은 사람은 폴링에서 410 `queue-closed` |

## 장애

| 상황 | 동작 | 왜 |
|---|---|---|
| Redis 가 안 뜬다 | 관문이 **닫힌다** — 선점이 503 `queue-unavailable` | 열어 두면 대기열이 지키려던 폭발이 그대로 DB 로 간다. 닫히면 아무도 못 사지만 아무것도 안 망가진다 |
| Redis 가 비었다(재시작) | 줄이 사라진다. 사람들이 다시 진입하면 새 순번 | 날아가도 사고가 아닌 것만 Redis 에 둔다(`D2`). 잡힌 좌석은 DB 에 그대로다 |
| 스케줄러가 멈춘다 | 줄이 안 준다. 폴링 응답의 `eta` 가 안 줄어든다 | 30 의 지표(`queue.admitted`)가 0 으로 떨어져 보인다 |

## 지표 (30 이 든다)

`queue.length{performance}` · `queue.active{performance}` · `queue.admitted` (카운터) · `queue.wait_seconds` (히스토그램, 진입→입장) · `queue.gate_rejected{reason}`

## 지금 안 하는 것

| 항목 | 왜 |
|---|---|
| 우선순위·선예매 | 줄 하나로 충분하다. 두 줄이면 합치는 규칙이 필요하다 |
| 사전 등록(오픈 전 줄서기) | 진입 시각 = 오픈 시각이면 결과가 같다 |
| 서명 토큰 | 반납이 안 된다. 위 「토큰」 |
| SSE | ADR 0003. 폴링 2초가 하트비트를 겸해서 오히려 단순하다 |

## 이 문서를 고칠 때

**속도·정원·TTL 을 바꾸면 위 등식을 다시 쓴다.** 셋은 서로 묶여 있다 — TTL 을 늘리면 정원이 더 빨리 차고, 속도를 올리면 DB 상한에 가까워진다.
31 의 측정값이 이 문서의 수치를 고치는 유일한 근거다.
