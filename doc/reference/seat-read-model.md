# 좌석 읽기 모델

좌석 현황 조회(10)의 계약과, 그것이 1만 명의 2초 폴링을 버티는 방법. 좌석도(41)와 대기열 화면(43)이 이 계약을 읽는다.
왜 이 모양인지는 ADR 0005.

**쓰기와 읽기를 가른다.** 쓰기(선점·확정·해제)는 `performance_seat` 에 트랜잭션으로 간다(`D4`). 읽기는 그 결과를
**버전이 붙은 스냅샷**으로 본다. Redis 는 스냅샷과 버전만 들고 좌석을 정하지 않는다(`D2`).

## 계약

### 전체 — `GET /api/performances/{id}/seats`

```json
{
  "version": 1842,
  "grades": [{ "code": "VIP", "name": "VIP", "price": 154000 }],
  "sections": [
    { "code": "F1-A", "name": "1층 A구역", "grade": "VIP",
      "rows": [
        { "label": "A", "seats": [ { "id": 9001, "n": 1, "s": "A" }, { "id": 9002, "n": 2, "s": "H" } ] }
      ] }
  ]
}
```

| 필드 | 뜻 |
|---|---|
| `version` | 이 스냅샷의 판. 선점·해제·확정마다 1 씩 는다 |
| `s` | 좌석 상태 한 글자 — `A` 빈자리, `H` 선점됨, `R` 팔림 |
| `id` | `performance_seat_id`. 선점 요청이 이 값을 보낸다 |
| `n` | 좌석 번호 |

응답 헤더: `ETag: "1842"`, `Cache-Control: no-cache`(써도 되지만 **매번 재검증**하라는 뜻이다).

**한 글자 상태와 짧은 키인 이유는 크기다.** 2천 석 × 폴링이라 필드 이름이 곧 대역폭이다. 2천 석 응답이 약 60KB 다.

### 재검증 — `If-None-Match`

```
GET /api/performances/7/seats
If-None-Match: "1842"

→ 304 Not Modified        (버전이 그대로면. 본문 없음, Redis GET 한 번)
→ 200 + 새 스냅샷          (바뀌었으면)
```

폴링의 대부분이 304 다. 오픈 초에도 초당 바뀌는 좌석은 수십 석이고 폴링은 초당 수천이라, 본문을 만드는 것은 그중 버전이 바뀐 순간뿐이다.

### 델타 — `GET /api/performances/{id}/seats/changes?since=1842`

```json
{ "version": 1851, "changes": [ { "id": 9002, "s": "R" }, { "id": 9015, "s": "H" } ] }
```

전체를 다시 받지 않고 바뀐 좌석만 받는다. `since` 가 너무 오래됐으면(변경 로그 밖) **410 Gone** — 클라이언트는 전체를 다시 받는다.
좌석도(41)는 첫 로드에 전체, 그 뒤 폴링에 델타를 쓴다.

## 버전과 스냅샷 — Redis

**10 은 DB 대체값으로 시작했다** — `SeatQuery.version` 이 `performance_seat.updated_at` 의 최댓값(마이크로초)을 버전으로 쓴다. Redis 절반(아래)과 델타는 `10a` 다.

| 키 | 타입 | 무엇 |
|---|---|---|
| `seat:ver:{performanceId}` | STRING(정수) | 현재 버전. 쓰기 트랜잭션이 커밋된 **뒤** `INCR` |
| `seat:log:{performanceId}` | STREAM | 변경 로그. 항목 = `{version, id, s}`. `MAXLEN ~ 10000` |
| `seat:snap:{performanceId}:{version}` | STRING(JSON) | 그 버전의 전체 스냅샷. TTL 10초 |

### 쓰기 쪽이 하는 일

선점·확정·해제 트랜잭션이 커밋되면 `afterCommit` 에서:

```
1. INCR seat:ver:{perf}                     → v
2. XADD seat:log:{perf} * version v id … s …   (바뀐 좌석마다)
```

**커밋 뒤라야 한다.** 커밋 전에 올리면 롤백된 선점이 화면에 `H` 로 보인다. `afterCommit` 이 실패하면(Redis 다운) 버전이 안 오르고,
그러면 폴링이 304 를 받아 **화면이 늦어질 뿐 틀리지는 않는다** — 다음 쓰기가 성공하면 따라잡는다. 스냅샷은 항상 DB 에서 만들기 때문이다.

### 읽기 쪽이 하는 일

```
전체 요청:
  v = GET seat:ver         (없으면 0 — Redis 가 비었으면 DB 에서 max(updated_at) 로 대신한다)
  If-None-Match == v      → 304
  snap = GET seat:snap:v  → 있으면 그대로
                          → 없으면 DB 에서 만들고 SET … EX 10, 돌려준다

델타 요청:
  v = GET seat:ver
  since >= v              → {version: v, changes: []}
  XRANGE seat:log (since, v]  → 없으면(잘렸으면) 410
                             → 있으면 좌석별 마지막 상태만 모아 돌려준다
```

**스냅샷을 DB 에서 만드는 것은 버전이 바뀐 직후 첫 요청뿐이다.** 같은 버전의 나머지 요청은 Redis 가 답한다.
2천 석을 DB 에서 읽는 것은 초당 수천이 아니라 「초당 버전이 바뀌는 횟수」다.

**동시에 여럿이 스냅샷을 만들 수 있다.** 같은 버전이라 결과가 같고, 마지막 `SET` 이 이긴다. 락을 안 건다 — 락이 더 비싸다.

## 정합성

| 물음 | 답 |
|---|---|
| Redis 와 DB 가 어긋나면 | DB 가 이긴다. 스냅샷은 DB 에서 만들고 버전은 순서만 준다 |
| 화면이 `A` 인데 선점이 0행이면 | 정상이다. 화면은 폴링 주기만큼 늦다. 선점 응답이 `seat-taken` 이면 화면이 그 좌석을 `H` 로 바꾼다(41) |
| 버전이 뒤로 가나 | 안 간다. `INCR` 뿐이다. Redis 가 비어 0 이 되면 클라이언트의 `since` 가 크므로 410 → 전체 재로드 |
| 스냅샷이 오래된 버전을 담나 | 키에 버전이 들어 있어 못 섞인다 |

## 크기와 비용 (추정 — 31 이 잰다)

| 항목 | 값 |
|---|---|
| 전체 스냅샷 | 2천 석 ≈ 60KB (gzip 뒤 ≈ 8KB) |
| 304 응답 | Redis GET 1 회, 본문 없음 |
| 델타 | XRANGE 1 회, 바뀐 좌석 수만큼 |
| 폴링 1만 명 × 2초 | 초당 5천 요청, 그중 본문이 있는 것은 버전 변경 횟수 × 폴링 위상 |

## 지금 안 하는 것

| 항목 | 왜 |
|---|---|
| 구역별 부분 응답 | 2천 석이면 전체가 감당된다. 만 석 홀이 생기면 그때 |
| SSE 푸시 | ADR 0003. 델타 폴링이 같은 효과를 sticky 없이 낸다 |
| DB 에 버전 컬럼 | 회차 행 하나가 선점마다 갱신되는 뜨거운 행이 된다(ADR 0005) |

## 이 문서를 고칠 때

**응답 필드를 바꾸면 41·43 이 같이 간다.** 계약이라 `SeatQueryTest`(10)의 스냅샷이 막고, 바꿀 때는 `version` 필드는 남긴다 —
그것이 없으면 재검증이 안 된다.
