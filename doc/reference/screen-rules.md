# 화면·문구 규약

> **ProjectShop 에서 이식한 문서다.** 예시·청크 번호(`2g`·`Q36` 등)·쇼핑 도메인(주문·셀러·정산)은 ProjectShop 것이다.
> 티켓 도메인과 Kotlin 에 맞추는 것은 `PLAN.md` 이식 청크 `P` 줄이 한다. 그 청크가 닫히면 이 머리말을 지운다.
> 그때까지는 **원칙은 믿고 예시는 안 믿는다.**

화면이 **권한·오류·빈 상태를 어떻게 그리나**. 서버가 무엇을 내려주는지는 `api-guidelines.md`(D5)가 정했고,
여기서는 그것을 받은 화면이 무엇을 하는지를 정한다.

## 기준

| 대상 | 기준 자료 |
|---|---|
| 접근성 | **KWCAG 2.2**(국가표준 KS X OT0003, WCAG 2.1 기반) |

**접근성을 범위 밖으로 뒀던 것을 뒤집었다.** 처음에는 그렇게 적었는데
**장애인차별금지법 제20조·제21조가 민간 사업자에게도 걸린다**(단계적 적용이 2015년에 끝났다).
범위 밖으로 둘 수 있는 것이 아니라 `D2` 의 법 요건과 같은 층이다.

되돌리는 비용도 다르다. 나중에 붙이면 **고치는 것이 아니라 다시 짜는 것**이 된다(`D23` 「접근성」).

**문구 문체가 `CLAUDE.md` 와 갈린다.** 그쪽은 개발자가 읽는 글이라 평서형이고,
화면은 사용자가 읽는 것이라 존댓말이다. 아래 「문구」 절을 본다.

시각 디자인은 청크 `13-0` 이 깐 `design-taste-frontend` 스킬이 맡는다.
이 문서는 **무엇을 보여주고 무엇을 감추나**만 정한다 — 그 판단은 스킬이 대신해 줄 수 없다.

### 그 스킬을 어디까지 쓰나

**기본은 쓰는 것이다.** 그 스킬이 막는 것은 생성형이 기본으로 뱉는 모양이고,
그건 페이지 종류를 안 가린다 — 보라 그라데이션·3등분 동일 카드·`#000000`·가짜 데이터는
쇼핑몰 화면에도 똑같이 나온다.

스킬이 자기 범위를 좁게 적어 뒀지만(`§13`), 같은 절 마지막 문장이
**"그런 화면이면 그렇다고 밝히고 해당되는 부분만 적용하라"** 다. 배제가 아니라 부분 적용이다.

| 화면 | 스킬을 어떻게 |
|---|---|
| 홈·상품 목록·상세 | 그대로 쓴다. 스킬이 겨냥한 것과 같은 종류다 |
| 주문 흐름·장바구니 | 다단계 폼이라 `§13` 밖이다. **`§9`(AI Tells)·`§4`(편향 교정)·`§6`(가드레일)만 적용**하고 흐름 설계는 이 문서가 정한다 |
| 셀러·관리 화면 | 목록과 표가 중심이라 `§13` 밖이다. 위와 같다 |

### 다이얼 값

**랜딩 기본값 `8/6/4` 를 안 쓴다.** 커머스는 `§1.A` 의 `trust-first / regulated` 줄이라
범위가 `VARIANCE 3-4 / MOTION 2-3 / DENSITY 4-5` 고, 그 안에서 아래로 확정했다(사용자 선택).

| 다이얼 | 값 | 무엇이 구속되나 |
|---|---|---|
| `DESIGN_VARIANCE` | **4** | 목록·주문 흐름은 대칭 그리드. 홈·상세만 오프셋·비대칭 비율. `md:` 미만은 단일 컬럼 강제 |
| `MOTION_INTENSITY` | **4** | `transform`·`opacity` 전환만. 자동 재생·스크롤 연출 없음 |
| `VISUAL_DENSITY` | **구매자 5 / 셀러 7** | 구매자는 `py-16~24`. 셀러는 카드 대신 1px 선, 숫자에 `font-mono` |

**`VARIANCE` 를 더 올리지 않는다.** 목록의 균등 그리드는 미학이 아니라 기능이다 —
가격·재고를 비교하려면 칸이 같아야 눈이 훑는다. 그리고 **개성은 이 다이얼에서 안 나온다.**
그건 `§9` 금지 목록이 하고, 다이얼을 올리면 값은 안 오른 채 반응형 규칙만 화면마다 늘어난다.

**`MOTION` 은 프리셋을 한 칸 넘겼다.** 2 는 전환이 없어서 **클릭이 먹혔는지가 안 보인다.**
4 의 제약이 안전을 만든다 — 레이아웃을 안 건드리는 두 속성만 쓰므로 `CLS` 가 안 흔들린다(`§6.D`).
`prefers-reduced-motion` 에서 전부 꺼지는 것은 그대로다.

**`DENSITY` 만 화면군마다 다르다.** 두 화면군의 목적이 반대다 — 구매자 화면은 상품 하나에
집중시키고, 셀러 화면은 주문 여러 건을 한 화면에서 처리한다. 같은 간격을 주면 한쪽이 틀린다.
**대가는 간격 토큰이 두 벌인 것**이라 경계를 코드에서 가른다(라우트 그룹, 청크 13).

### 다크모드

**양모드를 만든다**(`§8`). **안 만드는 것은 토글 버튼뿐이다** — `prefers-color-scheme` 만 따른다.

토글은 결정을 셋 부른다: 고른 값의 저장 위치(쿠키·localStorage·계정), 계정에 넣으면
설정 API 와 `D13` 수명에 줄이 는 것, 서버 렌더링이라 **첫 그림이 반대 모드로 번쩍이는 것**을
따로 막아야 하는 것. 지금 토큰을 일관되게 깔아 두면 **토글은 나중에 얹기만 하면 된다.**
반대로 색을 컴포넌트에 박으면 그때가 전면 수정이다.

**순수 `#000000`·`#ffffff` 를 안 쓴다**(`§8.B`). 깊이가 사라진다.

**스택 기본값(`§3`)은 우리 결정이 이긴다.** 스킬은 Tailwind v4·Motion·Phosphor 를 들고 있고
프레임워크는 Next.js + RSC 라 우리와 같다. 다른 것을 고르면 **스킬이 아니라 청크 13 이 맞다** —
출처 순위로 스킬은 업계 관례(4순위)고 프로젝트 규약이 3순위다(`D23` 축 1).

**`§9.G` em-dash 금지는 화면 문구에만 걸린다.** 개발자가 읽는 글(`CLAUDE.md`·문서·커밋)은
`—` 를 쓰고 그건 안 바꾼다. 두 문체가 갈리는 자리가 여기 하나 더 있다.

**`§9.D` 의 이름·수치 창작은 마케팅 페이지용이다.** 우리 화면은 DB 값을 그리므로 해당 없다.
**시드·데모 데이터에는 적용하지 않는다** — 그쪽은 재현이 목적이라 그럴듯함보다 고정이 중요하다.

**대비 점검은 스킬이 아니라 법에서 온 것이다.** 스킬을 안 쓰기로 해도 남는다.

## 화면 지도

**어떤 화면이 있고 어디서 어디로 가나.** 화면을 만들기 전에 여기 먼저 적는다.

지도가 없으면 링크를 걸 대상이 있는지 없는지를 그때그때 판단하게 되고,
`13-2` 에서 실제로 그랬다 — 「회원가입」 링크를 걸었다가 갈 곳이 없어서 뺐다.

| 경로 | 무엇을 | 누가 보나 | 어느 청크 |
|---|---|---|---|
| `/` | 홈. 지금은 들어온 사람을 상품 목록으로 보낸다 | 누구나 | `13-2` **완료** |
| `/products` | 상품 목록 | 누구나 | `14` **완료** |
| `/products/{상품번호}` | 상품 상세 | 누구나 | `14b` **완료** |
| `/cart` | 장바구니 | 누구나. **비로그인도 담는다**(청크 9) | `15-1` |
| `/checkout` | 주문서 | 로그인 | `15-2` |
| `/orders` | 내 주문 | 로그인 | `15-3` |
| `/orders/{주문번호}` | 주문 상세. 취소·확정·반품이 여기 있다 | 로그인 | `15-3` |
| `/login` | 로그인 | 비로그인 | `13-2` **완료** |
| `/signup` | 회원가입. 약관 동의가 같이 있다 | 비로그인 | `13d-2` **완료** |
| `/me` | 내 정보. 열람·이름 변경·비밀번호 변경·동의 철회 | 로그인 | `13e` **완료** |
| `/me/withdraw` | 회원 탈퇴. 무엇이 사라지고 무엇이 5년 남는지를 적고 비밀번호를 다시 받는다 | 로그인 | `13e` **완료** |
| `/terms`·`/privacy` | 이용약관·개인정보처리방침 | 누구나 | `13a-2` **완료** |
| `/withdrawal-guide` | 청약철회 안내. 기간·비용 부담·환급 기한 | 누구나 | `13a-2` **완료** |
| `/seller/products` | 파는 물건 관리 | 셀러 | `13f` |
| `/seller/orders` | 받은 주문 처리. 발송·배송완료 | 셀러 | `13g` |
| `/admin/roles` | 역할·권한 편집 | 관리자 | `16` |
| (지도에 없는 주소) | 없는 쪽. 상품 목록으로 보낸다 | 누구나 | `14b` **완료** |

**셀러·관리자 경로를 접두어로 가른다.** 화면군마다 밀도가 다르고(위 「다이얼 값」),
경로가 갈려 있어야 그 차이를 한 군데서 건다.

### 아직 없는 화면은 자리표시로 둔다

지도에 있는데 아직 안 만든 화면은 **「준비 중」 페이지를 놓는다.** 링크는 그대로 건다.

| 방법 | 무엇이 문제인가 |
|---|---|
| 링크를 안 건다 | 화면이 생길 때마다 링크를 넣었다 뺐다 한다. 어디에 걸어야 하는지도 그때 다시 찾는다 |
| 링크를 걸고 404 | 사용자가 고장으로 본다 |
| **링크를 걸고 「준비 중」** | 갈 곳이 있고, 없는 것이 아니라 아직인 것이 전해진다 |

자리표시는 **그 화면을 만드는 청크가 지운다.** 남아 있으면 그 청크가 안 끝난 것이다.

### 화면마다 다시 정하지 않는 것

화면 축 전체에 한 번씩 걸리는 것들이다. **화면마다 정하면 화면마다 달라진다.**

| 것 | 정한 것 | 왜 |
|---|---|---|
| 권한 | **화면을 그리기 전에 서버에서 `/api/me/permissions` 를 부른다**(`8a`) | 항상 최신이다. 로그인 때 한 번 받아 들고 다니면 **회수된 권한의 버튼이 남고**, 눌러야 403 이 난다. 서버가 어차피 막지만 표시가 거짓말을 한다 |
| 상품 사진 | **`picsum.photos/seed/{상품번호}`** 자리표시 | 스키마에 이미지 컬럼이 없다. 씨앗이 상품번호라 같은 상품은 언제나 같은 사진이다. **진짜 업로드는 청크 26** 이고 그때 이 자리만 바뀐다 |
| 목록 넘김 | **번호 페이징** | 서버가 `page`·`size` 로 내려준다(`D5`). **주소가 곧 상태**라 뒤로 가기·새로고침·링크 공유가 저절로 된다. 「더 보기」는 상세에 들어갔다 돌아오면 첫 페이지로 떨어진다 |
| 토스트 | **직접 만든다** | 쓰는 종류가 몇 개 안 되고, 위 「동적으로 바뀌는 것」이 요구하는 `role="status"` 와 자동으로 안 사라지는 것을 우리가 통제한다 |

**넷 다 되돌리는 값이 싸다** — 컴포넌트 교체지 서버 계약이나 스키마가 아니다.
반대로 접근성은 나중에 바꾸면 마크업을 다시 짜므로 앞당겨 건다(`D23` 「접근성」).

### 셸

모든 화면이 같은 머리와 발을 쓴다. 화면마다 다시 그리지 않는다.

```
┌─────────────────────────────────────┐
│ ProjectShop   상품  장바구니   로그인 │  머리
├─────────────────────────────────────┤
│                                     │
│           화면마다 바뀌는 곳          │
│                                     │
├─────────────────────────────────────┤
│ 이용약관 · 개인정보처리방침           │  발
└─────────────────────────────────────┘
```

**`<main>` 은 셸이 한 번만 그린다.** 화면은 그 안을 채우기만 하고 자기 `<main>` 을 안 만든다.

표지(landmark)가 하나여야 **건너뛰기 링크가 가리킬 대상이 하나**다. 화면마다 `<main>` 을 그리고
셸이 그것을 `div` 로 감싸면 링크는 `div` 에 닿고 표지는 안쪽에 남아 **둘이 어긋난다**(`13h`).

- **머리**는 어디서나 같은 자리에 있다. 지금 무엇을 보고 있든 상품·장바구니·계정으로 갈 수 있다
- **발**에 약관과 처리방침을 둔다. 전자상거래법이 요구하는 고지라 **모든 화면에서 닿아야 한다**
- 로그인 여부에 따라 머리의 항목이 갈린다. **권한으로 가리는 것은 `13b`** 가 붙인다

## 접근성

**마크업을 쓰는 모든 청크가 지킨다.** KWCAG 2.2 전부를 여기 옮기지 않는다 —
우리 화면에서 실제로 걸리는 것만 적고, 나머지는 기준 자료를 본다.

### 반드시 지키는 것

| 항목 | 규칙 | 우리 화면의 어디 |
|---|---|---|
| 대체 텍스트 | 뜻이 있는 이미지에 `alt`. 장식은 `alt=""` | 상품 이미지(14) |
| 키보드 | 마우스로 되는 것은 키보드로도 된다. 초점이 보인다 | 전부 |
| 초점 순서 | 화면에 보이는 순서와 같다 | 전부 |
| 대비비 | 본문 4.5:1, 큰 글자 3:1 | `13-0` 스킬이 고르는 팔레트가 이걸 통과해야 한다 |
| 레이블 | 모든 입력에 `label`. `placeholder` 로 대신하지 않는다 | 로그인·가입·주소 입력 |
| 오류 안내 | 어느 입력이 왜 틀렸는지를 글로 알린다. 색만으로 알리지 않는다 | 아래 「오류」 절과 같이 본다 |
| 제목 구조 | `h1`~`h6` 을 건너뛰지 않는다 | 전부 |
| 언어 | `<html lang="ko">` | 골격(`13-1`) |
| 반복 영역 건너뛰기 | 머리의 링크를 지나 본문으로 바로 가는 링크를 맨 앞에 둔다 | 셸(`13c`). **키보드만 쓰는 사람은 화면마다 같은 머리를 다시 통과한다** |

### 색만으로 알리지 않는다

이 규칙이 우리 설계와 정면으로 만나는 자리가 있다.

**필수 동의**와 **권한 없어 숨긴 것**은 색으로 구분하고 싶어지는 것들이다.
색은 보조고 **글과 구조가 먼저**다 — 필수는 "필수" 라고 쓰고, 숨긴 것은 아예 안 그린다.

숨기는 규칙(아래 절)이 접근성과 어긋나지 않는 이유가 이것이다.
**비활성으로 두면 스크린 리더가 읽고 만질 수 없다고 말한다.** 안 그리면 없는 것이다.

### 약관의 중요한 내용은 강조한다

접근성만의 얘기가 아니다. **약관규제법 제3조제1항이 요구한다** —
약관은 한글로 쓰고 **중요한 내용을 부호·색채·굵고 큰 문자 등으로 명확하게 표시**해야 한다.

`consent_item.body` 가 마크다운인 이유가 이것이다. 강조를 원문에 넣어 두면 화면이 살려서 그린다.
**본문을 통짜 텍스트로 뿌리면 이 의무를 못 지킨다.**

색만으로 강조하지 않는다는 위 규칙이 여기서도 그대로 걸린다 — 굵게와 색을 같이 쓴다.
법이 "부호, 색채, 굵고 큰 문자 **등**" 이라고 열거한 것도 하나로는 부족하다는 뜻으로 읽는다.

### 동적으로 바뀌는 것

토스트와 인라인 오류는 **화면이 바뀐 사실이 소리로도 전해져야 한다.**
`role="alert"` 또는 `aria-live` 를 붙인다. 안 붙이면 스크린 리더 사용자에게는 아무 일도 안 일어난다.

### 안 하는 것

| 항목 | 왜 |
|---|---|
| 자동 검사 도구 도입 | 프론트가 아직 없다. 청크 13 에서 `eslint-plugin-jsx-a11y` 를 같이 깐다 |
| 인증 마크 획득 | 실제 서비스가 아니다 |
| 수동 스크린 리더 검증 | 도구·환경이 필요하다. 청크가 서면 그때 |

## 권한 없는 것은 숨긴다

**할 수 없는 조작은 화면에 안 그린다.** 비활성화해서 보여주지 않는다.

`8a` 가 내려주는 권한 목록으로 판단한다. **역할 이름으로 판단하지 않는다** —
화면이 `seller_owner` 를 알기 시작하면 판정이 두 벌이 되고, 규칙이 바뀔 때 한쪽만 고쳐진다.

```
GET /api/me/permissions  →  order:read 가 목록에 있나
```

**대가를 안다.** 사용자가 "왜 안 보이지" 를 물을 수 없고, 권한이 생기면 버튼이 갑자기 나타난다.
그래도 숨기는 쪽을 고른 것은 **기능의 존재 자체가 안 새게** 하려는 것이다.
관리자 기능이 비활성 상태로 보이면 그 시스템에 무엇이 있는지가 드러난다.

**목록은 근사치다.** `8a` 의 응답은 대상 행이 없는 판정이라, 버튼을 보일지 정하는 데만 쓴다.
실제 허용은 언제나 서버가 그 자원을 만질 때 다시 정한다.

## 볼 수 없는 필드는 그 줄을 안 그린다

응답에서 **키 자체가 빠져 온다**(`D5`). 화면도 그 줄을 통째로 안 그린다.

```json
{ "user_id": 3, "display_name": "홍길동", "_visible_field_groups": ["basic"] }
```

`email` 이 없으므로 "전자우편" 행을 아예 안 만든다. `-` 나 `···` 로 자리를 채우지 않는다.

**값이 없는 것과 볼 수 없는 것을 섞지 않는다.** 서버가 그 둘을 구분해서 준다 —
값이 없으면 `null`, 볼 수 없으면 **키가 없다**. 화면도 그대로 가른다.

| 응답 | 화면 |
|---|---|
| 키가 없다 | 그 줄을 안 그린다 |
| 키가 있고 `null` | 그 줄을 그리고 "없음" 을 쓴다 |

## 오류는 자리를 가려서 보여준다

**사용자가 고칠 수 있는 것과 아닌 것을 가른다.** 전부 토스트로 띄우면 어느 칸이 틀렸는지를
사용자가 찾아야 하고, 전부 인라인이면 붙일 자리가 없는 오류를 못 그린다.

| 오류 | 어디에 | 예 |
|---|---|---|
| 그 입력칸의 값이 규칙에 안 맞음 | **그 칸 아래 인라인** | 비밀번호가 8자 미만 |
| **어느 칸인지 서버가 안 알려줌** | **폼 전체.** 칸을 지목하지 않는다 | 로그인 실패 |
| 요청은 옳은데 지금 상태가 안 맞음 | **토스트** | 이미 가입된 이메일, 필수 동의라 철회 불가 |
| 권한이 없음 (403) | **페이지 전체** | 감사 로그에 직접 주소로 들어옴 |
| 자원이 없음 (404) | **페이지 전체** | |
| 인증이 끊김 (401) | **로그인 화면으로 보낸다** | 다른 기기에서 탈퇴됨 |
| 서버 오류 (5xx) | **페이지 전체** | |

### 모르는 칸을 지목하지 않는다

**서버가 어느 칸이 틀렸는지 일부러 안 알려주는 오류가 있다.** 로그인 실패가 그렇다 —
없는 계정인지 틀린 비밀번호인지 가르면 **가입 여부를 물어보는 도구**가 된다(`D14`).

그럴 때 **입력칸에 `aria-invalid` 를 걸지 않는다.** 그 속성의 뜻은 「이 칸의 값이 유효하지 않다」인데,
로그인 실패에서 두 칸에 다 걸면 **맞은 이메일까지 「잘못된 입력」이라고 낭독된다.**
사실이 아닌 것을 말하는 것이라 색만으로 알리는 것보다 나쁘다.

| | 칸을 지목하나 |
|---|---|
| 형식이 틀렸다 — 화면이 안다 | **지목한다.** 그 칸에 `aria-invalid` 와 인라인 문구 |
| 조합이 틀렸다 — 서버만 알고 안 알려준다 | **안 지목한다.** 폼 전체 오류 하나 |

폼 전체 오류는 **제출 버튼 위, 입력칸 아래**에 두고 `role="alert"` 를 붙인다.
위에 두면 스크롤한 화면에서 안 보이고, 아래에 두면 방금 누른 자리 바로 옆이다.

**어느 칸인지는 `type` 으로 안다.** 상태 코드로는 못 가른다 — `422` 하나에 여섯 가지가 뭉쳐 있다.
`D5` 가 "프론트는 상태 코드가 아니라 `type` 으로 분기한다" 고 정한 이유가 이것이다.

**`detail` 문자열로 분기하지 않는다.** 문구를 다듬는 순간 화면이 깨진다.

### 401 은 조용히 보내지 않는다

세션이 끊겨서 로그인 화면으로 갈 때 **왜 나갔는지를 알린다.**
아무 설명 없이 로그인 화면이 나오면 사용자는 자기가 뭘 잘못 눌렀다고 생각한다.

지금은 401 응답에 본문이 없다(`5-1`). 본문이 생기는 것은 청크 `7b` 이고,
그전까지는 "로그인이 만료됐다" 같은 일반 문구를 쓴다.

## 빈 상태

**아무것도 없는 것과 조건에 맞는 게 없는 것을 가른다.**

| 상황 | 무엇을 쓰나 |
|---|---|
| 데이터가 아직 없다 | 무엇을 하면 생기는지 적고, 그 조작으로 가는 길을 준다 |
| 필터·검색 결과가 0건 | 조건을 바꾸라고 알린다. **조건을 지우는 길을 같이 준다** |

```
아직 없음    주문하신 상품이 없습니다. 상품을 둘러보세요.
결과 없음    조건에 맞는 주문이 없습니다. 조건을 지우고 다시 찾아보세요.
```

권한이 없어서 0건인 경우는 **여기 안 온다** — 그 화면에 애초에 못 들어온다(위 「숨긴다」).

## 기다리는 동안

| 상황 | 어떻게 |
|---|---|
| 첫 진입 | 뼈대(skeleton)를 그린다 |
| 이미 있는 화면을 갱신 | **기존 내용을 두고** 흐리게 하거나 위에 표시를 얹는다 |
| 사용자가 누른 버튼 | 그 버튼만 비활성 + 진행 표시. 화면 전체를 막지 않는다 |

갱신할 때 화면을 비우지 않는 이유는 **위치를 잃기 때문**이다.
목록이 통째로 사라졌다 나타나면 사용자가 보던 자리가 어디였는지 모른다.

**첫 진입의 뼈대는 `app/loading.tsx` 하나다**(`Q8`). 화면마다 모양이 다른 뼈대를 두면
화면이 늘 때마다 파일이 늘고, 그중 하나를 빠뜨리면 **그 화면만 멈춘 것처럼 보인다.**
거기 있는 것은 어느 화면에서나 참인 것 — 머리와 발은 셸이 이미 그렸고 바뀌는 것은 가운데뿐이다.

**이 파일이 없으면 브라우저가 이전 화면에 머문다.** 사용자에게는 누른 것이 안 먹은 것으로
보이고, 그래서 같은 링크를 다시 누른다.
## 되돌릴 수 없는 조작

| 무엇 | 무엇을 요구하나 |
|---|---|
| 탈퇴 | **비밀번호 재확인**. 확인 대화상자만으로는 부족하다 |
| 자원 삭제 | 확인 대화상자 |
| 동의 철회 | 없음 — 다시 켤 수 있다 |

**세션을 가진 것과 비밀번호를 아는 것을 가른다.** 세션을 훔친 사람이 탈퇴까지 할 수 있으면
주인이 계정을 영영 잃는다. 이 원칙은 서버에도 같이 걸려 있다(`5g`).

되돌릴 수 있는 것에 확인을 붙이지 않는다. 확인이 흔해지면 사용자가 읽지 않고 누른다.

**확인 문구는 무엇이 사라지는지를 적는다.** "진행하시겠습니까?" 만으로는 무엇을 잃는지 모른다.

```
나쁨    정말 진행하시겠습니까?
좋음    탈퇴하시면 주문 내역을 더 이상 조회하실 수 없습니다. 탈퇴하시겠습니까?
```

## 문구

### 화면 문구는 존댓말이다

**`CLAUDE.md` 의 「글 작성 규칙」은 여기 안 걸린다.** 그쪽은 개발자가 읽는 글(문서·주석·커밋)의
규칙이라 평서형을 쓴다. 화면은 **사용자가 읽는 것**이라 존댓말을 쓴다.

```
문서·주석·커밋   철회는 기존 행을 고치지 않고 한 줄을 더한다
화면            수신 동의를 해제하시겠습니까?
```

두 규칙이 한 저장소에 같이 있으므로, **어느 쪽 글을 쓰고 있는지 먼저 안다.**
같은 사실을 서버 로그와 화면에 각각 쓸 때 문체가 갈리는 것이 정상이다.

**`screen-text.test.ts` 가 막는다**(`Q34`). `.tsx` 와 화면 표 파일에서 한글이 든 문자열을 걷어
`다` 로 끝나는 것(앞이 `니` 인 존댓말은 빼고)을 찾는다. `doc-lint.sh` 의 반대쪽이다 —
그쪽은 개발자 글의 존댓말을, 이쪽은 화면 글의 반말을 막는다.

**못 보는 것 셋**: 변수로 조립한 문장 · 서버가 내려준 문구 · `~했음` 같은 다른 반말 어미.
셋째는 실측으로 0건이라 어미 목록을 안 만들었다 — 하나 나오면 그때 목록으로 판다.

### 지키는 것

| 규칙 | 나쁨 | 좋음 |
|---|---|---|
| 사용자를 탓하지 않는다 | 이메일을 잘못 입력하셨습니다 | 이메일 형식이 올바르지 않습니다 |
| 다음에 무엇을 할지 적는다 | 오류가 발생했습니다 | 잠시 후 다시 시도해 주세요 |
| 시스템 용어를 안 쓴다 | 422 Unprocessable Entity | 필수 동의 항목은 해제할 수 없습니다 |
| 내부 값을 그대로 안 보인다 | scope=own | 내 주문만 |
| 과하게 사과하지 않는다 | 대단히 죄송합니다. 불편을 끼쳐드려… | 잠시 후 다시 시도해 주세요 |

`CLAUDE.md` 의 나머지 규칙(중복 금지, 미사여구 금지, 필요한 만큼만)은 화면에도 그대로 걸린다.
존댓말이라고 길어질 이유가 없다.

### 서버 문구를 그대로 안 쓴다

`D5` 의 `detail` 은 **평서형이고 개발자가 읽는 것에 가깝다.**

```
서버 detail    필수 동의 항목이라 철회할 수 없다. 탈퇴로 처리한다
화면            필수 동의 항목은 해제할 수 없습니다. 탈퇴를 원하시면 아래에서 진행해 주세요.
```

화면은 `type` 을 보고 **자기 문구를 고른다.** `detail` 을 그대로 찍으면 문체가 갈리고,
서버 메시지를 다듬는 순간 화면 문구가 같이 바뀐다.

이것이 `D5` 의 "프론트는 상태 코드가 아니라 `type` 으로 분기한다" 를 지켜야 하는 이유 하나 더다.

## 이 문서를 고칠 때

화면을 만들다가 여기 없는 상황이 나오면 **그 상황을 여기 먼저 추가한다.**
화면마다 다르게 그리기 시작하면 사용자가 같은 뜻을 매번 새로 배워야 한다.

`13b`(화면 권한 반영)가 이 문서의 「숨긴다」와 「볼 수 없는 필드」를 코드로 옮긴다.
