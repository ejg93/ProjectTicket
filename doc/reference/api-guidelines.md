# API 설계 규약

> **ProjectShop 에서 이식한 문서다.** 예시·청크 번호(`2g`·`Q36` 등)·쇼핑 도메인(주문·셀러·정산)은 ProjectShop 것이다.
> 티켓 도메인과 Kotlin 에 맞추는 것은 `PLAN.md` 이식 청크 `P` 줄이 한다. 그 청크가 닫히면 이 머리말을 지운다.
> 그때까지는 **원칙은 믿고 예시는 안 믿는다.**

우리가 정한 것만 적는다. **여기 없는 것은 Zalando RESTful API Guidelines 를 따른다.**
링크는 `external-references.md` 에 있다.

통째로 베끼지 않는 이유는 유지 때문이다. 수백 개를 옮겨 적으면 원본이 바뀌었을 때 어긋난 채로 남는다.

## 기준에서 벗어난 것

먼저 적는다. 벗어난 것을 뒤에 묻어 두면 못 찾는다.

| 항목 | Zalando | 우리 | 왜 |
|---|---|---|---|
| 페이징 | 커서 기반 권장 (SHOULD) | **오프셋 기반** | 커서는 정렬 키가 고정돼야 하고 임의 페이지 이동이 안 된다. 관리자 화면(청크 16)이 페이지 번호를 쓴다. 데이터 규모가 작아 오프셋의 성능 문제가 안 온다 |
| 전체 개수 | 안 주는 것을 권장 (SHOULD) | **준다** | 위와 같은 이유. 관리자 화면에 총 건수가 필요하다 |

둘 다 `SHOULD` 라 벗어날 수 있다. 청크 42(성능 튜닝)나 70(부하 테스트)에서 오프셋이 실제로 문제가 되면 그때 커서로 바꾼다.

`MUST` 는 벗어나지 않는다. 벗어날 거면 기준으로 삼은 의미가 없어진다.

## 이름

### JSON 속성은 snake_case

Zalando 의 `MUST` 다. Java 필드는 camelCase 로 두고 **직렬화할 때만** 바꾼다.

```yaml
spring:
  jackson:
    property-naming-strategy: SNAKE_CASE
```

설정 한 줄이라 비용이 없고, 얻는 것이 있다. **DB 컬럼 이름과 JSON 필드 이름이 같아진다.**

```
DB          created_at, password_hash, is_org_role
JSON        created_at, password_hash, is_org_role
Java 필드    createdAt, passwordHash, isOrgRole
```

이름이 바뀌는 자리가 Java 안쪽 하나뿐이라, 로그와 쿼리와 응답을 같은 말로 읽을 수 있다.

```
로그:   WARN 주문 조회 실패 order_id=4837
쿼리:   select total_amount from orders where id = 4837
응답:   { "total_amount": 15000 }
```

셋을 같은 단어로 찾을 수 있다. 장애를 볼 때 검색어가 하나다.

### 프론트는 camelCase 를 쓴다

API 경계까지가 `snake_case` 고, 프론트는 받자마자 바꿔서 JS 관례대로 쓴다.

```
백엔드 ──snake──> API ──snake──> 변환 레이어 ──camel──> 프론트 코드
```

**변환은 한 곳에서만 한다.** `fetch` 를 감싼 함수 하나를 두고, 그것을 거치지 않는 호출을 금지한다.
두 곳에서 변환하면 어떤 응답은 바뀌고 어떤 것은 안 바뀌어서 추적이 안 된다.

이 결정은 프론트 안쪽 일이라 **백엔드는 몰라도 된다.** 청크 13(프론트 골격)에서 래퍼를 만들 때 붙인다.

대가가 하나 있다. 개발자 도구 네트워크 탭에는 `total_amount` 로 보이고 코드에는 `totalAmount` 로 있어서,
프론트를 디버깅할 때 한 번 변환해서 읽어야 한다.

타입을 손으로 두 벌 쓰면 어긋난다. 청크 2a 의 OpenAPI 스펙에서 타입을 생성하면 `snake_case` 로 나오므로,
TypeScript 의 템플릿 리터럴 타입으로 변환해서 쓴다.

**응답 record 에는 `@Schema(name = …)` 로 이름을 준다**(`Q45`). 스펙을 그리는 도구가 이름을
**자바 클래스의 짧은 이름**으로 지어서, `Page`·`Summary`·`Detail` 처럼 자원마다 같은 이름을 쓰면
**서로 덮어쓴다** — 한동안 `GET /api/orders` 가 정산 요약을 돌려준다고 적혀 있었다.
`SchemaNameTest` 가 소스에서, `OpenApiSpecTest` 가 스펙에서 각각 막는다.

**그 전제가 한동안 깨져 있었다**(`Q41`). 스펙을 그리는 swagger-core 는 Jackson 2 라
애플리케이션의 Jackson 3 설정(`property-naming-strategy`)을 못 읽어서 **낙타 표기로 그렸다** —
스펙을 보고 만든 타입은 없는 키를 읽게 된다. `OpenApiConfig` 가 표기를 물리고
`OpenApiSpecTest` 가 갈리는 것을 막는다. **봉투 메타 필드(`_visible_field_groups`)만 밑줄로 시작한다.**

### URL

- 자원은 **복수형 명사**. `/api/products`, `/api/orders`
- 동사를 쓰지 않는다. `/api/getProduct` 안 됨
- 여러 단어는 하이픈. `/api/order-items`
- 소문자만 쓴다

## 메서드

| 메서드 | 쓰는 곳 |
|---|---|
| GET | 조회. 부수 효과 없음 |
| POST | 생성. 그리고 아래 「동작」 |
| PUT | 전체 교체. 잘 안 쓴다 |
| PATCH | 부분 수정. 수정은 기본적으로 이쪽 |
| DELETE | 삭제 |

### `PATCH` 는 패치 문서의 형식을 밝힌다

RFC 5789 는 `PATCH` 의 본문이 「바꿀 것의 목록」이고 **그 형식을 미디어 타입이 식별한다**고 한다.
`application/json` 으로 부분 갱신을 보내면 **`null` 이 삭제인지 무시인지**를 정할 자리가 없다.

`application/merge-patch+json`(RFC 7396)을 쓴다 — **`null` 은 그 필드를 지우라는 뜻**이고,
안 보낸 필드는 안 건드린다. `api.ts` 가 `PATCH` 에 그 타입을 자동으로 붙인다(`Q11`).

**고칠 필드가 하나뿐일 때도 밝힌다.** 지금은 안 갈리지만 필드가 늘면 그때 갈리고,
그때는 이미 쓰는 곳이 여럿이라 계약 변경이 된다.

## 상태 코드

| 코드 | 언제 |
|---|---|
| 200 | 조회·수정 성공 |
| 201 | 생성 성공. `Location` 헤더에 새 자원 경로 |
| 204 | 성공했고 돌려줄 본문이 없음 |
| 400 | 요청 형식이 틀림 |
| 401 | 로그인 안 됨 |
| 403 / 404 | 권한 없음. **어느 쪽을 줄지는 자원마다 다르다.** 아래 「권한 실패」 |
| 409 | 상태가 안 맞음. 허용되지 않은 상태 전이, 재고 부족 |
| 422 | 형식은 맞는데 값이 규칙에 안 맞음 |

**열거값이 목록 밖이면 422 가 아니라 400 이다**(2026-08-29, `43a-16` 사용자 선택).

「형식은 맞는데 값이 규칙에 안 맞음」의 정의로만 보면 422 인데, **그 자리까지 못 간다** —
요청 필드를 enum 으로 받으므로 <b>역직렬화 단계에서 걸려서</b> 검증기가 돌기 전에 400 이 나간다.

**그래도 enum 으로 받는다.** 문자열로 받고 `@Pattern` 을 걸면 422 를 낼 수 있지만 값이 둘 갈린다.

| | enum 으로 받기 | 문자열 + `@Pattern` |
|---|---|---|
| 강제 지점 | **타입**(1위) | 앱 검증(3위) |
| 값 목록 사본 | `check` + enum | `check` + enum + **정규식** |
| 모르는 값 | 400 | 422 |

**사본이 하나 느는 값이 오류 코드 하나보다 크다.** 400 과 422 는 둘 다 「클라이언트가 고칠 것」을
말하고, 사본은 값이 늘 때마다 **한쪽만 고쳐지는 날**을 만든다.

**`Location` 이 만들어진 자원을 못 가리킬 때가 있다.** 결제(`POST /api/payments`)가 그 자리다 —
결제 결과를 다시 보는 경로가 주문 상세뿐이라 거기를 가리킨다. 결제만 여는 경로를 따로 내면
그 응답이 주문 상세의 `payment` 필드 그룹과 같은 것을 그리게 된다(청크 12-2).

**바깥이 거절한 것은 4xx 가 아니다.** 카드 거절은 요청 처리가 성공한 결과라 201 로 내려가고
본문의 `status` 가 그것을 말한다. 4xx 로 던지면 그 결과를 적은 기록이 같이 롤백된다(`D11`).

## 오류 본문

**RFC 9457 Problem Details.** `application/problem+json` 으로 내보낸다.

```json
{
  "type": "https://example.com/probs/insufficient-scope",
  "title": "권한이 부족하다",
  "status": 403,
  "detail": "이 주문은 다른 셀러의 것이다",
  "instance": "/api/orders/4837"
}
```

Spring Framework 6 부터 `ProblemDetail` 이 있으므로 직접 만들지 않는다.

```yaml
spring:
  mvc:
    problemdetails:
      enabled: true
```

`type` 이 URI 라서 오류 종류마다 설명 문서를 가리킬 수 있다. **프론트는 상태 코드가 아니라 `type` 으로 분기한다.**

### `type` 은 `tag:` URI 다

`tag:projectshop.example,2026:error:<슬러그>` 형태다. 목록은 코드의 `ErrorCode` 에 있다(청크 7b).

`https://` URL 을 안 쓴 것은 **없는 도메인을 가리키지 않으려는 것**이다.
쓰면 언젠가 열어보는 사람이 생기고 그때 404 가 난다. RFC 9457 은 `type` 이 역참조 가능해야 한다고
요구하지 않는다.

**`urn:shop:` 에서 옮겨 왔다**(`Q1`). RFC 8141 이 URN 의 네임스페이스 식별자를 **등록**하게 하는데
`shop` 은 정식 등록도, IANA 가 주는 비공식 이름(`urn-<숫자>`)도 아니었다 —
**문법만 맞고 URN 은 아닌 값**이었다. `tag:` URI(RFC 4151)는 등록이 필요 없고
권한 이름과 날짜로 소유를 밝힌다.

`projectshop.example` 은 자리표시다. RFC 2606 이 예시용으로 잡아 둔 이름이라 남의 것을 가리킬
위험이 없다. **진짜 도메인이 생기면 그때 바꾸고, 그건 계약 변경이다.**

**화면은 접두어를 모른다.** `ApiError` 가 슬러그를 떼어 주고 화면은 그것으로 분기한다 —
접두어가 다시 바뀔 때 고칠 자리가 `api.ts` 하나다. 두 상수가 갈리면 화면이 슬러그를 못 뽑아
**아홉 화면이 한꺼번에 기본 문구로 떨어지므로**, `api.test.ts` 가 서버 상수를 읽어 대조한다.

### 프레임워크가 끊는 오류도 우리 `type` 을 단다

헤더 누락·깨진 JSON·405·415 처럼 MVC 에 닿기 전에 끊기는 것들이다.
**하나로 뭉치면 안 된다**(`Q1`) — 전부 `validation-failed` 를 주면 **상태 코드보다 `type` 이 더 뭉쳐서**
「상태 코드가 아니라 `type` 으로 분기한다」는 이 문서의 근거가 그 자리에서 뒤집힌다.

`ApiExceptionHandler.frameworkCodeOf` 가 상태 코드로 가른다 — 예외 종류가 아니라 상태 코드로
가르는 이유는 프레임워크가 예외를 늘려도 상태 코드는 같은 표에 떨어져서다.

### 오류 본문에만 `trace_id` 를 넣는다

`D16` 이 정한 것이다. 성공 응답에 넣으면 모든 응답이 커지는데, 되짚어 볼 일이 있는 것은 실패한 요청이다.

요청에 `traceparent` 헤더가 있으면 그 안의 trace-id 를 쓰고 없으면 만든다.
**아직 로그와 안 묶여 있다** — MDC 에 넣는 것은 청크 2b 고, 지금은 애플리케이션 로그가 0건이다.

### 검증 실패는 어느 필드가 틀렸는지 준다

```json
{
  "type": "tag:projectshop.example,2026:error:validation-failed",
  "status": 400,
  "errors": [{"field": "display_name", "message": "공백일 수 없습니다"}]
}
```

**필드 이름은 요청에 쓴 그대로**(snake_case)다. Bean Validation 은 Java 이름을 주므로 바꿔서 내보낸다 —
요청에 쓴 이름과 오류에 나온 이름이 다르면 화면이 그 필드를 못 찾는다.
상태 코드는 종류가 적어서 서로 다른 오류가 같은 코드로 뭉친다.

## 목록 조회

### 요청

| 파라미터 | 뜻 | 기본값 |
|---|---|---|
| `page` | 0 부터 시작하는 페이지 번호 | 0 |
| `size` | 한 페이지 크기 | 20 |
| `sort` | `필드,방향`. 예: `created_at,desc` | 자원마다 정함 |

**정렬 필드는 허용 목록으로 받는다.** 컬럼명은 값이 아니라 식별자라 바인딩이 안 되고,
결합이 강제되므로 들어올 수 있는 값을 우리가 정한다(`D14`). 목록에 없는 필드는 400 이다.

| 자원 | 정렬 가능 | 기본 |
|---|---|---|
| 감사 로그 | 없음 | 최신순 고정 |
| 상품 | `created_at`, `name` | `created_at,desc` |

상품에 `price` 를 안 열었다. 가격은 `sku` 에 있어서 상품당 여럿이고
"최저가 기준인가", "품절 조합도 세나" 를 재고 축(52) 전에 정하면 감이다.

`size` 의 최대값을 100 으로 막는다. 안 막으면 목록 하나로 전체를 긁어 갈 수 있다.

**그 셋을 컨트롤러가 직접 안 받는다**(`Q23`). `Paging` 하나로 받고 `*Query` 에도 그대로 넘긴다.

```java
public ProductQuery.PublicPage list(String sort, Paging paging) { ... }
```

**보정이 `Paging` 의 생성자에 있어서** 그 타입이 존재한다는 것 자체가 「상한을 거쳤다」는 뜻이다.
전에는 보정이 `Paging.of()` 안에 있었고 **목록 입구 열 곳이 각자 그것을 불렀다** —
열한 번째가 빠뜨려도 컴파일도 테스트도 통과하고 상한만 조용히 사라진다.

**「그 타입을 안 쓰는 것」은 타입이 못 막는다.** `Page` 로 끝나는 것을 돌려주는 `*Query` 의
`public` 메서드가 `Paging` 을 받는지는 `ArchitectureTest` 가 본다.

**`sort` 는 자리가 다르다**(`Q24`). 허용 목록이 자원마다 달라서 `Paging` 처럼 한 곳으로 못 모은다 —
`ArgumentResolver` 는 누가 부르는지 모르니 어느 목록을 볼지도 모른다. 그래서 **둘로 덮는다.**

| 무엇 | 무엇을 막나 |
|---|---|
| `ListQuery.OrderBy` 타입 | 검증 안 된 문자열을 `order by` 자리에 쓰는 것 |
| `ArchitectureTest` 규칙 | **그 타입을 아예 안 거치는 것** |

```java
OrderBy orderBy = ListQuery.orderBy(sort, DEFAULT_SORT, SORTABLE);
... + " order by " + orderBy.clause() + ", p.product_id desc"
```

**타입만으로는 못 막는다.** 조립이 문자열이라 `" order by " + sort` 라고 쓰면 그대로 지나가고,
`public record` 의 생성자를 닫을 수 없어서 `new OrderBy(요청문자열)` 도 열려 있다.
**그 타입은 「거쳤다」를 뜻하지 「거칠 수밖에 없다」를 뜻하지 않는다.**

### 응답

```json
{
  "items": [ ... ],
  "page": 0,
  "size": 20,
  "total": 137
}
```

껍데기 이름을 하나로 고정한다. `data`·`list`·`content` 를 섞어 쓰면 프론트가 엔드포인트마다 다른 코드를 쓴다.

**빈 목록은 `[]` 다.** `null` 을 주지 않는다.

## 값의 형식

| 종류 | 형식 | 예 |
|---|---|---|
| 시각 | RFC 3339 (ISO 8601). **UTC 의 `Z`** — `time-rules.md` 「표현 — 층마다」가 정한다 | `2026-08-05T05:30:00Z` |
| 날짜 | `YYYY-MM-DD` | `2026-08-05` |
| 금액 | 정수. 원 단위 | `15000` |
| 열거값 | 대문자 스네이크 | `PAID`, `SHIPPING_READY` |

금액을 문자열로 주는 방식도 있지만(정밀도 손실 방지) 원화는 정수라 해당이 없다.
자세한 것은 D8 금액 규약에서 정한다.

## null 과 생략

Zalando 의 `MUST` — **없는 것과 `null` 에 다른 뜻을 주지 않는다.**

이 규칙이 우리 필드 마스킹(청크 4d)과 정면으로 만난다.

셀러가 주문을 볼 때 결제 수단이 안 보인다. 응답에 어떻게 나가야 하나.

| 방법 | 문제 |
|---|---|
| `"payment_method": null` | "권한이 없어서 안 보임" 과 "결제 수단이 아직 없음" 이 구분 안 된다 |
| 필드를 아예 생략 | 클라이언트가 필드 없음을 권한 문제인지 값 없음인지 모른다 |

**생략하되, 무엇이 보이는지를 같이 알려준다.**

```json
{
  "id": 4837,
  "total_amount": 15000,
  "recipient_name": "홍길동",
  "_visible_field_groups": ["basic", "shipping"]
}
```

`payment` 그룹이 목록에 없으므로 결제 관련 필드가 빠진 것이 **권한 때문**임이 드러난다.
필드가 있는데 값이 없으면 그건 진짜로 값이 없는 것이다.

밑줄로 시작하는 이름은 메타 필드라는 표시다. 자원의 속성이 아니다.

**밑줄은 "이 응답이 깎였다" 는 표시지 "필드 그룹" 이라는 뜻이 아니다.**

같은 단어가 두 자리에 나와서 갈라 둔다.

| 자리 | 이름 | 뜻 |
|---|---|---|
| 깎인 자원 응답 (`GET /api/me`) | `_visible_field_groups` | **이 응답에서** 무엇이 살아남았나 |
| 권한 목록 (`GET /api/me/permissions`) | `visible_field_groups` | 이 권한이 열어 주는 범위 |

앞은 옆의 필드들이 왜 빠졌는지를 설명하는 메타 정보라 밑줄이 붙는다.
뒤는 권한 항목 자체의 속성이라 밑줄이 없다 — **거기서는 깎인 것이 없다.**

### `allowed_actions` 는 밑줄이 없다

주문 상세가 **지금 이 자원에 무엇을 할 수 있는지**를 같이 내린다(청크 11c-3b).

```json
{
  "seller_order_number": "S-20260812-K3M9P7",
  "status": "DELIVERED",
  "allowed_actions": ["CONFIRM", "REQUEST_RETURN"]
}
```

밑줄이 안 붙는 이유는 위 규칙 그대로다 — **옆의 필드가 왜 빠졌는지를 설명하지 않는다.**
빠진 것이 없고, 이 자원의 지금 상태에서 열린 것을 세어 준 값이다.

**값은 「동작」 절의 경로 이름과 같다.** 소문자로 바꾸고 밑줄을 하이픈으로 바꾸면 경로가 된다.

```
"REQUEST_RETURN"  →  POST /api/shipments/{번호}/request-return
```

동작과 경로를 잇는 표를 화면이 따로 들면 동작이 늘 때 한쪽만 고쳐진다.

**권한 목록(`8a`)과 다르다.** 저쪽은 "이 사람이 이 동작을 할 수 있는 역할인가" 라 상태를 안 보고,
이쪽은 **이 행의 상태까지** 본다. 배송완료 주문 하나 때문에 셀러의 권한이 목록에서
통째로 사라지지 않게 하려고 둘을 갈랐다(`permission-rules.md` 「상태 축」).

### 모르는 열거값은 무시한다

**이 목록이 나가는 순간 값의 집합이 계약이 된다.** 화면이 `allowed_actions` 로 버튼을 그리므로,
서버가 동작을 하나 추가하면 화면은 **모르는 값**을 받는다.

**화면은 모르는 값을 조용히 건너뛴다.** 터지거나 빈 버튼을 그리지 않는다.
그래야 서버가 동작을 늘릴 때 화면 배포를 기다리지 않는다 — Stripe·Shopify 가 열거값을
늘릴 때 클라이언트에 요구하는 것과 같다.

같은 규칙이 상태값에도 걸린다. `status` 에 모르는 값이 오면 **그 값을 그대로 보여주고**
아는 값처럼 분기하지 않는다.

**서버 쪽에는 안 걸린다.** 서버가 모르는 값을 만나면 그건 데이터가 깨진 것이라
`Shipment.of()` 처럼 터뜨린다(`D23` 「열거값을 어디에 두나」).

## 권한 실패 — 403 이냐 404 냐

403 을 주면 **그 자원이 존재한다는 사실이 샌다.** 번호를 훑으면 실재하는 번호의 지도가 그려진다.
404 를 주면 정보는 안 새지만 클라이언트가 권한 문제인지 오탈자인지 모른다.

자원의 민감도로 가른다.

| 자원 | 권한 없을 때 | 왜 |
|---|---|---|
| 상품 | **403** | 어차피 공개 목록에 있다. 존재를 숨길 이유가 없다 |
| 주문 | **404** | 주문 수와 증가 속도가 새면 안 된다 |
| 결제 | **404** | 주문과 같다 |
| 사용자 | **404** | 계정 존재 여부는 가입 시도로 알 수 있지만 굳이 알려주지 않는다 |
| 셀러 | **403** | 공개 정보다 |
| 역할·권한 | **403** | 관리 기능이라 접근한 사람이 이미 로그인 상태다 |

로그인 자체가 안 됐으면 **401** 이다. 이건 자원과 무관하다.

### 판정 결과와의 대응

`permission-rules.md` 가 적어 둔 문제 — 우리 `Decision` 은 "거부 규칙이 있어서 거부" 와
"규칙이 없어서 거부" 를 같은 값으로 뭉치고 있다.

**응답은 둘을 구분하지 않는다.** 위 표대로 자원별로만 가른다.
구분해서 내보내면 "당신에게는 명시적 거부가 걸려 있다" 는 정보가 새고, 그것도 권한 구조의 노출이다.

내부적으로 구분하는 것은 필요하다. 감사 로그(청크 4b)에는 어느 규칙이 이겼는지가 남아야 한다.

### 판정 자체가 실패하면

DB 조회가 실패하는 등 판정을 못 한 경우다. XACML 의 `Indeterminate` 에 해당한다.

**거부로 떨어뜨리고 500 을 준다.** 허용으로 떨어지면 안 된다.
권한 판정이 고장 났을 때 열리는 시스템은 고장 자체가 공격 수단이 된다.

## 동작 — CRUD 가 아닌 것

주문 취소, 배송 시작, 정산 확정 같은 것이다. 자원의 생성·수정으로 표현이 안 된다.

**하위 경로에 POST 한다.**

```
POST /api/orders/{id}/cancel
POST /api/orders/{id}/ship
POST /api/settlements/{id}/confirm
```

`PATCH /api/orders/{id}` 로 `status` 를 바꾸는 방식은 쓰지 않는다.
전이표를 거치지 않는 상태 변경 경로가 생기기 때문이다(ADR 0009).
상태는 **동작의 결과**지 클라이언트가 정하는 값이 아니다.

허용되지 않은 전이는 **409** 다.

## 버전

**지금은 버전을 안 붙인다.** `/api/orders` 로 간다.

붙일 시점이 오면(청크 72) 그때 `/api/v2/...` 를 추가하고 기존 경로를 v1 으로 남긴다.
지금 `/api/v1/` 을 붙이면 쓰지도 않을 버전 체계를 이고 간다.

호환을 깨는 변경의 기준은 Zalando 의 호환성 장을 따른다.

## 파일 응답

**JSON 이 아닌 응답이 하나 있다** — 거래기록 내려받기(`GET /api/orders/{번호}/record`, 청크 `15-5`).
소비자가 열어서 읽고 보관하는 것이 목적이라, 구조를 파싱해야 뜻이 서는 형식은 그 목적에 안 맞는다.

| 무엇 | 어떻게 |
|---|---|
| 형식 | `text/plain;charset=UTF-8` |
| 저장 | `Content-Disposition: attachment` — 파일 이름에 그 자원의 노출 번호를 넣는다 |
| 권한 | **같은 조회를 재사용한다.** 표를 다시 읽으면 판정을 지나치는 두 번째 경로가 생긴다 |
| 오류 | 본문 형식만 다르고 상태 코드와 판정은 JSON 경로와 같다 |

**목록을 파일로 내리지 않는다.** 파일은 「이 자원 하나를 통째로 보관한다」는 뜻이고,
여러 건을 담기 시작하면 그건 조회지 보관이 아니다.

## 헤더

| 헤더 | 용도 |
|---|---|
| `traceparent` | 요청 추적. W3C Trace Context 형식 (D16) |
| `Idempotency-Key` | 멱등 요청. `POST /api/orders`·`POST /api/payments` 에 필수다 (D11) |
| `Location` | 201 응답에서 새 자원 경로 |

자체 헤더를 만들 때는 `X-` 를 붙이지 않는다. RFC 6648 이 그 관행을 폐기했다.

## 인증

세션 쿠키다. `HttpOnly` + `SameSite`. 토큰을 헤더로 받지 않는다.
근거는 `PLAN.md` 의 「인증은 세션 쿠키, JWT 아님」에 있다.

쿠키를 골랐으므로 CSRF 토큰이 필요하다(청크 5b). 쓰기 요청은 토큰을 같이 보낸다.

### 401 에는 `WWW-Authenticate` 를 붙인다

RFC 9110 제15.5.2절이 「The server generating a 401 response **MUST send a WWW-Authenticate
header field** containing at least one challenge」라고 한다. **예외가 없다.**

**등록된 스킴을 안 쓴다**(`Q12`). `Basic` 이나 `Digest` 를 넣으면 브라우저가 **기본 인증
대화상자를 띄워 우리 로그인 화면을 가리고**, 우리 인증은 세션 쿠키라 그 상자에 무엇을 넣어도
안 맞는다. `WWW-Authenticate: Session` 을 쓴다 — 브라우저는 모르는 스킴을 무시하므로
팝업이 안 뜨고, 형식상 챌린지는 하나 있다.

**버린 길 셋**을 적어 둔다. 등록된 스킴(팝업이 뜬다), 403 으로 바꾸기(「인증이 없다」와
「권한이 없다」가 뭉치고 화면의 401 처리를 다시 짜야 한다), 그냥 두기(MUST 위반이 근거 없이 남는다).

## 이 문서를 고칠 때

새 규칙이 필요해지면 여기 추가하고, Zalando 에 이미 있는 규칙이면 **적지 말고 따른다.**
중복해서 적으면 원본이 바뀌었을 때 어느 쪽이 맞는지 모르게 된다.

기준을 벗어날 때는 맨 위 표에 추가한다. 벗어난 사실이 한 군데 모여 있어야 나중에 되돌릴 수 있다.
