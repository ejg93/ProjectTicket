# 관측 규약

> **ProjectShop 에서 이식한 문서다.** 예시·청크 번호(`2g`·`Q36` 등)·쇼핑 도메인(주문·셀러·정산)은 ProjectShop 것이다.
> 티켓 도메인과 Kotlin 에 맞추는 것은 `PLAN.md` 이식 청크 `P` 줄이 한다. 그 청크가 닫히면 이 머리말을 지운다.
> 그때까지는 **원칙은 믿고 예시는 안 믿는다.**

요청 하나를 로그에서 처음부터 끝까지 따라갈 수 있도록 추적 ID·로그 레벨·형식을 정한다.

기준은 Micrometer Tracing 과 W3C Trace Context 헤더 형식이다.
OpenTelemetry 를 안 붙이는 근거는 `external-references.md` 에 있다.

## 감사 로그와 다르다

| | 관측 로그 (이 문서) | 감사 로그 (청크 4b) |
|---|---|---|
| 답하는 질문 | 이 요청이 어디서 느려졌나, 왜 실패했나 | 누가 무슨 권한으로 무엇을 했나 |
| 저장 | 파일 | DB 테이블 |
| 보관 | 지워도 된다 | 지우면 안 된다 |
| 개인정보 | 안 담는다 | 행위 주체를 담는다 |

둘을 한 곳에 쓰면 지워도 되는 것과 안 되는 것이 섞인다.

### 감사 기록은 사건 종류가 전파를 정한다

`AuditLog.Kind` 를 호출자가 고르고 그 값이 트랜잭션 전파를 결정한다(청크 `4b-2`).

| 종류 | 전파 | 언제 |
|---|---|---|
| `ATTEMPT` | `REQUIRES_NEW` | **업무가 안 일어난 것 자체가 기록할 사실**인 사건. 권한 거부 |
| `OUTCOME` | `REQUIRED` | 업무가 성립해야 사실이 되는 사건. 역할 부여, 상품 생성, 탈퇴 |

한쪽으로 몰면 양쪽 다 감사가 깨진다. 전부 `REQUIRES_NEW` 면 롤백된 일이 "했다" 로 남고,
전부 `REQUIRED` 면 **실패한 시도가 정의상 한 줄도 안 남는다.**

후자가 실제로 있었다. `@Transactional` 서비스 안에서 판정하고 거부로 예외를 던지면
그 거부 기록까지 같이 롤백돼서, **경로마다 남는 것과 안 남는 것이 갈렸다.**
판정 밖에서 기록하는 조회 경로만 남아 있어서 **감사 로그로 시도를 세면 수가 틀린다.**

종류를 인자로 받는 이유는 강제 지점을 타입까지 올리려는 것이다(`D23` 축 2).
새 사건을 추가할 때 안 고르면 컴파일이 안 되므로 판단을 건너뛸 수 없다.

**대가 둘을 안다.** `REQUIRES_NEW` 는 커넥션을 하나 더 잡고,
`audit_log` 에 외래키가 없어서 **아직 커밋 안 된 행을 가리키는 기록이 남을 수 있다.**
후자는 원래 그렇게 설계된 것이다 — 계정이 파기돼도 기록은 남아야 해서 외래키를 안 걸었다(`V10`).

## 추적 ID

요청이 들어올 때 발급하고 그 요청에서 나가는 **모든 로그 줄에 찍는다.**
로그가 뒤엉켜도 ID 로 묶으면 요청 하나가 복원된다.

| 항목 | 값 |
|---|---|
| 헤더 형식 | `traceparent` (W3C Trace Context) |
| 발급 | Micrometer Tracing + Brave. 헤더가 오면 이어받고 없으면 만든다 |
| 로그에 찍는 값 | `traceId` **뒤** 6자리, `spanId` **앞** 4자리 |
| 전달 | MDC 에 넣어 로그 패턴이 자동으로 집어간다 |

자체 헤더를 만들지 않는다. 청크 62·63 에서 관측 도구를 붙일 때 갈아엎게 된다.

로그에 전체 32자리를 찍으면 줄이 길어져서 일부만 쓴다.
도구에 넣을 때는 전체 값이 필요하므로 MDC 에는 전체를 담는다.

**뒷자리를 쓴다.** Brave 의 128비트 ID 는 **앞 8자리가 생성 시각(epoch 초)**이라
같은 시간대에 온 요청이 앞부분에서 전부 같아 보인다.

```
6a799d9b13834020bad1ab9f11421451
6a799d9beabee5fd24c6f854f2f4ea2c    ← 앞 8자리가 같다. 앞자리를 찍으면 못 가른다
```

**스팬은 반대로 앞자리다.** 루트 스팬의 ID 가 추적 ID 의 하위 64비트와 같아서,
둘 다 뒷자리를 찍으면 `[d6d1cb,d1cb]` 처럼 같은 글자가 두 번 보인다.

### 값을 만드는 곳은 하나다

오류 응답의 `trace_id`(아래)도 **추적기에서 가져온다.** `traceparent` 헤더를 따로 파싱하지 않는다 —
두 자리가 각자 정하면 헤더가 깨졌을 때 어느 쪽이 이기는지가 갈리고,
그러면 **사용자가 불러 준 ID 로 로그를 찾았는데 안 나온다.**

### 응답에는 오류일 때만 넣는다

RFC 9457 Problem Details 본문에 `trace_id` 를 넣는다(청크 7b).

```json
{ "type": "...", "status": 403, "detail": "...", "trace_id": "018f2b3c..." }
```

사용자가 오류 화면의 ID 를 불러주면 그 요청의 로그로 바로 간다.

성공 응답에는 안 넣는다. 쓸 일이 없는데 모든 응답이 커진다.

## 형식 — 사람이 읽는 텍스트

```
09:55:01.175Z INFO  [018f2b,a3c1] c.p.s.order.OrderService : 주문 생성 order_id=1024
```

**시각은 UTC 고 `Z` 를 붙인다**(`Q35`, `time-rules.md` 「표현 — 층마다」). 안 적으면 JVM 시간대를 따라가 Windows 와 CI 가 갈렸다.

JSON 으로 안 찍는 이유는 **로그를 모을 수집기가 없어서**다.
구조화해 봐야 결국 터미널에서 눈으로 읽는다.

서버가 여럿이 되거나 수집기가 붙으면(청크 63) 그때 JSON 으로 바꾼다.
로그를 남기는 코드는 안 건드리고 logback 설정만 바뀐다.

프로필별로 형식을 가르지 않는다. **안 돌려본 설정은 쓸 때 깨져 있다.**

## 레벨 — ERROR 는 사람이 개입할 것에만

| 레벨 | 무엇을 찍나 | 예 |
|---|---|---|
| `ERROR` | **사람이 고쳐야 하는 것** | 5xx, 배치 실패, DB 연결 끊김 |
| `WARN` | 지금은 도는데 이상한 것 | 재시도 발생, 응답이 느림, 설정이 기본값으로 떨어짐 |
| `INFO` | 업무가 지나간 흔적 | 주문 생성, 로그인, 4xx |
| `DEBUG` | 개발 중에만 보는 것 | 판정 근거, 쿼리 파라미터 |

**4xx 는 `ERROR` 가 아니다.** 검증 실패도 403 도 서버가 제대로 동작한 결과다.

`ERROR` 를 사람이 개입할 것에만 쓰면 `ERROR` 가 뜨는 순간 볼 가치가 생긴다.
아무 데나 섞으면 아무도 안 본다. 이게 이 절의 전부다.

### 권한 거부는 INFO

화면이 권한에 따라 버튼을 가리는 것은 청크 13b 다. 그 전까지는 **정상적인 거부가 자주 난다.**
`WARN` 으로 올리면 정상 거부가 경고를 채운다.

공격 시도를 가려내는 것은 감사 로그(4b)가 할 일이다. 그쪽은 DB 에 있어서 세고 묶을 수 있다.

## 개인정보는 안 찍는다

**식별자만 찍는다.** 이름·이메일·연락처·주소는 로그에 안 넣는다.
내용이 필요하면 ID 로 DB 를 조회한다.

```
찍는다      user_id=7 order_id=1024 status=paid amount=15000
안 찍는다   email=... name=... phone=... address=...
```

마스킹 방식을 안 쓴 이유가 있다. **금지 목록은 새 필드가 생길 때마다 갱신해야 하고, 빠뜨리면 조용히 샌다.**
애초에 안 찍으면 뺄 것도 샐 것도 없다.

### 객체를 통째로 찍지 않는다

```java
log.info("주문 생성 {}", order);              // 금지. toString 이 전부 뱉는다
log.info("주문 생성 order_id={}", order.id()); // 필요한 필드만 고른다
```

`toString()` 은 나중에 필드가 추가되면 그것도 같이 뱉는다.
로그 코드를 안 고쳤는데 개인정보가 새기 시작한다.

### 요청 본문을 통째로 찍지 않는다

로그인 요청 본문에 비밀번호가 있다. 회원가입 본문에 이름과 연락처가 있다.
본문을 찍는 필터를 만들지 않는다.

예외 스택트레이스에 파라미터가 섞여 나오는 경우가 있다.
예외 메시지에 값을 넣지 말고 식별자만 넣는다.

## 무엇을 찍나

| 자리 | 레벨 | 담는 것 |
|---|---|---|
| 요청 시작·끝 | INFO | 메서드, 경로, 상태 코드, 걸린 시간 |
| 업무 사건 | INFO | 주문 생성, 상태 전이, 결제 결과 — 식별자와 결과만 |
| 권한 판정 | DEBUG | 어느 규칙이 걸렸는지. `D6` 의 판정 근거 문자열 |
| 재시도 | WARN | 어떤 예외로 몇 번째인지 |
| 배치 | INFO 시작·끝 / ERROR 실패 | 기준 시각, 처리 건수 |
| 외부 호출 | INFO | 대상, 걸린 시간, 결과 |

## 지금 안 하는 것

| 항목 | 왜 |
|---|---|
| 로그 수집기 | 청크 63. 서버가 1대라 파일 하나를 보면 된다 |
| 지표 노출 | 청크 62. 볼 화면이 없다 |
| OpenTelemetry | 헤더 형식만 맞춰 두고 미룬다 |
| 로그 무결성 보관 | 규제 대상이 아니다 |
| 이상징후 탐지 | 감사 로그가 쌓인 뒤에 볼 일이다 |

## 이 문서를 고칠 때

새 로그 지점이 생기면 위 「무엇을 찍나」 표에 넣고 레벨을 정한다.
`ERROR` 를 새로 쓸 때는 **사람이 무엇을 해야 하는지** 답할 수 있어야 한다. 답이 없으면 `WARN` 이다.
