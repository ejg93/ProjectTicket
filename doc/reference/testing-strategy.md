# 테스트 전략

> **ProjectShop 에서 이식한 문서다.** 예시·청크 번호(`2g`·`Q36` 등)·쇼핑 도메인(주문·셀러·정산)은 ProjectShop 것이다.
> 티켓 도메인과 Kotlin 에 맞추는 것은 `PLAN.md` 이식 청크 `P` 줄이 한다. 그 청크가 닫히면 이 머리말을 지운다.
> 그때까지는 **원칙은 믿고 예시는 안 믿는다.**

무엇을 어느 층에서 검증하고, 테스트가 무엇에 의존해도 되는지 정한다.

기준 자료는 Test Pyramid(개념)와 Spring Boot·Testcontainers 공식 문서(도구)다.
링크는 `external-references.md` 에 있다.

## 층

| 층 | 무엇을 검증 | 의존 | 바탕 |
|---|---|---|---|
| 단위 | 순수 계산 | 없음 | 없음 |
| 통합 | SQL, 스키마 제약, 스프링 배선, 응답 모양 | 컨테이너 DB | `PostgresTestBase` |
| HTTP | 쿠키 왕복, 세션, 실제 상태 코드, 관통 흐름 | 컨테이너 DB + 서블릿 컨테이너 | `HttpTestBase` |
| 화면 | 오류 이름에 따른 분기, 상태에 따른 표시, 조작 뒤의 갱신 | jsdom | `*.test.tsx`(Vitest + Testing Library) |
| E2E | 프록시·세션 쿠키·CSRF 가 실제로 오가나 | 진짜 브라우저 + 기동한 서버 둘 | `e2e/*.spec.ts`(Playwright) |

**화면 층은 판단을 고정하지 그림을 고정하지 않는다**(`Q9`). 여백과 색은 바뀌라고 있는 것이고
굳히면 고칠 때마다 빨개진다. 여기 거는 것은 **서버 응답을 받아 무엇을 그릴지 고르는 자리**다.

**층 하나가 더 있다 — 두 층에 흩어진 문자열의 대조**(`Q16`). 화면이 `error.slug` 로 분기하고
백엔드가 그 슬러그를 바꾸면 **그 가지는 죽고 사용자는 영영 기본 문구만 본다.** 빌드도 타입 검사도
린트도 통과하고, **화면 테스트조차 같은 틀린 문자열을 쓰면 초록이다.** 그래서 이 대조는
화면이 아니라 **백엔드 테스트**로 둔다 — 실물 목록(`ErrorCode`)이 거기 있어서다.

| 테스트 | 무엇을 대조하나 |
|---|---|
| `ErrorSlugScreenTest` | 화면의 `switch (error.slug)` 가짓수 ⊆ `ErrorCode` 의 슬러그 |
| `ScreenLengthTest` | 화면 입력칸의 `maxLength` = 요청 record 의 `@Size(max)` (`Q27`) |
| `OrderRecordTextTest.StatusLabels` | Java 상태 코드 표 = `order-text.ts` 의 표 |
| `WithdrawalNoticeScreenTest` | 화면의 제한 사유 문구 표 = `WithdrawalRestrictionReason`(`D2` R4) |
| `PasswordHintScreenTest` | 화면의 비밀번호 길이 문구 = `@Password` 의 `@Size` |

**대개 한쪽만 본다.** 화면이 쓰는 것이 서버에 있어야 하고 그 반대는 아니다 — 서버 오류를 화면이
다 나눠 적을 이유가 없고, 안 적은 것은 `default` 로 간다.

**`R4` 만 양쪽을 본다**(`Q20-2`). 화면에만 있는 키는 죽은 가지지만, **실물에만 있는 사유는
고지가 없는 상품**이다 — 제17조제2항 단서가 표시를 제한의 성립 요건으로 두므로 그 자리는
「안 적어도 되는 것」이 아니다. **법이 걸린 대조는 부분집합이 아니라 같음으로 잰다.**

**이 대조들은 화면 소스를 읽으므로 `build.gradle.kts` 의 `comparedScreens` 입력에 걸려 있다.**
안 걸면 화면만 고친 청크에서 `test` 가 `UP-TO-DATE` 로 건너뛴다 — `Q16` 이 그것을 실제로 밟았고,
`OrderRecordTextTest` 는 그때까지 **걸려 있으면서 안 도는 상태**였다.

**`BuildInputTest` 가 그 신고를 막는다**(`Q25`). 저장소가 같은 함정을 **네 번** 밟았고
기록은 재발을 못 막았다. 테스트 소스가 읽는 저장소 밖 경로를 **두 방법으로** 걷어
(소스를 글자로 · `Path` 상수를 리플렉션으로 — 둘이 못 보는 자리가 서로 다르다)
신고 목록이 그것을 덮는지 본다.

**신고 목록은 `build.gradle.kts` 가 시스템 속성으로 내려보낸다.** 그 파일을 글자로 읽지 않는다 —
신고를 쓰는 방식이 하나 늘면(지금도 파일 하나씩과 폴더 통째로가 섞여 있다) 읽는 쪽이 깨진다.

**실행할 때 경로가 정해지는 자리는 둘 다 못 본다.** `StackVersionConsistencyTest` 가 그 하나고
`BuildInputTest.DYNAMIC_ALLOWED` 에 이유와 같이 적혀 있다. 그 수를 박아서 조용히 늘지 않게 한다.

**브라우저가 아니다.** jsdom 이라 프록시·세션 쿠키·CSRF 는 못 밟는다. 그쪽은 `HttpFlowTest` 가
백엔드에서 보고, **화면까지 관통하는 층은 `Q18` 이 세웠다** — 아래 「E2E」.

### E2E — 무엇을 보고 무엇을 안 보나

**조건이 이미 차 있었다**(`Q18`). `D15` 는 「프록시·세션·CSRF 가 얽힌 버그가 한 번이라도 나면」이라고
적어 뒀는데, `13-2` 에서 「로그인이 200 인데 화면이 안 넘어가는」 결함이 났고 그때는 손으로 잡았다.

**스모크 하나뿐이다.** 로그인 → 상품 → 장바구니. 케이스를 늘리는 층이 아니다 —
느리고 정리 비용이 있어서, 여기 있어야 할 이유가 「그 셋이 실제로 오가나」가 아니면 아래로 내린다.

**백엔드를 Playwright 가 안 띄운다.** Gradle 기동이 느려서 밖에서 올린다 —
로컬은 사람이, CI 는 `e2e.yml` 의 앞 step 이(`Q18-1`). `webServer` 로 띄우는 것은 Next 뿐이다.

**`dev` 가 아니라 `start` 로 띄운다.** 개발 서버는 첫 요청에 컴파일해서 타임아웃이 실행마다 흔들린다.

**세운 날 바로 값을 했다.** 담기 버튼을 누르고 결과를 안 기다린 채 `/cart` 로 갔더니 「비었다」가 나왔다 —
요청이 끝나기 전에 화면을 읽은 것이고, **이 층이 아니면 안 보이는 종류다.** 성공 문구를 기다리게 고쳤다.


### 층은 넷인데 레인은 둘이다

**층은 「무엇을 검증하나」로 가르고 레인은 「얼마나 자주 돌 수 있나」로 가른다.**
축이 달라서 표를 따로 둔다.

| 레인 | Gradle 태스크 | 무엇이 도나 | 2026-09-06 |
|---|---|---|---|
| 빠른 것 | `test` | 컨테이너를 안 타는 것 — 단위 층과 문서 대조 | **87개** / 10초 |
| 느린 것 | `integrationTest` | 통합 층 + HTTP 층 | 930개 / 72~78초 |

**어느 레인을 언제 돌리나는 도장이 정한다**(`2z-2`) — 청크를 닫을 땐 빠른 것, push 앞엔 둘 다(`/verify`).
느린 것을 청크마다 돌리면 코드 청크 하루 열여덟에 22분이다.

### 느린 레인을 무엇으로 줄였나

**재고 나서 켰다**(`2i-1`). 스위트 263개의 시간 합이 76초인데 벽시계가 그보다 한참 길었다 —
**차이가 컨테이너·Spring 컨텍스트·JVM 기동**이고, 그 자리를 하나씩 잰 것이 아래다.

| 단계 | 벽시계 | 델타 | 무엇을 했나 |
|---|---|---|---|
| 기준선 | 103초 | — | 컨테이너를 매번 새로 띄운다 |
| 컨테이너 재사용 | 87~91초 | **−14초** | `~/.testcontainers.properties` 에 `testcontainers.reuse.enable=true` |
| 테스트 bcrypt 4 | 72~78초 | **−13초** | `PostgresTestBase.Containers` 의 `@Primary PasswordEncoder` |
| 컨텍스트 합치기 | — | 0 | **할 것이 없었다.** `BackendApplicationTests` 가 이미 `PostgresTestBase` 를 상속한다 |
| fork 2 | 58~72초 | **되돌렸다** | 아래 |
| fork 마다 DB · fork 2 | **81초**(중앙값) | **−12초** | `2i-2`. 아래 「fork 를 못 늘리는 이유」가 풀렸다 |
| 컨텍스트 셋 → 둘 | **53초**(중앙값) | **−2초, 그리고 편차** | `2i-3`. 아래 「컨텍스트 가짓수가 기동 횟수다」 |

**`.withReuse(true)` 는 코드에 이미 있었다.** 안 걸린 것은 로컬 파일의 스위치였고, 로그가
「Reuse was requested but the environment does not support the reuse of containers」로 말하고 있었다.
**켜져 있다고 도는 게 아니다** — 이 저장소가 같은 함정을 밟은 자리가 또 늘었다.

**bcrypt 는 테스트만 4 다.** 운영은 `SecurityConfig` 의 10 그대로고(`D14`), 시드가 심은 해시는
비용이 해시 안에 있어서 여전히 10 으로 검증된다. 빨라지는 것은 픽스처를 만드는 `encode` 뿐이다.

### fork 를 못 늘리는 이유 — 롤백 안 하는 테스트가 DB 를 나눠 쓴다

`maxParallelForks = 2` 로 세 번 돌려 **두 번이 빨갰다.** 깨진 것은 `AuditLogTest` 다.

시도 기록은 `REQUIRES_NEW` 라 **테스트 롤백에 안 쓸린다**(`4b-2` 의 목적이다). 그래서
`PostgresTestBase.purgeCommittedAuditLogs` 가 매 테스트 앞에서 그 표를 비우는데,
**fork 둘이 컨테이너 하나를 나눠 쓰면 한쪽의 비우기가 다른 쪽이 방금 쓴 행을 지운다.**
「허용은 남기지 않는다」가 1을 세고 「거부는 업무가 롤백돼도 남는다」가 0을 센다.

컨테이너를 fork 마다 따로 띄우면 격리는 되지만 재사용이 죽어서 −14초를 도로 내놓는다.
**고치려면 fork 마다 스키마를 나눠야 하고, 그건 이 청크의 범위가 아니다.**

#### `2i-2` 가 그것을 풀었다 — 그리고 이득이 작았다

**컨테이너 하나 안에서 DB 만 가른다.** `PostgresTestBase.Containers` 의 `forkDatabase` 가
`shop_test_<작업트리>_<worker>` 를 만들고, `forkRedis` 가 Redis 논리 DB 를 fork 마다 잡는다.
**Redis 도 같은 사고를 안고 있었다** — `LoginAttemptTest` 가 `login:fail:*` 를 통째로 지우고,
`HttpTestBase` 의 계정 일련번호가 JVM 마다 1부터라 fork 끼리 같은 이메일을 만든다.

| forks | 벽시계(세 판) | 중앙값 |
|---|---|---|
| 1 | 110 · 93 · 67 | **93초** |
| 2 | 83 · 45 · 81 | **81초** |
| 4 | 86 · 84 · 75 | **84초** |

**넷이 둘보다 안 낫다.** 남은 병목이 테스트 실행이 아니라 **fork 마다 새로 뜨는 Spring 컨텍스트**라,
fork 를 늘리면 그 값이 같이 곱해진다. 그래서 기본을 2 로 두고 `-PintegrationForks=N` 으로 다시 잴 수 있게 열어 뒀다.
**편차가 크다**(같은 설정에서 45~83초) — Windows 의 Docker 다. 판을 셋 미만으로 재고 결론 내지 않는다.

**컨텍스트 수는 `2i-3` 이 쟀다** — 아래 「컨텍스트 가짓수가 곧 기동 횟수다」.

**작업트리 사이는 아직 안 갈린다.** Redis 논리 DB 번호가 줄마다 1부터라 병렬 줄 둘이
재사용 컨테이너를 나눠 쓰면 겹친다 — `CLAUDE.md` 「병렬 줄」의 「느린 레인도 한 줄만」이 그대로 남는다.

**표식은 `@Tag("db")` 고 `PostgresTestBase`·`HttpTestBase` 에 달려 있다.**
컨테이너가 그 둘에만 있어서 DB 를 쓰려면 상속해야 하고, **상속하면 태그가 따라온다** —
새 테스트가 표식을 빠뜨릴 자리가 없다. 상속하지 않고 DB 를 쓰면 빠른 레인에서 곧바로 빨개진다.

**`build` 는 두 레인을 다 돈다.** 가른 것은 **도는 자리**지 무엇을 검증하나가 아니라서,
청크를 닫는 기준은 `/verify` 의 빠른 도장이고, `BUILD SUCCESSFUL`(두 레인)은 push 앞이다(`2z-2`).

**빠른 레인이 전체의 9% 다**(`2i-1`·`Q19` 뒤. 69 → 87개). 위 층 표의 「단위」 줄이 얇다는 뜻이고 그것이 실제 모양이다 —
SQL·제약·배선을 보는 코드가 대부분이라 DB 를 탄다. **채우는 것은 다른 일이다**:
`4c-0` 처럼 순수 계산을 떼어내는 작업은 도메인마다 판단이 달라 한 청크에 안 들어간다.
레인을 가른 값은 **그 작업이 얼마나 남았는지가 숫자로 보이게 된 것**이다.

### 컨텍스트 가짓수가 곧 기동 횟수다

**fork 마다 Spring 컨텍스트를 새로 띄운다.** 그래서 **캐시에 몇 가지가 있나**가 그대로
기동 횟수가 된다 — `2i-2` 가 「fork 넷이 되레 늘었다」고 본 값이 이것이다.

**재는 법**: `./gradlew integrationTest -DcontextCacheLog=1` 이 `logging.level.…test.context.cache`
를 **테스트 JVM 에** 걸고 표준 출력을 연다. `-D` 만 주면 Gradle JVM 에 가서 **한 줄도 안 나오고,
못 센 것이 성공처럼 보인다.**

| | 컨텍스트 | 미스 | fork 2 중앙값 |
|---|---|---|---|
| `2i-3` 전 | **3** | 3 | 55초 (55·175·55) |
| `2i-3` 후 | **2** | 2 | **53초** (53·52·54) |

**셋째가 `@AutoConfigureMockMvc` 였다.** 그 표시는 캐시 키의 일부라, 클래스마다 붙이면
**같은 설정인데 컨텍스트가 갈린다** — 78개 중 15개만 붙이고 있었다. `PostgresTestBase` 로
올려서 하나로 모았다. MockMvc 를 안 쓰는 테스트도 그 자동설정을 지고 가지만
**컨텍스트 하나를 통째로 아끼는 값이 더 크다.**

**중앙값보다 편차가 더 줄었다** — 전에는 판마다 55~175초로 튀었고 지금은 52~54초다.
컨텍스트가 적을수록 **어느 fork 가 기동 비용을 무는 경우의 수**가 준다.

**컨텍스트를 안 늘리고 기동을 재는 길이 있다**(`Q47`). `@SpringBootTest` 에 나쁜 값을 `properties` 로 주면 캐시 키가 달라져 **가짓수가 하나 는다** — `ApplicationContextRunner` 는 그 빈만 올린 컨텍스트를 그 자리에서 만들고 버려서 캐시에 안 들어간다. **빠른 레인에서 기동 실패를 잰다.**

**fork 넷은 여전히 안 낫다**(56·55·56, 중앙값 56초). `2i-2` 가 열어 둔 물음의 답이고,
남은 병목이 컨텍스트 가짓수가 아니라 **기동 자체의 값**이라는 뜻이다. 기본은 2 그대로다.

**`@AutoConfigureMockMvc` 를 바탕에 둔 것이 MockMvc 를 권하는 뜻은 아니다** — 아래 「HTTP 층을
왜 따로 두나」가 그대로 산다. 관통하는 흐름은 `HttpTestBase` 가 든다.

**마찰 하나를 내주고 컨텍스트 하나를 샀다**(사용자 선택, 2026-09-11). 전에는 클래스마다 표시를
붙이는 행위가 **최소한의 마찰**이었다 — MockMvc 를 쓰려면 한 줄을 적어야 했다. 지금은
**상속만으로 딸려 오고**, 남은 것은 이 문단(5위)뿐이다. 9차 마무리의 독립 리뷰가 그 자리를 짚었고
**알고 그대로 뒀다**: 맞바꾼 것이 컨텍스트 하나(기동 한 번)이고, 마찰은 **경계를 정한 문서가 있을 때만**
값을 한다 — 그 문서가 아래에 있다.

**되돌릴 때가 오면 이 값이 근거다**: MockMvc 를 쓰는 파일이 늘어 「HTTP 층에 있어야 할 것」이
거기로 새기 시작하면, 표시를 도로 클래스로 내리거나 **쓰는 파일 목록을 테스트로 고정한다**
(`PublicSurfaceTest` 와 같은 모양). 지금은 열다섯이다.

### 화면 도구를 언제 늘리나

**지금은 Vitest + Testing Library + jsdom 이 전부고 그것으로 충분하다**(`Q16`·`Q17`).
늘릴 것마다 **조건을 적어 둔다** — 「나중에」는 처분이 아니다.

| 도구 | 언제 넣나 | 왜 지금은 아닌가 |
|---|---|---|
| `@testing-library/user-event` | **폼 타이핑·탭 순서를 칠 때** | 지금 필요한 조작이 클릭·제출뿐이라 `fireEvent` 로 된다 |
| `axe-core` | ~~화면 테스트가 열 파일을 넘으면~~ **넣었다 — `Q21`**(2026-09-11). `vitest-axe` 를 안 쓴다: 정식 판이 없고 2025-01 이후 안 움직이며 매처 타입이 vitest 4 에 안 붙었다. 위는 우리 헬퍼 열 줄(`src/test/axe.ts`) | `jsx-a11y` 는 정적이라 JSX 만 본다 — 조건부로 생긴 DOM 은 못 본다 |
| MSW | **화면이 클라이언트에서 직접 부르는 곳이 늘면** | 지금은 서버 컴포넌트 위주라 `vi.mock` 이 더 싸다 |
| Playwright(E2E) | ~~조건~~ **`Q18` 이 세웠다** | `13-2` 에서 그 셋이 얽힌 결함이 이미 났다 |

**둘째가 찼고 넣었다** — `Q20` 이 넷을 더해 **열한 파일**이 됐다(2026-09-11). 세는 단위는
`frontend/src/**/*.test.tsx` 고, `.test.ts` 는 DOM 을 안 그려서 `axe` 가 볼 것이 없다.

### axe 가 무엇을 잡고 무엇을 못 잡나

**넣기 전에 쟀다**(`Q21`, `2e-1` 과 같은 방법 — 신호가 얇은 게이트는 켜 둬도 아무것도 안 막는다).

| 컴포넌트 | 위반 | 도는 규칙 | 해당없음 |
|---|---|---|---|
| `LoginForm` | 0 | 12 | 74 |
| `CartLine` | 0 | 12 | 74 |
| `CartLine`(살 수 없음) | 0 | 7 | 79 |
| `PurchasePanel` | 0 | 8 | 78 |

**잎사귀 컴포넌트에서는 규칙 86개 중 8~14% 만 돈다.** 이미지·랜드마크·표가 없어서고,
**색 대비는 jsdom 에 진짜 CSS 가 없어서 아예 안 돈다** — axe 값의 큰 몫이 그것이다.

**부수기가 두 번 엇나갔다.** `role="button"` 오용은 **`jsx-a11y` 가 잡고 axe 는 못 잡았고**,
끊긴 `aria-describedby` 는 axe 기본 규칙에서 위반이 아니다. axe 가 문 것은 라벨 잃은 체크상자인데
**그건 Testing Library 질의가 먼저 깨진다** — 질의를 접근 가능한 이름으로 하는 것 자체가 이미 검사다.

**그래서 이것은 접근성을 보증하는 물건이 아니라 되돌아가는 것을 막는 물건이다.**
보증이 필요해지면 진짜 브라우저를 띄우는 층(E2E)이 그 자리다.

### 화면 테스트가 무엇을 잡나

**「없는 코드」를 고정하는 테스트는 실행 경로까지 가야 한다**(`Q17`). 「확인 대화상자를 안 띄운다」
같은 판단은 **그리기만 보면 그 자리에 코드가 새로 들어와도 안 걸린다** — 실제로 첫 판이 그랬고,
`window.confirm` 을 일부러 넣었는데 초록이었다. 폼을 제출해야 그때부터 잡는다.

**조용히 실패하는 자리가 셋 있다**(`Q17` 에서 다 밟았다).

| 무엇 | 증상 |
|---|---|
| `fireEvent.submit` 을 **버튼**에 건다 | 오류도 경고도 없이 아무 일이 안 일어난다. **폼 요소**에 걸어야 한다 |
| `location.replace` 에 `spyOn` | `Cannot redefine property` — `vi.stubGlobal("location", …)` 로 갈아 끼운다 |
| 조건부 렌더를 안 그리는 쪽으로만 본다 | 「안 그린다」와 「그릴 것이 없다」가 안 갈린다. **남는 것도 같이 본다** |

### HTTP 층을 왜 따로 두나

**MockMvc 는 서블릿 컨테이너를 안 띄운다.** 실제 HTTP 와 갈리는 자리가 세 번 나왔다.

| 청크 | MockMvc | 기동한 서버 |
|---|---|---|
| 5-1 | 403 | 401 |
| 5-2 | 테스트 17개 전부 통과 | **아무도 가입 못 함** |
| 5 | 손대지 않은 테스트 6개가 깨짐 | 정상 |

셋 다 손으로 `curl` 을 걸어서 잡았다. 값을 했지만 자동이 아니라 **다음 청크가 깨뜨려도 모른다.**

### 무엇을 어느 층에

**관통하는 흐름만 HTTP 층에 둔다.** 규칙 하나하나는 통합 층에 둔다.

롤백이 없어서다. 요청이 별도 스레드에서 자기 트랜잭션으로 도니까 `@Transactional` 이 안 먹고,
테스트가 만든 데이터를 직접 지워야 한다. `HttpTestBase` 는 이메일이 `http-test-` 로 시작하는
계정과 그 감사 기록만 지운다 — `audit_log` 는 계정에 외래키가 없어서 따로 지운다.

정리 비용이 붙는 층이므로 케이스를 늘리지 않는다. 여기 있어야 할 이유가
"쿠키·세션·실제 상태 코드" 가 아니면 통합 층으로 내린다.

**`PagingResolverTest` 가 그렇게 내려왔다**(`Q26`). `Q23` 이 HTTP 층에 두면서 댄 근거는
「인자를 만들어 주는 것을 서블릿 컨테이너가 부른다」였는데, 그것은 위 목록에 없다.
**`MockMvc` 가 `WebMvcConfigurer` 를 그대로 태워서** 재는 것이 안 줄었다 —
등록을 빼고 두 층에서 각각 돌려 보니 **같은 하나가 빨갰다.**

**규칙을 못 담은 경우였으면 이 목록을 고쳤을 것이다.** 내려가는지 먼저 재 보고,
안 되면 근거를 목록에 더한다 — 테스트를 그냥 두고 규칙만 어기는 쪽이 제일 나쁘다.

### 무엇을 어디에

**DB 를 안 봐도 답이 나오면 단위다.** 판정 계산이 그렇다.

```java
// 단위 — 규칙을 코드로 만들어 넘긴다
evaluate(List.of(allow("seller", "seller"), deny("seller", "own")), memberOf, userId, target)

// 통합 — DB 에서 규칙을 읽어 오는 것이 검증 대상이다
evaluator.decide(userId, "order", "update_status", target)
```

| 검증 대상 | 층 |
|---|---|
| 판정 규칙의 우선순위, 스코프 해석, 필드 합집합 | 단위 |
| `loadRules` 쿼리가 규칙을 제대로 읽나 | 통합 |
| 트리거·기본키·체크 제약이 잘못된 데이터를 막나 | 통합 |
| 마이그레이션이 순서대로 적용되나 | 통합 |
| API 응답 모양, 상태 코드 | 통합 (청크 7 이후) |

### 새 로직을 짤 때

**계산과 입출력을 갈라 놓으면 단위로 검증할 수 있다.** 청크 4d 에서 `PermissionEvaluator.evaluate` 를
`decide` 에서 떼어 낸 것이 그 예다. 테스트 전용 사본을 만드는 것이 아니라 운영 경로를 나누는 것이다.

가르는 비용이 얻는 것보다 크면 통합으로 둔다. 억지로 나누면 인터페이스만 늘고 읽기 어려워진다.

**로직을 건드리는 청크는 순수 계산을 떼어 단위 층에 둔다**(`Q19`). 뗀 것은 값과 집합을
인자로 받는 static 이고 DB 를 모른다. 인스턴스 메서드는 표에서 읽어 그것을 부르는 껍데기가 된다.

| 뗀 것 | 무엇이 빨라졌나 |
|---|---|
| `PermissionEvaluator.evaluate`(`4c-0`) | 케이스당 0.04초 → 0.0012초. **30배** |
| `BusinessCalendar` 영업일 계산과 `OrderDeadlines`(`Q19`) | 법 기한(`D2` R3·R5)을 컨테이너 없이 본다 |

**안 떼는 것도 근거를 적는다.** 정산 지급액은 SQL 이 줄을 되읽어 합산하도록 일부러 설계했다
(`SettlementService`). 앱이 같은 계산을 한 벌 더 가지면 **계산이 두 벌**이 되고 어긋날 자리가 생긴다 —
떼는 것이 항상 옳은 게 아니라, 얻는 것이 사본의 비용보다 클 때만 뗀다.

## 컨테이너

**테스트가 컨테이너를 직접 띄운다.** `PostgresTestBase` 를 상속하면 붙는다.

손으로 띄운 로컬 컨테이너에 붙이면 세 가지가 깨진다.

- Docker Desktop 을 끄면 테스트가 전부 실패한다
- 앞선 테스트가 남긴 데이터에 결과가 좌우된다
- CI 러너에는 붙을 DB 가 아예 없다. `2c` 의 워크플로가 service 컨테이너를 안 띄우는 이유가 이것이다 —
  테스트가 스스로 띄우므로 러너의 Docker 만 있으면 된다

컨테이너는 테스트마다 새로 뜨지 않는다. `static` 으로 한 번 띄우고 JVM 이 끝날 때까지 쓴다.
Spring 컨텍스트 캐싱과 맞물려서 기동 비용이 전체 실행에 한 번만 든다.

이미지는 `docker-compose.yml` 과 같은 `postgres:17-alpine` 이다. 버전이 갈리면 테스트가 통과해도 운영에서 깨진다.

### Testcontainers 버전을 왜 직접 적나

Boot 의 BOM 이 Testcontainers 를 관리하지 않으므로 `build.gradle.kts` 에서 BOM 을 직접 넣는다.
지금은 `2.0.5` 다.

**2.x 로 올릴 때 셋이 걸렸다**(`2f-2`). 셋 다 **BOM 한 줄로는 안 끝난다.**

| 무엇 | 어떻게 드러나나 |
|---|---|
| 모듈 좌표에 `testcontainers-` 접두어가 붙었다 | `Could not find org.testcontainers:postgresql:` — **버전이 안 붙어서 「없는 모듈」처럼 보인다** |
| `org.testcontainers.containers.PostgreSQLContainer` 가 deprecated 다 | 새 자리는 `org.testcontainers.postgresql` 이다 |
| 새 클래스는 **제네릭이 아니다** | `<?>`·`<>` 를 그대로 두면 `does not take parameters` |

**Boot 의 `@ServiceConnection` 은 새 클래스로도 붙는다** — 문서로 확인한 것이 아니라 돌려서 봤다.

1.x 를 쓰던 동안에는 `1.21.4` 미만이 Docker Engine 29 에서 안 떴다. docker-java 가 API 버전을
1.32 로 잡는데 Docker 29 의 최소 지원이 1.44 라서 `/info` 가 빈 응답과 400 을 줬고,
오류 메시지가 `Could not find a valid Docker environment` 라 원인이 안 드러났다.

## 격리

통합 테스트는 `@Transactional` 로 트랜잭션째 되돌린다. 테스트가 넣은 데이터가 다음 테스트에 안 남는다.
**HTTP 층은 롤백이 안 된다** — 위 「무엇을 어느 층에」를 본다.

**되돌아가는 것은 데이터뿐이다.** 스레드에 남는 것은 따로 비운다.
로그인 컨트롤러가 `SecurityContextHolder` 에 심은 인증이 그렇고, MockMvc 테스트들이
스레드를 나눠 쓰기 때문에 **다음 테스트 클래스가 인증된 상태로 시작한다.**
`PostgresTestBase` 의 `@AfterEach` 가 비운다 — 테스트마다 붙이면 빠뜨리고,
빠뜨렸을 때 깨지는 것이 빠뜨린 클래스가 아니라 남의 클래스다.

마이그레이션이 넣은 역할·권한은 그대로 쓴다. 판정이 **실제 초기 데이터 위에서** 도는지 봐야 해서다.
테스트용 역할을 따로 만들면 운영 데이터와 다른 것을 검증하게 된다.

### 경쟁을 보려면 롤백을 끈다

동시성 테스트는 통합 층에 있으면서 **트랜잭션만 끈다**(`@Transactional(propagation = NOT_SUPPORTED)`).
테스트가 트랜잭션을 열고 있으면 다른 스레드가 그 안의 변경을 못 보고 잠금도 안 걸려서
**경쟁 자체가 안 일어난다.** HTTP 층으로 올리는 것과는 다른 선택이다 — 서블릿이 필요한 게 아니라
커밋이 필요한 것이라 층을 안 옮긴다.

대가는 HTTP 층과 같다. **만든 것을 직접 지운다.** 규칙도 같게 둔다.

| 규칙 | 왜 |
|---|---|
| 계정 이메일·셀러 코드에 접두사를 붙이고 그것만 지운다 | 남의 층이 만든 것을 지우면 그쪽이 조용히 깨진다 |
| **정리를 한 트랜잭션으로 묶는다** | 금액 등식이 지연 트리거라 자식만 지운 상태에서 문장이 커밋되면 터진다 |
| **시작할 때도 한 번 지운다** | 앞선 실행이 죽으면 재사용 컨테이너에 데이터가 남아 다음 실행이 시작도 못 한다 |

**출발선을 맞춘다.** 스레드를 만드는 시간이 주문 하나보다 길어서, 그냥 띄우면
먼저 만들어진 스레드가 혼자 끝낸다. 래치로 다 모아 두고 한 번에 출발시켜야 겹친다.

**막았다는 것만 보지 말고 안 막으면 무엇이 나는지도 본다.** 데드락 회피는 `sku_id` 정렬이
유일한 장치인데, 정렬을 지워도 테스트가 통과할 수 있다 — 조회 쿼리에 `order by` 가 없어서
플래너가 두 요청에 같은 순서를 돌려주면 순환이 안 생긴다. 잠그는 순서를 손으로 엇갈리게 만든
대조 테스트를 같이 둬서 위험이 실재함을 못박는다.

## 스냅샷 테스트

청크 4c 가 쓴다. 케이스가 수백 개라 기대값을 사람이 다 못 쓴다.

```
1. 모든 조합을 돌려 결과를 파일로 쓴다
2. 파일을 커밋한다
3. 이후 테스트는 "지금 결과 == 파일 내용" 만 본다
4. 판정을 고치면 깨진다 → diff 를 보고 의도한 변경인지 판단한다
```

기대값을 적는 것이 아니라 **변화를 감지**하는 방식이다.

### 형식 — 마크다운 표

`permission-rules.md` 의 매트릭스와 같은 모양이라 문서와 대조하기 쉽다.
diff 가 행 단위로 나와서 어느 칸이 바뀌었는지 바로 보인다.

CSV 는 도구로 열기 좋지만 사람이 읽기 어렵고, JSON 은 diff 가 지저분하다.
고정폭 텍스트는 값 하나가 길어지면 정렬이 밀려서 전체가 바뀐 것처럼 보인다.

### 위치

`src/test/resources/snapshots/` 에 둔다. 테스트가 읽고 쓰는 파일이라 테스트 자원이다.

문서에서 참조해야 하면 `doc/` 에서 링크한다. 파일을 두 곳에 두지 않는다.

### 갱신

**명시적 명령으로만 갱신한다.**

```
gradlew test                              비교만 한다. 다르면 실패
gradlew test -Dsnapshot.update=true       파일을 다시 쓴다
```

자동으로 덮어쓰면 테스트가 항상 통과하고, 판정이 바뀐 것을 아무도 모른 채 커밋된다.
그러면 스냅샷을 두는 의미가 없어진다.

갱신한 뒤에는 **`git diff` 를 반드시 본다.** 의도한 칸만 바뀌었는지 확인하는 것이 이 장치의 목적이다.

## 커버리지

**측정만 하고 목표를 두지 않는다.** JaCoCo 리포트는 `gradlew build`(정확히는 `check`)가 만든다.

**`test` 뒤에 딸려 오게 두지 않는다.** 리포트가 두 레인의 결과를 다 읽어야 해서 느린 레인에
매달리는데, `test` 가 리포트를 부르면 **빠른 레인을 돌릴 때마다 컨테이너가 뜬다** —
이름만 빠른 레인이 된다.

```
backend/build/reports/jacoco/test/html/index.html
```

목표 수치를 두면 수치를 채우려는 테스트가 생긴다. 통과 여부만 보고 결과를 안 보는 테스트,
게터를 훑는 테스트 같은 것들이다. 그런 테스트는 커버리지를 올리지만 아무것도 막지 못한다.

대신 **무엇을 검증해야 하는지를 문서로 적는다.** 위 「무엇을 어디에」 표가 그 역할이다.

숫자가 갑자기 떨어지면 뭔가 빠뜨린 것이므로 그때 본다. 기준으로 쓰지 않을 뿐 안 보는 것은 아니다.

## 테스트 이름

한국어로 쓰고 `@DisplayName` 을 붙인다. 실패 목록이 그대로 명세가 된다.

```
PermissionEvaluatorTest > 거부 > 자기가 주문한 자기 셀러 주문은 자기가 못 바꾼다 FAILED
```

메서드 이름은 영어로 둔다. 스택 트레이스와 리포트 파일명에 들어가서다.

## 알려진 구멍은 테스트로 고정한다

지금 통과하는 것이 정상이지만 고쳐야 할 동작은 **그대로 통과하는 테스트**로 남긴다.

`PermissionEvaluatorTest.KnownHole` 이 그 예다. 감사자가 새 권한으로 뚫리는 것을
`isTrue()` 로 고정해 뒀다. 나중에 고치면 이 테스트가 깨지고, 그때 기대값을 뒤집는다.

주석으로만 남기면 잊는다. 테스트로 두면 못 잊는다.

## 응답 표기 훑기는 한 자원에만 둔다

`ResponseEnumCaseTest` 는 **주문 응답에 저장값이 그대로 실린 칸이 있나**를 묻는다.
칸 이름을 안 적고 **저장값 집합을 들고 응답 전체를 훑어서**, 새 칸이 생겨도 등록 없이 걸린다.

**다른 자원에는 같은 훑기를 안 만든다**(2026-08-29, `43a-10` 사용자 선택).

| 무엇 | 어디 |
|---|---|
| 저장값이 열거형을 지나나 | **타입**(1위) — `EnumValue.of(code, X::of)` 가 모르는 값에 터진다 |
| 열거 칸이 그 자리를 안 지나나 | **훑기**(4위) — 주문 자원에만 있다 |

훑기가 잡는 것은 **「헬퍼를 안 부르고 생 문자열을 실은 새 칸」** 하나뿐이다.
그 위험은 자원마다 같지만 **비용도 자원마다 든다** — 응답 하나를 채우려면 그 자원의 fixture가 통째로 필요하다.
주문은 결제·환불·이력·계약을 다 품어서 **한 응답으로 여러 열거형을 지난다**. 다른 자원은 한둘씩이다.

**그래서 훑기를 늘리는 대신 타입을 믿는다.** 열거형이 없어서 훑기가 못 보던 값들은
`43a-8`~`43a-13` 이 전부 열거형으로 세웠고, 그때부터 강제 지점이 4순위가 아니라 1순위다.

**되살릴 조건**: 다른 자원에서 **표기를 빠뜨린 칸이 실제로 한 번 새면** 그 자원에 훑기를 만든다.
`43a-6` 이 주문에서 그렇게 생겼다 — 훑기는 **사고가 난 자리에 세우는 것**이지 미리 까는 것이 아니다.

## 오늘 날짜에 기대지 않는다

**테스트가 달력을 타면 특정 날에만 깨진다.** 그런 실패는 늦게 드러난다 —
CI 가 없어서 아무도 안 돌리는 날이 있고, 돌려도 그날은 초록일 수 있다.

`OrderStatusServiceTest.movesDeadlineOffHolidays` 가 그렇게 됐다.
**기한의 말일이 금요일인 날에만** 깨지고 며칠을 잠복했다(청크 `11-4` 가 고쳤다).

### 시각은 테스트가 정한다

지금을 쓰는 코드는 `Clock` 을 주입받고, **달력에 걸리는 테스트는 고정된 날짜를 넣는다**(사용자 선택).

```java
// 안 한다. 결과가 돌리는 날에 따라 갈린다
service.markDelivered(id);
assertThat(calendar.isBusinessDay(readBack())).isTrue();

// 한다. 언제 돌려도 같은 답이다
assertThat(service.deadlineFrom(LocalDate.of(2026, 8, 10)))
        .isEqualTo(LocalDate.of(2026, 8, 18));
```

**대가를 안다.** `now()` 가 DB 쪽에도 있어서(`delivered_at = now()`) 자바의 `Clock` 을 고정해도
그 컬럼은 서버 시간을 쓴다. 둘을 완전히 맞추려면 DB 의 시간까지 갈아야 하는데 거기까지 안 간다 —
**날짜 계산을 자바 쪽에서 검증하고, DB 시각은 "채워졌나" 만 본다.**

### 어디까지 걸리나

| 테스트 | 날짜를 넣나 |
|---|---|
| 기한·영업일·정산일을 계산한다 | **넣는다.** 계산기를 직접 부르는 단위 테스트로 내린다 |
| 값이 채워졌는지만 본다 | 안 넣는다. `isNotNull()` 은 달력을 안 탄다 |
| 관통 흐름 | 안 넣는다. 흐름이 이어지는지가 목적이다 |

## 이 문서를 고칠 때

새 층이 생기거나(화면 테스트, 계약 테스트) 의존이 늘면 여기에 적는다.
"무엇을 어디에" 표에 없는 종류의 검증이 생기면 그때 한 줄 추가한다.
