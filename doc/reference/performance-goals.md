# 성능 목표 (`D13`)

**무엇을 얼마나 빠르게 해야 하나**를 숫자로 정하고, 그 숫자를 **어떻게 재는지**까지 같이 적는다.
재는 방법이 없는 목표는 목표가 아니라 바람이다.

근거는 31 의 1차 부하(`doc/notes/load-1.md`), 35 의 2차(`doc/notes/load-2.md`), 35b~35d 의 3차(`doc/notes/load-3.md`)다.

## 먼저 — 이 숫자가 무엇의 숫자인가

**노트북 한 대**에서 쟀다. k6·nginx·앱·Postgres·Redis 가 같은 CPU 를 나눠 썼다.
그래서 여기 적는 목표는 「이 서비스가 낼 수 있는 최대」가 아니라 **「이 구성에서 이만큼은 나와야 한다」의 바닥**이다.

바닥을 목표로 두는 이유는 하나다 — **깨졌을 때 무엇이 나빠졌는지 알아채려고** 둔다.
최대를 목표로 두면 기계가 바뀔 때마다 목표가 흔들려서 회귀를 못 본다.

**바닥은 대수마다 다르다.** 1차의 값은 앱이 셋인 줄 알고 쟀지만 실제로는 한 대가 다 받았다(nginx 가 이름을 기동 때 한 번만 풀었다 — 35 가 찾아 고쳤다).
같은 노트북에서 앱을 진짜로 셋으로 나누면 CPU 와 커넥션을 나눠 가져 **모든 값이 나빠진다**. 그래서 목표를 모양별로 나눠 적는다.

**부하 계정의 bcrypt 비용이 3차부터 4 다**(`load/prepare.sql`, 35b). 아래 선점(동시 300)·전체 HTTP·처리량의 값은 비용 10 으로 쟀다 —
그 칸으로 회귀를 보려면 부하 계정을 비용 10 해시로 돌린다(`load-3` 「35b」의 (A10)). 3차의 Docker 할당은 7.75GB 다(1·2차 16.5GB).

## 목표

| 무엇 | 한 대 목표 | 셋(같은 기계) 목표 | 왜 이 값인가 |
|---|---|---|---|
| 좌석 선점 p95 (동시 300) | **≤ 350ms** | **≤ 750ms** | 실측(290ms·621ms)에 20% 여유. 이 값이 대기열이 지키는 상한(`D12`)의 실체다 |
| 좌석 선점 p95 (동시 100) | **≤ 100ms** | **≤ 100ms** | 한가한 시간의 응답. 한 대 47ms·셋 82ms 라 같은 값을 쓴다 — 여기서 늘면 DB 쪽이 변한 것이다 |
| 좌석 선점 p95 (동시 300, 로그인 제외) | 미측정 | **≤ 25ms** | 셋 실측 17ms 에 20% 넘는 여유(`load-3` 「35b」 (B)). 로그인을 측정 밖으로 뺀 판이다. 위 칸들과 같이 **선점 요청 전체**의 값이라 대부분(약 96%)이 409 `duplicate-hold` 거절 경로다 — 이긴 선점만의 값이 아니다 |
| 전체 HTTP p95 (동시 300) | **≤ 900ms** | **≤ 1,500ms** | 로그인(bcrypt **비용 10**)이 섞인 값이다. 비용 4 부하 계정으로는 셋 73ms 다(`load-3` 「35b」 (A)) |
| 처리량 | **≥ 450 req/s** | **≥ 340 req/s** | 각 모양 실측(565·424)의 80%. **대수를 늘리면 이 기계에서는 떨어진다** — 나눈 값은 처리량이 아니라 한 대가 죽어도 사는 것이다 |
| 5xx 비율 | **0** | **0** | 경합·정원 초과·줄 서기는 4xx 다. **5xx 는 우리가 못 한 것**이라 하나도 안 받는다 |
| 대기열 입장 대기 p95 | **≤ 2 × (순번 ÷ R)** | 같다 | 절대값이 아니라 **등식 대비**로 본다 — 300명이면 이론값이 15초 언저리고 실측은 4.0초·2.4초로 그보다 빨랐다. **줄에 선 사람 1만**(셋)은 비율 p95 0.53(`load-3` 「35c」, 순번 100 초과). 이론보다 빠른 것은 판 평균 입장률이 R 의 2.2배여서다 — 앱 셋이 각자 5초마다 돈다는 해석은 추정이고 `35f` 가 확정한다 |
| 대기열 폴링 p95 (줄 1만) | 미측정 | **≤ 140ms** | 셋 실측 116ms 에 20% 여유(`load-3` 「35c」). 폴링 하나가 DB 를 둘 친다(계정 생존 + 회차 상태) |
| 좌석 현황 조회 | **스냅샷 생성 ≤ 판 변경 횟수** | 같다 | 절대 수가 아니라 비율이다. 폴링 수에 비례해 늘면 캐시가 안 먹는 것이다(`D20`). **실측은 100 rps 0.9 · 1,000 rps 19.7 · 5,000 rps 35.8**(셋, `load-3` 「35d」) — 1,000 부터 못 맞춘다. 스냅샷에 락이 없는 탓으로 본다(추정, `35j`). 판 변경이 0 인 구간에도 TTL 10초마다 다시 만든다 — 이 문장이 그 경우를 안 다룬다(`35j` 가 같이 고친다) |
| 좌석 현황 GET p95 (1,000 rps) | 미측정 | **≤ 70ms** | 셋 실측 55ms 에 20% 넘는 여유(`load-3` 「35d」). 5,000 rps 계단은 응답 약 4,180 rps(성공 4,030)에서 연결이 끊겨(그 계단 안 3.6%) 위 5xx 칸을 못 지킨다 — 이 구성(nginx 워커 1)의 천장으로 본다(추정, `35k`) |

**목표를 안 정한 것**: 기동 시간·메모리·DB 커넥션 수. 지금 아픈 자리가 아니고, 아파지면 그때 숫자를 정한다.

## 어떻게 재나

| 무엇 | 어디서 |
|---|---|
| 선점 p95·처리량·5xx | `load/seat-rush.js`(k6). 돌리는 법은 `load/README.md` |
| 대기열 대기 | 같은 스크립트의 `admission_wait_ms`. 줄 1만은 `load/queue-surge.js` 의 `wait_over_expected`(대기 ÷ (순번 ÷ R)) |
| 순수 예매 경로 | `seat-rush.js` 를 `PRELOGIN=1` 로 — 요약의 `http_req_duration{phase:run}` |
| 앱 쪽 같은 시간대 | Grafana 대시보드 `ticket-core`(30) — `seat.hold.latency`·`queue.wait_seconds`·`queue.length`. **대수별 카운터는 여기서 못 본다** — Prometheus 가 `app:8080` 하나를 긁어 셋 중 아무 대나 본다(`35h`) |
| 스냅샷 비율 | `load/seat-poll.js` 계단 + 판 변경은 `seat:ver:{id}` 의 차, 생성은 **앱마다** `/actuator/prometheus` 의 `seat_snapshot_built_total` 합(`load/README.md` 「좌석 폴링」) |
| **대수가 실제로 갈렸나** | 인스턴스마다 `seat.hold.latency` 의 `count`. **한 대에 몰려 있으면 문이 안 나눈 것이다** — 35 가 그렇게 찾았다 |

**부하와 대시보드를 같이 본다.** k6 는 「밖에서 본 시간」이고 지표는 「안에서 본 시간」이라,
둘이 갈리면 그 차이가 곧 네트워크·프록시·큐 대기다.

## 목표를 못 맞추면

| 무엇이 넘었나 | 먼저 볼 것 |
|---|---|
| 선점 p95 | 커넥션 풀(10)과 선점 트랜잭션. `pg_stat_statements` 가 기동 인자로 켜져 있다 |
| 전체 HTTP p95 | 로그인 비중. bcrypt 비용 10 이 응답의 얼마인지 갈라 본다 |
| 처리량 | **먼저 어느 모양인지 본다.** 한 대 값과 셋 값을 섞어 보면 없는 회귀가 보인다 |
| 5xx | **즉시 본다.** 목표가 0 이라 하나만 나와도 원인을 찾는다 |
| 대기열 대기 | 입장 속도 R 이 대수를 따라 오르나 — 락은 겹침만 막고 대마다 5초 주기로 돈다(`35f`, `load-3` 「35c」) |

## 다시 정하는 조건

1. **k6 를 다른 기계로 뺀 뒤** — 지금 숫자는 부하 생성기와 서버가 CPU 를 나눠 쓴 값이다
2. **커넥션 풀을 올린 뒤** — 풀 10 이 병목이면 다른 숫자가 나온다(가상 스레드 측정도 같은 이유로 결론을 못 냈다)
3. ADR 0003 의 입장 속도 R·정원 C 를 바꾸면 — 대기열 목표는 그 값에서 나온다
4. **인스턴스가 다른 기계로 갈린 뒤** — 「셋」 열은 한 노트북에서 JVM 셋이 CPU 를 나눈 값이라 기계가 갈리면 뜻이 달라진다
5. **3차가 드러낸 것을 고친 뒤**(`35f`~`35k`) — 입장 속도·폴링의 DB 조회·스냅샷 락·nginx 연결을 바꾸면 대기열·좌석 현황 칸이 움직인다

**고칠 때는 근거가 된 측정 노트를 같이 적는다**(`load-1`·`load-2`…). 숫자만 바뀌고 근거가 없으면 다음 사람이 되돌릴 수가 없다.
