# 시각 규약

시각을 어디에 어떻게 저장하고, 「관람일 N일 전」을 무엇으로 세고, 만료를 누가 판정하나.

## 저장은 UTC, 판단은 KST

**이 문서에서 제일 중요한 규칙이다.** 둘을 섞으면 하루 경계가 어긋난다.

| 층 | 시간대 | 강제 지점 |
|---|---|---|
| DB 저장 | `timestamptz`. Postgres 가 UTC 로 보관한다. **DB 세션 기본값도 UTC**(`V1`) | 마이그레이션 타입 |
| Kotlin 값 | `OffsetDateTime`. **`LocalDateTime` 금지** | `ArchitectureTest` 규칙(13 이 더한다) — 시간대가 없으면 받는 쪽이 짐작한다 |
| 업무 판단 | `Asia/Seoul`. 「관람일」「당일」「N일 전」은 전부 KST 달력이다 | 아래 「관람일과 구간」. 코드가 `ZoneId` 를 명시한다 |
| API 응답 | UTC, `Z` | `spring.jackson.time-zone: UTC` |
| API 요청 | **오프셋 필수.** 없으면 400 | `OffsetDateTime` 으로 받는다 |
| 로그 | UTC, `Z` | `logback-spring.xml` — 장애 때 로그·DB·API 를 같은 문자열로 맞춘다 |
| 화면 | KST | 화면 코드가 `Asia/Seoul` 로 그린다. 서버는 안 바꾼다 |

`timestamp`(시간대 없음)를 안 쓰는 이유: 같은 값이 서버 설정에 따라 다른 순간을 가리킨다. `timestamptz` 는 순간 하나를 가리키고 표시할 때만 시간대를 입힌다.

**한국은 서머타임이 없다.** `Asia/Seoul` 은 언제나 `+09:00` 이라 하루가 늘 24시간이다 — 경계 계산에 예외가 없다.

## 시계는 DB 다

**만료·마감·타임아웃 판정은 전부 SQL 의 `now()` 로 한다.** 앱 시계를 안 쓴다.

```sql
-- 선점 (13): 만료 시각을 DB 가 계산한다
insert into reservation (…, held_until) values (…, now() + interval '5 minutes');

-- 스윕 (14): 지났는지도 DB 가 판정한다
update reservation set status = 'expired' where status = 'held' and held_until < now();
```

이유는 **인스턴스가 셋이 되기 때문**이다(33). 세 JVM 의 시계가 초 단위로 어긋나면 한 대가 넣은 `held_until` 을 다른 대가 「아직 안 지났다」고 본다.
DB 는 하나고 그 시계도 하나다.

**앱의 `Clock` 은 계산기에만 쓴다** — 수수료 구간(17)·예상 대기(21)처럼 **입력을 받아 답을 내는 순수 함수**가 `Clock` 을 주입받고, 테스트가 고정값을 넣는다(`D8`).
그 함수가 DB 행을 판정하지 않는다.

**앱 시계 호출(`java.time` 의 인자 없는 `now()`·`Clock.system*()`·`System.currentTimeMillis()`)은 `ArchitectureTest.noAppClockReads` 가 막는다**(`G7a`). 주입받은 `Clock` 으로 부르는 `now(clock)` 은 된다. 예외는 넷이고 이름으로 적혀 있다 — 목록이 낡으면 그 테스트가 선다:

| 클래스 | 왜 앱 시계인가 |
|---|---|
| `DemoSeeder` | `local` 시드의 회차 시각을 「지금부터 며칠 뒤」로 놓는다. 판정이 아니다 |
| `HealthController` | 응답에 서버 시각을 싣는다. 판정이 아니다 |
| `AbsoluteSessionTimeoutFilter` | 비교 상대인 세션 생성 시각을 Spring Session 이 앱 시계로 찍는다. DB `now()` 로 재면 두 시계가 섞인다 |
| `MockPaymentGateway` | 가짜 승인번호의 일련 부분. 판정이 아니다 |

**시각 컬럼의 기본값도 `now()`** 다 — `created_at`·`acted_at`·`updated_at`(트리거). 앱이 값을 넣지 않는다.

## 관람일과 구간

취소 수수료(ADR 0003, `D6`)는 **관람일 기준 N일 전**으로 갈린다. 「N일 전」을 정확히 정한다.

| 항목 | 값 |
|---|---|
| 관람일 | `performance.starts_at` 을 **KST 달력일**로 바꾼 날짜 |
| 취소일 | 취소 요청 시각(`now()`)을 KST 달력일로 바꾼 날짜 |
| N일 전 | `관람일 - 취소일` (달력일 차) |
| 당일 | N = 0 |

```
관람일   2026-09-25 19:30 KST
취소     2026-09-15 23:59 KST  → N = 10 → 0%
취소     2026-09-16 00:00 KST  → N = 9  → 10%
취소     2026-09-25 09:00 KST  → N = 0  → 취소 불가
```

**시각이 아니라 날짜로 센다.** 24시간 단위로 세면 저녁 공연과 낮 공연의 구간 경계가 갈리고, 사용자에게 「9일 20시간 전」을 설명할 방법이 없다.
실무(예매처 약관)도 날짜다. 구간 경계는 **KST 자정**이고, 그것이 이 규약의 진짜 시험대다 — `RefundPolicyTest`(17)가 자정 앞뒤 1초를 잰다.

SQL 로 세면:

```sql
(p.starts_at at time zone 'Asia/Seoul')::date - (now() at time zone 'Asia/Seoul')::date
```

`at time zone` 을 빼면 UTC 날짜로 세서 **한국 시각 0시부터 9시 사이의 취소가 전날로 잡힌다.** 그 자리가 이 문서를 쓴 이유다.

**청약철회와의 관계**: 전자상거래법의 7일 청약철회는 「시간이 지나 다시 판매하기 곤란한 재화」에 예외를 두고 공연 티켓이 그에 해당할 수 있다.
**조문은 확인하지 않았다** — `D6` 가 확인하고, 그때까지 우리 수수료 구간이 약관의 계약 조건이다(이용약관 제3조, `V3`).

## 판매 마감은 절대 시각이다

`performance.sales_close_at` 은 달력일이 아니라 **순간**이다. 기본은 `starts_at - 1시간`(ADR 0004)이고 기획사가 바꿀 수 있다.
「마감 지났나」는 `sales_close_at < now()` 하나다 — 날짜 경계가 없다.

`sales_open_at < sales_close_at < starts_at` 을 check 가 든다(16a).

## 자동 전이의 주기와 기준

| 무엇 | 주기 | 판정 | 어디 |
|---|---|---|---|
| 선점 만료 스윕 | 30초 | `held_until < now()` | 14 |
| 결제 타임아웃 | 30초, 같은 스케줄러 | `paying_until < now()` | 16 |
| 회차 종료 | 1분 | `sales_close_at < now()` and `status = 'open'` | 16a |
| 대기열 입장 | 5초 | Redis 시각(`TIME` 명령) — DB 가 아니다. 대기열은 Redis 안에서 닫힌 세계다(`D12`) | 22 |

**주기가 짧을수록 좋은 것이 아니다.** 30초는 「5분 선점이 5분 30초까지 남을 수 있다」는 뜻이고 그 정도는 화면의 카운트다운이 덮는다.
5초로 줄이면 DB 를 6배 더 훑는다. 값은 ADR 0003 이 정했고 31 이 재서 고친다.

## 계산한 기한은 박제한다

기한을 매번 계산하지 않는다. **정해지는 순간 컬럼에 적는다.**

| 값 | 언제 정해지나 | 왜 박제하나 |
|---|---|---|
| `held_until` | 선점 시점 | 선점 시간(5분)을 나중에 바꿔도 이미 잡은 좌석의 만료가 안 흔들린다 |
| `paying_until` | 결제 시작 시점 | 같다 |
| `sales_close_at` | 회차 생성 시점(기본값 계산) | 기본 규칙을 바꿔도 이미 만든 회차가 안 흔들린다 |
| 환불 수수료율·환불액 | 취소 시점 | 구간표를 개정해도 지난 환불이 안 바뀐다. `refund` 행이 율과 액을 든다(`D6`) |
| `price` | 회차 오픈 시점 | `performance_seat` 에 박제. 산 사람과 살 사람의 가격이 갈리면 안 된다(`V6`) |

## 저장 정밀도

Postgres `timestamptz` 는 **마이크로초**까지 담고 나머지를 올린다. Kotlin 의 `OffsetDateTime` 은 나노초다.

```kotlin
// 안 된다. 저장되면 올림돼서 다음 순간이 된다
LocalTime.MAX                    // 23:59:59.999999999

// 한다. 저장 정밀도에 맞춘다
LocalTime.of(23, 59, 59, 999_999_000)
```

지금 이 값을 만드는 자리는 없다 — 기한을 전부 `now() + interval` 로 DB 가 만들기 때문이다. 앱이 「말일 24시」를 만들게 되는 날 이 절이 걸린다.

## 지금 안 하는 것

| 항목 | 왜 |
|---|---|
| 영업일·공휴일 | 우리 기한은 전부 달력일 또는 절대 시각이다. 정산 주기(27, 정산 규약)가 영업일을 쓰면 그때 `holiday` 표를 들인다 |
| 앱 시계 고정으로 만료 테스트 | 시계가 DB 라 안 된다. 만료 테스트는 지난 시각의 행을 직접 넣는다(`D8`) |
| 시간대를 사용자마다 | 한국어·한국 관객 하나다(ADR 0003) |

## 이 문서를 고칠 때

**「관람일과 구간」의 정의를 바꾸면 `D6` 와 `RefundPolicyTest` 가 같이 간다.** 주기 값은 ADR 0003 이 들고 이 문서는 그것을 인용만 한다.
