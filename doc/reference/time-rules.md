# 시각·영업일 규약

> **ProjectShop 에서 이식한 문서다.** 예시·청크 번호(`2g`·`Q36` 등)·쇼핑 도메인(주문·셀러·정산)은 ProjectShop 것이다.
> 티켓 도메인과 Kotlin 에 맞추는 것은 `PLAN.md` 이식 청크 `P` 줄이 한다. 그 청크가 닫히면 이 머리말을 지운다.
> 그때까지는 **원칙은 믿고 예시는 안 믿는다.**

시각을 무엇으로 저장하고 기간을 어떤 단위로 세고 배치를 언제 어느 기준으로 돌리는지 정한다.

공휴일을 테이블에 두는 결정은 ADR 0009 에 있다.

## 저장은 UTC, 판단은 KST

**이 문서에서 제일 중요한 규칙이다.** 둘을 섞으면 하루 경계가 어긋난다.

| 축 | 값 |
|---|---|
| 저장 | `timestamptz`. Postgres 가 UTC 로 보관한다 |
| 업무 판단 | `Asia/Seoul`. "오늘", "이번 달", "말일" 은 전부 KST 기준이다 |

`timestamp` 가 아니라 `timestamptz` 인 이유가 있다.
`timestamp` 는 시간대 정보가 없어서 같은 값이 서버 설정에 따라 다른 순간을 가리킨다.
`timestamptz` 는 순간 하나를 가리키고, 표시할 때만 시간대를 입힌다.

기존 마이그레이션이 전부 `timestamptz` 를 쓰고 있다. 이 문서는 그것을 규칙으로 확정한다.

**Java 쪽은 `OffsetDateTime` 이다.** `LocalDateTime` 을 필드·반환·파라미터에 두면 `ArchitectureTest` 가 빨갛다(`Q32`) —
시간대가 없어서 받는 쪽이 짐작하게 된다. `ZonedDateTime` 은 막지 않는다. 아래 「판단은 KST」가 그것으로 하루 경계를 자른다.

### 표현 — 층마다

**시각이 지나는 층마다 어느 시간대로 적나를 한 자리에 둔다**(`Q35`). 절 넷에 흩어져 있어서 `D5` 가 `+09:00` 을 예로 들어도 아무도 못 봤다.

| 층 | 시간대 | 강제 지점 |
|---|---|---|
| DB 저장 | UTC (`timestamptz`) | 마이그레이션 타입. 새 컬럼은 `Q31` 이 잰다 |
| Java 값 | `OffsetDateTime` — 오프셋은 안 정한다(`now()` 는 JVM, JDBC 는 UTC) | `ArchitectureTest`(`Q32`) — `LocalDateTime` 금지 |
| 업무 판단 | KST (`Asia/Seoul`) | 아래 「판단을 KST 로 하는 이유」. 코드가 `ZoneId` 를 명시한다 |
| **API 응답** | **UTC, `Z`** | `spring.jackson.time-zone: UTC` + `ResponseTimeFormatTest` |
| **API 요청** | **오프셋 필수** — 없으면 400. `Z` 를 권한다 | 아직 시각을 받는 입구가 없다(2026-09-13). 생기면 `@DateTimeFormat(iso = DATE_TIME)` 이 아니라 `OffsetDateTime` 으로 받는다 — `LocalDateTime` 은 위 규칙이 막는다 |
| 날짜 (`YYYY-MM-DD`) | KST 업무일 | 아래 「기간은 날짜로 센다」 |
| **로그** | **UTC, `Z`** | `logback-spring.xml` 의 `%d{…,UTC}Z`. 사용자 결정(2026-09-13) — 읽기는 9시간 더해야 하지만 장애 때 로그·DB·API 를 같은 문자열로 맞춘다 |
| 화면 | KST | `format.ts` 가 `Asia/Seoul` 로 그린다. 서버는 안 바꾼다 |

### 판단을 KST 로 하는 이유

```
주문 시각  2026-08-06 00:30 KST  =  2026-08-05 15:30 UTC

"8월 거래" 인가 "8월 5일 거래" 인가
  UTC 로 세면  → 8월 5일
  KST 로 세면  → 8월 6일
```

셀러와 고객이 사는 날짜가 KST 다. 정산 대상 기간, 파기 기한, 자동 확정일이 전부 여기 걸린다.

집계 쿼리에서 날짜로 자를 때 시간대를 명시한다.

```sql
where created_at >= '2026-08-01 00:00+09' and created_at < '2026-09-01 00:00+09'
```

## API 표기 — UTC

```json
{ "created_at": "2026-08-06T00:55:01Z" }
```

서버·DB·로그가 전부 한 기준이라 비교와 정렬에 변환이 없다.
문자열로 정렬해도 시간 순서와 같다.

한국 시각으로 바꾸는 것은 프론트가 한다. `D5` 가 정한 camelCase 변환 래퍼와 같은 자리다.
그 래퍼를 거치지 않은 시각이 화면에 나오면 UTC 가 그대로 보인다.

`curl` 로 응답을 직접 볼 때는 9시간을 더해서 읽어야 한다. 이건 알고 치르는 대가다.

**설정이 정하고 테스트가 고정한다**(`Q35`). `spring.jackson.time-zone: UTC` 가 직렬화 문맥을 박고 `ResponseTimeFormatTest` 가
`/api/policies/privacy_policy` 의 `effective_at` 이 `Z` 로 끝나는지 본다. **설정 없이도 `Z` 였다** — Jackson 3 가 문맥 시간대를
UTC 로 두고 그쪽으로 맞춘다. 기본값에 안 기댄 이유: 그 설정을 `Asia/Seoul` 로 바꾸니 바로 `+09:00` 이 나갔다.

## 기간은 날짜로 센다

**초일을 안 넣고, 말일 24시에 끝난다.**

```
배송완료  2026-08-06 14:30
  8/7 부터 센다 (초일 불산입)
  7일째가 8/13
  만료는 2026-08-13 23:59:59.999999 KST
```

시각 단위(정확히 168시간)로 안 세는 이유는 **법정 기간이 날짜 단위라서**다.
청약철회는 전자상거래법이 정한 기간이고 민법의 기간 계산을 따른다.
우리가 정하는 기간까지 같은 규칙으로 맞추면 화면에 남은 기간이 한 방식으로만 나온다.

### 저장 정밀도가 마이크로초다

위 `.999999` 는 여섯 자리다. **Postgres `timestamptz` 가 거기까지만 담고 나머지를 올린다.**

자바의 `LocalTime.MAX` 는 아홉 자리(`.999999999`)라 그대로 넣으면 **올림돼서 다음날 `00:00:00`**
이 된다. 시각으로 비교하는 코드는 멀쩡하고 **날짜로 되돌리는 코드만 틀린다.**

```java
// 안 된다. 저장되면 말일이 아니라 말일+1 의 00:00 이다
lastDay.atTime(LocalTime.MAX)

// 한다. 저장 정밀도에 맞춘다
lastDay.atTime(23, 59, 59, 999_999_000)
```

### 24시는 다음 날짜에 속한다

**기간의 끝을 날짜로 되돌리는 자리는 항상 한 칸 밀릴 위험이 있다.**
「말일 24시」와 「말일+1 의 0시」는 같은 순간이고, 그 순간에서 날짜를 뽑으면 말일+1 이 나온다.

| 무엇을 하나 | 안전한가 |
|---|---|
| 기한이 지났나 본다(`isBefore`) | **안전하다.** 순간끼리 비교한다 |
| 남은 날수를 센다 | 안전하다. 차를 구한다 |
| **그 값에서 날짜를 뽑는다** | **위험하다.** 저장 정밀도에 따라 한 칸 밀린다 |

셋째가 필요하면 **저장된 시각이 아니라 계산에 쓴 날짜를 쓴다.**
날짜가 필요한 자리라면 애초에 날짜를 따로 들고 있는 것이 맞다.

`11-4` 가 이 규칙을 코드에 맞췄다 — `OrderStatusService.END_OF_DAY` 가 그 값이다.

### 말일이 쉬는 날이면 다음 영업일

민법이 기간의 말일이 토요일이나 공휴일이면 그 다음날 만료된다고 정한다.
기간이 사용자에게 유리한 쪽으로 늘어난다.

```
만료 예정  2026-08-15 (광복절)
  → 2026-08-17 (토·일을 지나 월요일)
```

**조문 번호는 확인하지 않았다.** 규칙 자체는 실무에서 통용되는 것이고,
법률 검토가 필요해지면 그때 조문을 확인한다. `D2` 의 요건표도 같은 단서를 달았다.

### 계산한 기한은 박제한다

기한을 매번 계산하지 않는다. **정해지는 순간 컬럼에 적는다.**

임시공휴일이 나중에 `holiday` 테이블에 추가되면 매번 계산하는 방식은 이미 지난 기한까지 흔들린다.
사용자에게 "어제까지였는데 오늘 보니 그저께까지였다" 가 생긴다.

박제하는 값과 계산 시점은 이렇다.

| 기한 | 언제 정해지나 |
|---|---|
| 청약철회 만료 | 배송완료 처리 시점 |
| 자동 구매확정 예정일 | 배송완료 처리 시점 |
| 개인정보 파기 예정일 | 탈퇴 처리 시점 |

`D8` 이 수수료율을 주문 시점에 박제한 것과 같은 이유다. 나중에 기준이 바뀌어도 과거가 안 바뀐다.

### 자동 구매확정 기간의 제약

**8일이다**(`D7`). 다만 날수보다 센 제약이 하나 있다 — **청약철회 기간보다 짧으면 안 된다.**
짧으면 아직 반품할 수 있는 주문이 확정돼서 정산 대상에 들어간다.

**말일 보정이 이 제약을 깬다.** 청약철회 말일이 쉬는 날이라 하루 밀리면 8일째와 같은 날이 된다.
날수로만 계산하면 그날 자정에 확정 배치가 도는데, 그때 청약철회는 아직 살아 있다.

```
배송완료 2026-08-10
  청약철회 7일째  8/17 (광복절 대체공휴일) → 8/18
  자동확정 8일째  8/18                      → 같은 날
                                            → 8/19 로 민다
```

**두 기한을 따로 계산하지 않는다.** 자동확정은 `max(8일째, 청약철회 만료 다음날)` 을 구하고
거기서 말일 보정을 건다. `OrderStatusService.autoConfirmLastDay` 가 그것이고 테스트로 고정돼 있다.

## 영업일

`holiday` 테이블에 있는 날과 토·일요일이 영업일이 아니다.

**영업일 계산이 필요한 자리는 둘뿐이다.**

| 자리 | 쓰임 |
|---|---|
| 기한의 말일 보정 | 말일이 쉬는 날이면 다음 영업일로 민다 |
| 정산 지급일 | 아래 참조 |

그 밖의 기간은 전부 역일로 센다. 영업일 계산을 넓게 쓰면 `holiday` 테이블이 비어 있는 구간에서
결과가 조용히 틀린다.

`holiday` 에 데이터가 없는 연도는 **토·일만 걸러진다.** 연말에 다음 해를 채워 넣는 것이 운영 작업이다.

## 정산 지급일 — 매월 10일

| 항목 | 값 |
|---|---|
| 대상 기간 | 전달 1일 00:00 KST ~ 말일 24시 KST |
| 지급일 | 매월 10일 |
| 10일이 쉬는 날이면 | 다음 영업일 |

```
8월 거래  →  9/10 지급
9/10 이 일요일  →  9/11 지급
```

날짜가 고정돼 있어서 셀러가 기억할 수 있다. 영업일 계산은 보정 한 번에만 걸린다.

## 배치 — 04:00 KST, 전날 24시 기준

**실행 시각과 판단 기준을 가른다.**

| 항목 | 값 |
|---|---|
| 실행 | 매일 04:00 KST |
| 판단 기준 시각 | 전날 23:59:59.999999 KST |

```
04:00 실행  →  기준 = 어제 24시
07:00 재실행 →  기준 = 같음  →  결과 같음
```

`now()` 를 그대로 쓰면 배치가 밀리거나 다시 돌 때마다 대상이 달라진다.
기준을 고정하면 **몇 시에 몇 번을 돌리든 결과가 같다.**
`D13` 의 파기 배치(청크 10a)가 "두 번 돌아도 결과가 같아야 한다" 를 요구한다.

04:00 인 이유는 주문이 가장 적은 시간대이고, 자정 직후를 피해서
전날 마지막 주문의 트랜잭션이 확실히 끝난 뒤이기 때문이다.

이 시각에 도는 것

| 배치 | 하는 일 | 청크 |
|---|---|---|
| 자동 구매확정 | 예정일이 지난 주문을 확정한다 | 11 |
| 개인정보 파기 | 파기 예정일이 지난 배송지·계정 정보를 지운다 | 10a |
| 거래기록 파기 | 5년이 지난 주문을 지운다 | 10a |
| 정산 확정 | 매월 지급일에만 돈다 | 17 |

### 예외 — 결제 만료는 5분마다

결제를 안 끝낸 주문이 재고를 잡고 있다(`state-machines.md`). 하루에 한 번 풀면 하루 종일 잡힌다.

이 배치만 04:00 규칙에서 뺀다. 판정이 **경과 시간**이라 고정 기준이 필요 없고,
30분이 지났는지만 보므로 몇 번을 돌리든 결과가 같다.

기준 시각을 고정하는 이유가 재실행 결과를 같게 하는 것이었다.
경과 시간으로 판정하면 그 목적이 다른 방식으로 이미 채워진다.

## 이 문서를 고칠 때

새 기한이 생기면 **어느 시점에 박제하는지**를 위 표에 넣는다.
영업일 계산을 새로 쓰는 자리가 생기면 정말 필요한지 먼저 본다 — 지금 둘뿐인 것이 규칙이다.
