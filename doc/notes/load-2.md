# 부하 2차 — 인스턴스 셋과 대조 (35)

2026-09-18. 스크립트는 1차와 같다(`load/seat-rush.js`). 재는 대상만 달라졌다 — Kafka(28·29)와 좌석 판(D20)이 붙은 뒤의 같은 구성이다.

**2차의 결론은 숫자가 아니라 결함 둘이다.** `D13`(32) 과 대조하려고 돌렸더니 **대조 이전에 구성이 말과 달랐다.**

## 먼저 — 33 의 「인스턴스 셋」은 한 대였다

k6 를 돌린 뒤 인스턴스마다 `seat.hold.latency` 를 읽었더니 **한 대가 전부 받았다**(9,174 : 0 : 0).

| 무엇 | 어떻게 |
|---|---|
| 원인 | `upstream { server app:8080; }`. nginx 는 `server` 의 이름을 **기동 때 한 번** 풀고 그 주소를 계속 쓴다. `--scale app=3` 이 A 레코드 셋을 줘도 첫 하나만 쥔다 |
| 고친 것 | `resolver 127.0.0.11 valid=5s` 를 두고 `proxy_pass` 의 호스트를 **변수로** 적었다. 변수면 매 요청에 다시 푼다 |
| 대가 | `upstream` 블록을 못 써서 keepalive 와 죽은 대 건너뛰기가 없다. 대수가 실제로 느는 것이 먼저라 받아들였다 |
| 확인 | 고친 뒤 같은 부하에서 2,675 : 2,632 : 2,651 |

**1차(31)의 숫자도 한 대의 것이다.** 아래 표에서 1차와 「셋을 띄웠지만 한 대」 열이 거의 같은 것이 그 근거다.
`D13` 이 「인스턴스 셋 + 풀 10 의 바닥」이라고 적은 처리량 목표는 실은 **한 대의 바닥**이었다.

**healthcheck 도 같이 드러났다.** 33 이 `wget` 으로 적었는데 JRE 이미지에 `wget` 도 `curl` 도 없다 —
컨테이너가 계속 `unhealthy` 였고 앱은 멀쩡했다. Dockerfile 에 `curl` 을 넣고 `/actuator/health/readiness` 를 보게 고쳤다.

## 잰 것

기계·Docker 할당·데이터는 1차와 같다(`load-1.md`). 한 노트북 안이라는 사실도 그대로다.

| 시나리오 | VU | 램프/유지 | 1차(한 대) | 2차 — 셋을 띄웠지만 한 대 | 2차 — 진짜 셋 |
|---|---|---|---|---|---|
| A. 첫 물결 | 100 | 20s / 40s | 47ms / 145ms / 334rps | 40ms / 126ms / 326rps | **82ms / 179ms / 321rps** |
| B. 경합 | 300 | 10s / 20s | 290ms / 743ms / 565rps | 231ms / 682ms / 577rps | **621ms / 1,210ms / 424rps** |

세 값은 차례로 `hold_latency_ms` p95 · `http_req_duration` p95 · 처리량이다. 좌석은 A 가 100석, B 가 300석으로 세 회차 모두 같다.

| 지표 | A(셋) | B(셋) |
|---|---|---|
| `admission_wait_ms` p95 | 68ms | 2,380ms |
| `http_req_failed` | 19.56% | 17.91% |
| 5xx | 0 | 0 |

`http_req_failed` 는 전부 409 다(`seats_taken` 수와 정확히 같다). 앱 쪽 `http_server_requests` 에도 5xx 가 한 건도 없다 —
k6 가 밖에서 본 것과 앱이 안에서 센 것이 같다.

## 읽은 것 — 셋이 한 대보다 느리다

셋으로 나눈 뒤 **모든 지연이 나빠졌고 처리량은 26% 떨어졌다**(577 → 424 rps). 기계가 하나라서다:
k6·nginx·Postgres·Redis 가 쓰던 CPU 를 JVM 셋이 나눠 가졌고, DB 커넥션도 10 이 아니라 30 이 됐다.

**이것이 33 을 되돌릴 근거는 아니다.** 인스턴스를 나눈 값은 처리량이 아니라 **한 대가 죽어도 서비스가 사는 것**이고,
그것은 세션을 Redis 로 뺀 것(20a)·스케줄러 락(33)·아웃박스 릴레이가 같이 만든 성질이다.
대수를 늘려 처리량이 느는 모양은 **기계가 갈라진 뒤에** 보인다 — 지금 숫자는 그 전 단계다.

같은 부하에서 `queue.admitted` 가 826 : 203 : 71 로 갈렸다. 셋이 동시에 입장을 돌렸으면 셋이 비슷했을 것이라,
이 치우침이 곧 **스케줄러 락이 한 번에 한 대만 돌렸다**는 증거다(33).

## `D13` 을 어떻게 했나

숫자를 느슨하게 안 고쳤다. 목표는 회귀를 보려고 두는 것이라 느슨해지면 볼 것이 없어진다.
대신 **목표가 어느 모양의 것인지**를 `D13` 에 적었다 — 지금 값은 「한 대」의 바닥이고, 「같은 기계에 셋」은 별도 열이다.
