# 부하 6차 — 늘어난 대의 기동을 가른다(53a)

`load-5` 와 같은 판(`scripts/k8s-hpa-test.sh`, 줄 1만 → 선점)을 readiness `initialDelaySeconds: 20` 을 걷은 차트로 한 번 더 쳤다.
새 파드의 「생성 → Ready」를 「생성 → Started」(컨테이너 기동 + JVM·Spring 기동)와 「Started → Ready」(탐침 대기)로 가른다. 조건은 `load-5` 「조건」과 같다 — 다른 것은 차트의 readiness 지연뿐이다.

## 읽은 것

**지연을 걷어도 Ready 가 안 빨라졌다.** 늘어난 파드는 JVM 기동만 29~34초다 — CPU 를 6대·DB·k6 가 나누는 판 한가운데서 뜬다. 지연 20초는 이 기동과 겹쳐서 안 보였다.
그래서 설계의 「readiness 지연은 startupProbe 성공 뒤부터 센다」는 이 판과 안 맞는다 — 그 뜻이면 `load-5` 의 Ready 는 기동 + 20초 이상이어야 한다. 실측을 믿고 `stack.md` 「k8s 앱 파드의 기동」에 적었다.
지연은 그래도 걷은 채 둔다. 기동이 20초보다 짧아지면(`53b`) 그 20초가 Ready 의 바닥이 된다.

**Ready 를 정하는 것은 JVM 기동이다.** Started → Ready 는 5초 안이다. 부하가 낮을 때(미리 로그인 중) 18.7초, 판 한가운데서 29~34초 — 같은 이미지가 CPU 경합으로 두 배 가까이 늘어난다.
`53b` 의 조건(생성 → Started ≥ 10초)이 찼다.

`load-5` 보다 폴링·선점 p95 가 높고 Ready 가 늦은 것은 이 판이 5대에서 한 번 더 걸음을 디딘 것(3 → 5 → 6)과 겹친다. 판 하나라 차이를 지연 탓으로 돌리지 않는다.
