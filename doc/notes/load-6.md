# 부하 6차 — 늘어난 대의 기동을 가르고 CDS 로 줄인다(53a·53b)

`load-5` 와 같은 판(`scripts/k8s-hpa-test.sh`, 줄 1만 → 선점)을 두 번 더 쳤다. `53a` 는 readiness `initialDelaySeconds: 20` 을 걷은 차트, `53b` 는 거기에 CDS 아카이브를 구운 이미지(`backend/Dockerfile`).
새 파드의 「생성 → Ready」를 「생성 → Started」(컨테이너 기동 + JVM·Spring 기동)와 「Started → Ready」(탐침 대기)로 가른다. 조건은 `load-5` 「조건」과 같다. 판마다 클러스터를 새로 올렸다.

## 읽은 것

**Ready 를 정하는 것은 JVM 기동이다.** Started → Ready 는 세 판 다 5초 안이다. 같은 이미지가 부하가 낮을 때 18.7초, 판 한가운데서 29~34초 — CPU 경합으로 두 배 가까이 늘어난다.

**지연을 걷는 것만으로는 Ready 가 안 빨라졌다**(`53a`). 늘어난 파드의 JVM 기동이 20초를 넘어서 지연이 기동과 겹쳐 안 보였다.
그래서 설계의 「readiness 지연은 startupProbe 성공 뒤부터 센다」는 이 판과 안 맞는다 — 그 뜻이면 `load-5` 의 Ready 는 기동 + 20초 이상이어야 한다. 실측을 믿고 `stack.md` 「k8s 앱 파드의 기동」에 적었다.
지연을 걷은 값은 `53b` 에서 나왔다 — CDS 로 기동이 14~15초가 되자 Ready 가 20~21초다. 지연 20초를 그대로 뒀으면 바닥이 22초 남짓이었다.

**CDS 가 생성 → Started 를 절반으로 줄였다**(31.5~36.5 → 16.3~17.5초, −44% 이상 — `53b` 닫힘 20%). 클래스를 읽고 검증하는 몫이 아카이브로 가서 CPU 경합에도 덜 늘어난다.
폴링·선점 p95 가 `53a` 보다 낮은 것은 새 대가 15초 일찍 받기 시작한 것과 겹치지만 판 하나라 그 탓으로만 돌리지 않는다 — `load-5` 두 판도 226·167 로 갈렸다. 폴링 p95 는 여전히 `D13` 칸(140ms)을 넘는다(`load-5` 「읽은 것」과 같은 이유).
