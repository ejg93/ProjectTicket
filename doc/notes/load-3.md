절마다 그 행이 잰 것이고, `D13`(`35e`)이 이 노트를 근거로 목표를 고친다.

## 35b — 순수 예매 경로

같은 모양(앱 셋, VU 300, 램프 10초 / 유지 20초, `seat-rush.js`)에서 로그인만 바꿨다. 판 사이에 좌석·Redis 를 되돌렸다(`README.md`).
(A10) 은 같은 날 같은 구성에서 부하 계정 300 의 해시만 데모 계정의 비용 10 으로 바꾼 판이다 — 2차와의 차를 bcrypt 와 나머지로 가르려고.

| 판 | bcrypt | 로그인 | 선점 p95 | HTTP p95 | 처리량 | 반복률 | 5xx | 입장 대기 p95 |
|---|---|---|---|---|---|---|---|---|
| `load-2` B(2026-09) | 10 | 반복마다 | 621ms | 1,210ms | 424 rps | — | 0 | 2,380ms |
| (A10) | 10 | 반복마다 | 292ms | 670ms | 559 rps | 108 회/초 | 0 | 4,020ms |
| (A) | 4 | 반복마다 | 85ms | 73ms | 865 rps | 170 회/초 | 0 | 2,040ms |
| (B) | 4 | 측정 밖(`PRELOGIN=1`, 300개 6초) | 17ms | 15ms | 363 rps | 164 회/초 | 0 | 2,010ms |

- 판마다 `seats_won` 300 — 계정 300 이 한 석씩 잡고 나머지 반복은 409 `duplicate-hold`(31 부터 같은 모양).
- (B) 의 처리량이 낮은 것은 반복당 요청이 줄어서다(로그인·CSRF GET 셋이 빠진다). 반복률은 (A) 와 비슷하다 — 처리량은 이 비교의 축이 아니다.

**읽은 것.** 같은 날 비용만 바꾼 (A10)→(A) 에서 선점 p95 가 292 → 85ms, HTTP p95 가 670 → 73ms 다. 로그인이 쥔 CPU 를 같은 기계의 선점이 기다렸다고 본다(추정 — 이 판은 CPU 를 안 쟀다).
(A)→(B) 로 로그인 왕복까지 빼면 선점 요청 p95 가 17ms 다. **다만 이 값의 대부분은 거절 경로다** — 판마다 이긴 선점은 300 이고 나머지(약 96%)는
계정당 한 석 제한의 409 `duplicate-hold` 라 `SeatHoldService.insertReservation` 에서 끊겨 조건부 UPDATE 까지 안 간다. 이긴 선점만의 값은 안 갈랐다 — 1·2차의 선점 p95 도 같은 섞임이다.
`load-2` B → (A10)(621 → 292ms)은 같은 비용 10 인데 반으로 줄었다 — 그 사이 번들 여럿의 코드와 Docker 메모리(7.75 vs 16.5GB)가 같이 바뀌어
이 노트로는 원인을 못 가른다. 입장 대기 p95 는 비용 4 판에서 2초 언저리고 (A10) 에서 4초다 — 입장 주기(5초)의 몇 번째 틱에 걸리나로 정해지는 값이라
로그인이 느린 판에서 한 틱 밀린 것으로 본다(추정 — 대기는 진입 때부터 재서 로그인 시간은 안 든다. 왜 밀리는지는 안 갈랐다).

## 35c — 대기열 진입 1만

**줄에 선 사람 1만**(사용자 결정) — 계정·세션 1만을 VU 500 이 20 개씩 들고 2초마다 순번을 묻는다. 입장하면 그 자리에서 `DELETE` 로 반납한다.
세션은 `prelogin.js` 가 먼저 한 판으로 만들었다(1만 개 188초, 실패 0). 램프 60초 동안 1만이 줄에 서고, 유지 600초.

| 무엇 | 값 |
|---|---|
| 진입 · 반납 · 빠짐 | 10,000 · 9,992 · 8 — 반납 + 빠짐 = 진입 = 계정 수 1만(남은 줄 0). 반납 `DELETE` 는 전부 204 였다(`check` 실패 0) |
| 줄 최대 | 진입 때 본 순번 최대 6,765(k6 `queue_rank`). 1만이 다 서기 전에 입장이 앞을 덜어서 1만에 안 닿는다 |
| 입장 대기 | p50 77초 · p95 155초 · 최대 165초 |
| 등식 비율(대기 ÷ (순번 ÷ R), 순번 100 초과만) | p50 0.46 · p95 0.53 · 최대 1.01 — **목표 「≤ 2」를 넉넉히 섰고, 이론의 절반이다** |
| 전부 입장까지 | 약 225초(줄이 +196초에 1,165명, +255초에 0) — 이론(R=20) 은 500초 |
| 폴링 GET p95 · 요청 p95 | 116ms · 115ms. **바퀴 간격은 안 쟀다** — 바퀴 하나가 계정 20 × 요청이라 p95 지연이면 2.3초로 2초를 넘을 수 있다(추정). 스크립트에 `poll_round_ms` 를 더했다 — `35g` 의 재측정이 잰다 |
| 요청률 | 활성 구간(약 225초) 평균 약 1,800 rps, 전체 평균 609 rps. **목표 5,000 rps 는 못 냈다** — 1만이 동시에 줄에 있던 순간이 없다 |
| 5xx | 0(요청 409,318) |
| CPU 정점(+76초) | 앱 대당 약 350% · DB 145% · Redis 61% · nginx 84% · k6 159%. 앱 메모리 대당 1.2GB |
| Redis CPU | 673초 동안 약 136초(평균 20%) |
| 대수별 입장 | 3,054 : 2,885 : 4,261(각 앱의 `queue_admitted_total`, 시험판 200 포함). 같은 구간 Prometheus 의 `increase(queue_admitted_total)` 는 2,947 이었다 — 수집 대상이 하나라서다(`35h`) |
| 천장 | 이 판에서는 안 닿았다 — 오류 0, 폴링 p95 116ms. 요청률이 목표의 절반 아래라 천장을 말할 근거가 없다 |
| 못 잰 것 | Redis `DBSIZE`·세션 수(행 ④) — `35g` 의 재측정이 같이 적는다 |

**읽은 것 — 입장 속도가 R 보다 빠르다.** `D12` 의 R 은 「5초마다 100명 = 20명/초」인데 판 전체 평균은 약 44명/초다(1만 ÷ 약 225초).
코드는 이것과 맞는다 — `AdmissionScheduler` 가 대마다 `fixedDelay 5s` 로 돌고 락(`SchedulerLock`)은 쥔 뒤 놓아서 **겹침만** 막는다.
그러면 셋이 서로 다른 위상으로 5초에 많게는 세 번 입장을 돌린다. **다만 이 판의 자료로는 그 해석이 확정되지 않는다(추정)** —
대수별 입장이 고르게 갈린 것은 락이 대를 번갈아 잡는 경우(합이 R)와도 같고, 꼬리 구간(+196초 1,165명 → +255초 0)은 약 20명/초로 R 한 배다.
위상에 따라 1~3배로 흔들린다는 쪽이 자료와 맞는다. 2차의 826 : 203 : 71 을 다시 읽는 것, HPA 6대(`38`)면 최대 약 120명/초라는 것도 같은 추정 위다.
**확정하는 시험이 `35f` 다** — 앱 셋이 같은 5초에 입장을 돌릴 때 합이 `BATCH_SIZE` 를 넘나.

**읽은 것 — 빠짐 8 은 경합으로 본다(추정).** `QueueService.position` 은 토큰을 먼저 보고(`tokenFor`), 없으면 줄 순번(`ZRANK`)을 따로 읽는다 —
두 읽기 사이에 입장 Lua 가 끼면 토큰도 없고 줄에도 없어 404 `not-in-queue` 다. 코드상 가능한 길이고, 하트비트(90초)가 끊길 만큼 바퀴가 길었다는 근거는 없다.
다만 404 시각을 입장 시각과 맞춰 보지 않았고 바퀴 간격도 안 쟀다 — `35g` 의 시험이 확정한다. 맞다면 화면은 이것을 「대기열에서 빠졌습니다」로 읽는다(`43`).

**도구가 먼저 선 자리.** 첫 판은 `setup()` 이 세션 1만을 돌려주게 했는데 k6 는 그 값을 VU 마다 복사한다(k6 의 동작).
그 판에서 Docker VM(7.75GB)이 메모리 부족으로 굳었다 — `docker ps` 가 답을 안 해서 Docker Desktop 을 다시 켰다. 같은 때 앱 셋도 상한 없이 메모리를 키우고 있어서
(다음 판 정점 대당 1.2GB, `35i`) **어느 쪽이 결정타였는지는 못 갈랐다** — VM 이 굳어 그 순간의 메모리를 못 읽었다.
그래서 미리 로그인을 따로 한 판으로 빼고(`prelogin.js` → `load/results/sessions.json`), 측정 판은 `SharedArray` 로 한 벌만 읽는다.
k6 컨테이너에는 `--memory=2g` 를 건다 — 넘치면 VM 이 아니라 k6 만 죽는다. 이번 판 k6 는 최대 336MB 였다.

**신규 행 후보(`35e` 가 세운다)**: ① 입장 속도를 대수와 무관하게 — 마지막 입장 시각을 Redis 에 두고 5초 안이면 건너뛴다 ② 폴링 GET 의 토큰·순번을 한 Lua 로 읽는다 ③ Prometheus 가 `app:8080` 하나를 긁어 셋 중 아무 대나 본다(`docker/prometheus/prometheus.yml`) — 대수별 카운터를 못 가른다. 이 노트의 대수별 값은 앱마다 `/actuator/prometheus` 를 직접 읽었다 ④ compose 의 앱에 메모리 상한이 없다 — JVM 이 VM 의 70% 까지 크려 한다(`MaxRAMPercentage=70`), 셋이면 VM 을 넘는다.

## 35d — 좌석 폴링 스냅샷 비율

`seat-poll.js` 가 공개 GET `…/seats` 를 계단(100·1,000·5,000 rps, 각 60초, 사이 10초)으로 치고, VU 마다 받은 ETag 로 `If-None-Match` 를 싣는다.
같은 시간에 `seat-rush.js`(`ROTATE=1`, VU 10, 계정 1천 미리 로그인)가 선점으로 판을 바꾼다. 판 변경은 `seat:ver:1` 의 차,
스냅샷 생성은 **앱마다** `/actuator/prometheus` 의 `seat_snapshot_built_total` 합 — 5초 표본에서 계단 구간만 잘랐다.

| 계단 | 실측 rps | 200 : 304 | p95 | 판 변경 | 스냅샷 생성 | 비율(생성 ÷ 변경) |
|---|---|---|---|---|---|---|
| 100 | 100 | 29% : 71% | 7ms | 172 | 153 | **0.9** |
| 1,000 | 1,000 | 69% : 31% | 55ms | 381 | 7,488 | **19.7** |
| 5,000 | 응답 약 4,180(성공 4,030, 놓친 반복 49,063) | 4% : 96% | 167ms | 17 | 609 | **35.8** |

- 연결 오류 9,094 — 전부 5,000 계단의 `connection reset by peer`·`EOF`. 그 계단 안에서 3.6%(판 전체로는 2.9%). nginx 로그에 연결 부족 문구는 없어
  `worker_connections 1024` 와 accept 백로그 중 무엇인지는 못 갈랐고, k6 도 VU 상한(2,000)에 막혀 반복 49,063 을 놓쳤다.
  **이 구성(nginx 워커 1 · k6 VU 2,000)의 공개 GET 천장이 4,000 rps 언저리다**(추정 — 원인을 못 갈랐다).
- 셋째 계단의 판 변경 17 은 쓰는 쪽의 이긴 선점이 줄어서다. 쓰는 쪽도 nginx 끊김을 맞았다(실패 83). 좌석이 바닥난 탓은 아니다 — 계단 셋 동안 789석을 잡았고
  `ROTATE` 의 좌석 식은 VU 끼리 안 겹친다. 왜 줄었는지는 안 갈랐다.
- **못 잰 것**: 계단마다의 앱·Redis CPU(행 ④) — `35j` 의 재측정이 같이 적는다.

**읽은 것 — 판이 바뀌는 동안 스냅샷이 폴링 수를 따라 는다.** 100 rps 에서는 판 하나에 스냅샷이 한 번 꼴(0.9)로 목표를 지킨다.
1,000 rps 에서는 판 하나에 약 20번 만든다 — **`D13` 이 「캐시가 안 먹는 것」이라 부른 모양이다.** 원인은 스냅샷에 락이 없어서
(`D20` 「동시에 여럿이 만들 수 있다」) 판이 바뀐 직후 첫 생성이 끝나기 전에 온 요청이 각자 만드는 것으로 본다(추정 — 생성 시간도 동시 생성 수도 안 쟀다).
`seat-poll.js` 는 도달률 실행기라 VU 하나의 요청 간격이 「VU 수 ÷ rps」다(1,000 계단에서 약 0.3초). 그 간격 안에 판이 바뀌면 VU 가 든 ETag 가 낡아 200 이다 —
판이 초당 6번 꼴로 바뀐 1,000 계단에서 200 이 69% 다.
화면의 좌석도가 델타(`/seats/changes?since=`)를 쓰는 이유가 이것인데, 이 측정은 전체 GET 만 쳤다.

**첫 판은 버렸다.** 쓰는 쪽이 좌석을 `__VU` 로만 골라 계정을 돌려도 VU 마다 같은 좌석을 쳤다 — 선점 10 뒤로 판이 한 번도 안 바뀌었다.
그 판에서도 스냅샷은 셋째 계단에서 6번 늘었다 — TTL 10초가 지나면 판이 그대로여도 새 VU 의 첫 요청(ETag 없음)이 다시 만든다.
**판 변경이 0 이면 비율은 정의가 안 되지만 생성은 0 이 아니다** — 목표 문장이 이 경우를 안 다룬다.

**신규 행 후보(`35e` 가 세운다)**: ⑤ 스냅샷 생성을 판마다 하나로(single-flight — `SET NX` 락이나 앱 안 잠금) ⑥ 공개 GET 의 연결 천장 — nginx `worker_processes`·`worker_connections`·`listen backlog` 와 upstream keepalive.

## 35d-재 — 고친 뒤 좌석 폴링(35j·35k)

같은 날 같은 구성에서 `35d` 를 다시 돌렸다. 바뀐 것 둘 — 같은 대 안에서 판마다 스냅샷 하나(`35j`) · nginx 워커 4 × 연결 4,096(`35k`).
k6 는 `MAX_VUS=4000`·`--memory=3g` 로 한 번 더 줬다. 쓰는 쪽은 그대로 VU 10 + `ROTATE`(사용자 확인). 두 판을 돌렸다 —
첫 판은 CPU 표본이 첫 계단에서 끝나(`docker stats` 한 번이 3초쯤) 시각 기준 고리로 둘째 판을 다시 쟀다. 비율은 두 판이 같은 모양이다.

| 계단 | 응답 rps | 200 : 304 | p95 | 판 변경 | 스냅샷 생성 | 비율 | 고치기 전 비율 |

| 100 | 100 | 26% : 74% | 15ms | 179 | 239 | **1.34**(첫 판 1.34) | 0.9 |
| 1,000 | 1,000 | 36% : 64% | 21ms | 274 | 777 | **2.84**(첫 판 2.79) | 19.7 |

- 셋째 계단의 CPU 정점: 앱 374~452% × 3 · k6 384% · nginx 181% · DB 177% · Redis 49% — 합이 22 vCPU 중 약 20 이다.

**읽은 것.** 비율이 셋 다 대수(3) 이하다 — `D13` 「생성 ≤ 대수 × 판 변경」을 지킨다(`35j`). 같은 대 안의 중복은 시험이 0 으로 잰다

**한 노트북에서 공개 GET 은 약 4,500 rps 에서 CPU 가 찬다.** 그 위는 k6 를 다른 기계로 뺀 뒤에야 잴 수 있다(`D13` 「다시 정하는 조건」 1).
