## 35b — 순수 예매 경로

같은 모양(앱 셋, VU 300, 램프 10초 / 유지 20초, `seat-rush.js`)에서 로그인만 바꿨다. 판 사이에 좌석·Redis 를 되돌렸다(`README.md`).
(A10) 은 같은 날 같은 구성에서 부하 계정 300 의 해시만 데모 계정의 비용 10 으로 바꾼 판이다 — 2차와의 차를 bcrypt 와 나머지로 가르려고.

| 판 | bcrypt | 로그인 | 선점 p95 | HTTP p95 | 처리량 | 반복률 | 5xx | 입장 대기 p95 |
|---|---|---|---|---|---|---|---|---|
| `load-2` B(2026-09) | 10 | 반복마다 | 621ms | 1,210ms | 424 rps | — | 0 | 2,380ms |
| (A10) | 10 | 반복마다 | 292ms | 670ms | 559 rps | 108 회/초 | 0 | 4,020ms |
| (A) | 4 | 반복마다 | 85ms | 73ms | 865 rps | 170 회/초 | 0 | 2,040ms |
| (B) | 4 | 측정 밖(`PRELOGIN=1`, 300개 6초) | 17ms | 15ms | 363 rps | 164 회/초 | 0 | 2,010ms |

- 판마다 `seats_won` 300 — 계정 300 이 한 석씩 잡고 나머지 반복은 409 `duplicate-hold`(31 부터 같은 모양).
- (B) 의 처리량이 낮은 것은 반복당 요청이 줄어서다(로그인·CSRF GET 셋이 빠진다). 반복률은 (A) 와 비슷하다 — 처리량은 이 비교의 축이 아니다.

**읽은 것.** 같은 날 비용만 바꾼 (A10)→(A) 에서 선점 p95 가 292 → 85ms, HTTP p95 가 670 → 73ms 다 — **로그인이 쥔 CPU 를 같은 기계의 선점이 기다렸다.**
(A)→(B) 로 로그인 왕복까지 빼면 선점 p95 가 17ms — **선점 경로 자체(조건부 UPDATE + 관문 Redis)는 300 동시에서 20ms 안이다.**
`load-2` B → (A10)(621 → 292ms)은 같은 비용 10 인데 반으로 줄었다 — 그 사이 번들 여럿의 코드와 Docker 메모리(7.75 vs 16.5GB)가 같이 바뀌어
이 노트로는 원인을 못 가른다. 입장 대기 p95 는 비용 4 판에서 2초 언저리고 (A10) 에서 4초다 — 입장 주기(5초)의 몇 번째 틱에 걸리나로 정해지는 값이라
로그인이 느리면 줄에 늦게 서서 한 틱 밀린다.

## 35c — 대기열 진입 1만

**줄에 선 사람 1만**(사용자 결정) — 계정·세션 1만을 VU 500 이 20 개씩 들고 2초마다 순번을 묻는다. 입장하면 그 자리에서 `DELETE` 로 반납한다.
세션은 `prelogin.js` 가 먼저 한 판으로 만들었다(1만 개 188초, 실패 0). 램프 60초 동안 1만이 줄에 서고, 유지 600초.

| 무엇 | 값 |
|---|---|
| 진입 · 반납 · 빠짐 | 10,000 · 9,992 · 8 — 셋의 합이 1만이다(남은 줄 0) |
| 줄 최대 | 진입 때 본 순번 최대 6,765(k6 `queue_rank`). 1만이 다 서기 전에 입장이 앞을 덜어서 1만에 안 닿는다 |
| 입장 대기 | p50 77초 · p95 155초 · 최대 165초 |
| 등식 비율(대기 ÷ (순번 ÷ R), 순번 100 초과만) | p50 0.46 · p95 0.53 · 최대 1.01 — **목표 「≤ 2」를 넉넉히 섰고, 이론의 절반이다** |
| 전부 입장까지 | 약 225초(줄이 +196초에 1,165명, +255초에 0) — 이론(R=20) 은 500초 |
| 폴링 GET p95 · 요청 p95 | 116ms · 115ms. 2초 간격이 지켜졌다 |
| 요청률 | 활성 구간(약 225초) 평균 약 1,800 rps, 전체 평균 609 rps. **목표 5,000 rps 는 못 냈다** — 1만이 동시에 줄에 있던 순간이 없다 |
| 5xx | 0(요청 409,318) |
| CPU 정점(+76초) | 앱 대당 약 350% · DB 145% · Redis 61% · nginx 84% · k6 159%. 앱 메모리 대당 1.2GB |
| Redis CPU | 673초 동안 약 136초(평균 20%) |
| 대수별 입장 | 3,054 : 2,885 : 4,261(각 앱의 `queue_admitted_total`, 시험판 200 포함) |

**읽은 것 — 입장 속도가 대수에 비례한다.** `D12` 의 R 은 「5초마다 100명 = 20명/초」인데 실측은 약 44명/초다.
`AdmissionScheduler` 가 대마다 `fixedDelay 5s` 로 돌고 락(`SchedulerLock`)은 **겹침만** 막는다 — 락을 쥔 채 끝나면 놓아서,
셋이 서로 다른 위상으로 5초마다 한 번씩 입장을 돌린다. 대수별 입장이 고르게 갈린 것이 그 증거다.
2차가 본 826 : 203 : 71 은 「한 대만 돈다」가 아니라 「돈 횟수가 대마다 다르다」였다. 등식 비율 0.5 가 같은 말을 한다.
지금은 R 이 DB 상한의 4% 라 안전하지만(`D12`) HPA 6대(`38`)면 약 120명/초 — **대기열이 지키려던 상한이 대수를 따라 오른다.**

**읽은 것 — 빠짐 8 은 하트비트가 아니라 경합이다.** 폴링 간격 p95 가 2초 언저리라 90초 하트비트가 끊길 일이 없다.
`QueueService.position` 은 토큰을 먼저 보고(`tokenFor`), 없으면 줄 순번(`ZRANK`)을 따로 읽는다 — 두 읽기 사이에 입장 Lua 가 끼면
토큰도 없고 줄에도 없어 404 `not-in-queue` 다. 화면은 이것을 「대기열에서 빠졌습니다」로 읽는다(`43`). 1만 중 8, 입장했는데 빠졌다는 말을 듣는다.

**도구가 먼저 선 자리.** 첫 판은 `setup()` 이 세션 1만을 돌려주게 했는데 k6 가 그 값을 VU 500 에 하나씩 복사해
Docker VM(7.75GB)이 메모리 부족으로 굳었다 — `docker ps` 가 답을 안 해서 Docker Desktop 을 다시 켰다.
그래서 미리 로그인을 따로 한 판으로 빼고(`prelogin.js` → `load/results/sessions.json`), 측정 판은 `SharedArray` 로 한 벌만 읽는다.
k6 컨테이너에는 `--memory=2g` 를 건다 — 넘치면 VM 이 아니라 k6 만 죽는다. 이번 판 k6 는 최대 336MB 였다.

**신규 행 후보(`35e` 가 세운다)**: ① 입장 속도를 대수와 무관하게 — 마지막 입장 시각을 Redis 에 두고 5초 안이면 건너뛴다 ② 폴링 GET 의 토큰·순번을 한 Lua 로 읽는다 ③ Prometheus 가 `app:8080` 하나를 긁어 셋 중 아무 대나 본다(`docker/prometheus/prometheus.yml`) — 대수별 카운터를 못 가른다. 이 노트의 대수별 값은 앱마다 `/actuator/prometheus` 를 직접 읽었다 ④ compose 의 앱에 메모리 상한이 없다 — JVM 이 VM 의 70% 까지 크려 한다(`MaxRAMPercentage=70`), 셋이면 VM 을 넘는다.
