# 가상 스레드 — 켠 것과 끈 것 (35a)

2026-09-18. 시나리오는 `load/seat-rush.js` 의 B(300 VU), 기계·구성은 `load-1.md` 와 같다.
`spring.threads.virtual.enabled` 만 바꾸고 같은 조건으로 두 번 돌렸다. 좌석은 회차마다 되돌렸다.

| 지표 | 끔 | 켬 | 차이 |
|---|---|---|---|
| 선점 p95(`hold_latency_ms`) | 538ms | **423ms** | −21% |
| 선점 p90 | 393ms | 305ms | −22% |
| HTTP p95 | 827ms | 851ms | +3% |
| 처리량 | 507 req/s | 497 req/s | −2% |
| 좌석 확보 | 300 | 300 | 같다 |
| 5xx | 0 | 0 | 같다 |

## 읽은 것

**결론을 낼 만한 차이가 아니다.** 선점 p95 가 100ms 남짓 낫게 나왔지만 처리량과 HTTP p95 는 오히려 조금 나쁘고,
두 회차 사이의 흔들림(같은 설정으로 돌린 `load-1` B 와 이번 「끔」도 p95 가 743ms 대 827ms 로 갈린다)보다 작다.

**이유는 막는 자리가 스레드가 아니어서다.** 이 경로는 JDBC 로 막히고 커넥션 풀이 10 이라,
요청을 받아 주는 스레드가 늘어도 DB 앞에서 같은 수만큼 줄을 선다. 가상 스레드가 값을 하는 자리는
「막는 호출이 많은데 풀이 그보다 크다」인데 지금은 반대다.

## 그래서 지금은

**끈 채로 둔다**(`docker-compose.yml` 의 기본값 `false`). 켜서 나빠지지는 않으므로 나중에 다시 볼 값이고,
다시 볼 조건은 둘이다 — **k6 를 다른 기계로 뺀 뒤**(이번 숫자는 k6 와 앱이 CPU 를 나눠 쓴 값이다),
그리고 **커넥션 풀을 올린 뒤**(풀이 병목이면 스레드 모델을 바꿔도 같은 자리에서 막힌다).

다시 재는 자리는 **`load-2`(31 의 둘째 회차)**다 — 거기서 k6 를 다른 기계로 빼고 풀을 올린 채로 같이 잰다.
`SPRING_THREADS_VIRTUAL_ENABLED=true docker compose up -d --scale app=3` 로 언제든 켜서 잰다.
