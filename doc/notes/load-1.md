# 부하 1차 — 오픈 순간 (31)

2026-09-18. 스크립트는 `load/seat-rush.js`, 돌리는 법은 `load/README.md`.

**숫자는 이 기계의 것이다.** k6·앱 셋·Postgres·Redis·nginx 가 전부 같은 노트북에 있어서 서버 성능이 아니라
**이 구성 전체**를 잰 값이다. `D13`(32)이 목표를 정할 때 그 사실을 같이 든다.

| 무엇 | 값 |
|---|---|
| 기계 | Intel Core Ultra 7 155H (16코어 22스레드), RAM 31.5GB, Windows 11 |
| Docker | 22 vCPU / 16.5GB 할당 |
| 구성 | nginx 1 + app 3(컨테이너) + Postgres 17 + Redis 7, 전부 같은 compose 망 |
| 데이터 | 데모 회차 하나, 좌석 1,000석. 계정 300 |

## 잰 것

| 시나리오 | VU | 램프/유지 | 결과 |
|---|---|---|---|
| A. 첫 물결 | 100 | 20s / 40s | 좌석 100석 확보, 선점 p95 **47ms**, HTTP p95 **145ms**, 334 req/s, 5xx 0 |
| B. 경합 | 300 | 10s / 20s | 좌석 300석 확보, 선점 p95 **290ms**, HTTP p95 **743ms**, 565 req/s, 5xx 0 |

두 시나리오 모두 **실패한 요청(5xx)이 없다.** 19.6%·18.1% 로 잡힌 `http_req_failed` 는 전부 409 다 —
이미 좌석을 쥔 계정이 또 잡으려 한 것(`duplicate-hold`, 15)이라 **설계대로 막힌 것**이지 오류가 아니다.

| 지표 | A(100 VU) | B(300 VU) |
|---|---|---|
| `admission_wait_ms` p95 | 22ms | **4,040ms** |
| `hold_latency_ms` p95 | 47ms | 290ms |
| `http_req_duration` p95 | 145ms | 743ms |
| 처리량 | 334 req/s | 565 req/s |

## 읽은 것

**대기열이 실제로 줄을 세웠다.** A 에서는 줄이 비어 진입이 곧 입장이라 대기가 22ms 인데, B 에서는 p95 가 4초다 —
입장이 5초마다 100명씩(R = 20/초)이라 300명이 몰리면 뒷사람이 한두 회를 기다린다. 이것이 `D12` 등식이 의도한 모양이고,
그 대가로 **선점 요청이 DB 에 닿는 속도가 평평해진다**(B 의 선점 p95 가 HTTP p95 의 절반 아래다).

**병목은 DB 가 아니다.** 커넥션 풀 10, 선점 트랜잭션 p95 290ms 면 이론 상한(`D12` 의 추정 500 tx/s)에 한참 못 미친다.
B 의 HTTP p95 743ms 를 끌어올린 것은 로그인 bcrypt(비용 10)와 **한 노트북에서 k6 와 앱 넷이 CPU 를 나눠 쓴 것**이다 —
1차에서는 여기까지만 말한다. 다음 회차(`load-2`)에서 로그인을 한 번만 하고 재보면 갈린다.

## 다음에 잴 것

## 겪은 것

| 무엇 | 어떻게 |
|---|---|
| 로그인 뒤 첫 POST 가 403 | 로그인은 CSRF 토큰을 **버리기만 한다**(22). 스크립트가 로그인 뒤 GET 을 한 번 더 쳐서 새 토큰을 받는다 |
| 선점이 전부 400 | `Idempotency-Key` 는 **UUIDv4 여야 한다**(13). 아무 문자열이나 보내면 형식 검증에 걸린다 |
| 다시 돌리면 전부 409 | 좌석이 잡힌 채로 남는다. `load/README.md` 의 되돌리기 SQL 을 쓴다 |
