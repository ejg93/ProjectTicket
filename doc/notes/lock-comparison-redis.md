# 좌석 락 — Redis 락을 더해 다시 (34)

2026-09-18. 19 가 만든 측정(`LockComparisonTest`, `gradlew measure`)에 **Redis 락**을 넷째 방식으로 더해 같은 조건으로 잰다.
ADR 0006 의 셋과 같은 표라 그 수치와 나란히 읽는다. **ADR 0008 은 이 숫자를 보고 Fable 이 쓴다.**

**비교 대상이 바뀐 이유**: PLAN 은 Redisson 이었는데 33 이 스케줄러 락을 `SET NX` 직접 구현으로 정했다(사용자 선택).
재는 질문은 그대로다 — 좌석 하나를 두고 다툴 때 **DB 조건부 UPDATE 와 Redis 락 중 무엇이 싼가**.

| 무엇 | 값 |
|---|---|
| 기계 | Intel Core Ultra 7 155H (16코어 22스레드), RAM 31.5GB, Windows 11 |
| 구성 | 한 JVM + Testcontainers Postgres 17 + Redis 7. 커넥션 풀 10 |
| 방식 | 같은 좌석 하나를 N 스레드가 동시에 노린다. 승자는 늘 하나 |

## 읽은 것

**Redis 락이 조건부 UPDATE 보다 느리다.** 1000 스레드에서 전체가 1.5~2배, p50 은 4~6배다.
진 쪽이 DB 를 아예 안 건드리는데도 그렇다 — 즉 **비용이 DB 가 아니라 Redis 왕복에 있다.**

이유는 클라이언트다. Lettuce 는 커넥션 하나를 여러 스레드가 나눠 쓰는(멀티플렉싱) 구조라
1000개의 `SET NX` 가 그 하나의 줄에 선다. DB 는 커넥션 10개가 병렬로 받는다.

**락은 두 왕복이고 조건부 UPDATE 는 한 문장이다.** 잡고(SET NX) 일하고 놓는(EVAL) 동안 DB 문장도 한 번 도니
Redis 락 경로는 최소 3회 왕복이고, 조건부 UPDATE 는 1회다. 좌석처럼 **판정 자체가 한 문장으로 되는 일**에
락을 얹으면 그만큼이 순수한 추가 비용이다.

**낙관락이 이번 회차에서 조건부 UPDATE 보다 빠르게 나왔다**(ADR 0006 의 1 : 1.4 와 순서가 뒤집혔다).
회차 간 흔들림 안이고, 두 방식 모두 한 왕복이라 원래 비슷한 자리다 — 이 표로 ADR 0006 의 결론(조건부 UPDATE 유지)을
뒤집지 않는다. 뒤집으려면 `version` 열을 들여야 하는데 그 값은 여전히 없다.

## 그래서

**좌석에는 Redis 락을 안 쓴다.** 스케줄러에는 쓴다(33) — 거기서는 「같은 일을 두 번 안 하기」가 목적이라
왕복 두 번이 한 회에 한 번이고, 좌석은 요청마다다. 같은 도구를 쓰는 자리와 안 쓰는 자리를 가르는 기준이 그것이다.
