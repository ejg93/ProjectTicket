# 부하 5차 — HPA 실측(52)

줄 1만 → 선점(`load/open-rush.js`, 49)을 kind 클러스터 안 Job 으로 쳐서 HPA 가 몇 대까지, 몇 초 만에 늘리나 쟀다. 돌리는 것은 `scripts/k8s-hpa-test.sh`.
`load-4` 는 같은 판을 compose 셋(고정 3대)에서 쟀다.

| k6 | `grafana/k6:2.2.0` Job — initContainer 가 세션 1만(emptyDir), 본판 VU 500 × 계정 20 · `HOLD` 660s · `http://app:8080`(ClusterIP, nginx 없음) |

## 읽은 것

**늘리기는 한 번에 최대로 간다.** 두 판 다 3 → 6 이 한 걸음이었다 — 첫 표본의 CPU 가 이미 344%·224% 라 목표 대수가 상한(6)에 걸린다. `behavior` 기본값의 늘리기 안정화가 0초라 그대로 간다.
**새 파드는 26~31초에 Ready 다.** 처음 셋(DB·Kafka 와 같이 뜬 것)은 106초였다 — Flyway 를 같이 기다린 값이다. 판이 끝난 뒤 `kubectl logs` 에서 `Started TicketApplication in` 줄을 못 찾아서(로그 설정은 root INFO 라 찍힌다 — kubelet 이 판 동안 로그를 돌려 써 앞부분이 빠진 것으로 본다, 확인 못 함) JVM 기동과 readiness 를 못 갈랐다 — `startTime`→Ready 로만 쟀다(52 실패 사다리).
**입장 속도는 대수와 무관하다** — 6대에서도 등식 비율 p50 1.02~1.03 으로 compose 셋(1.01)과 같다. `35f` 의 예산 창이 k8s 에서도 선다.

**쏠림은 입장에만 있다.** 입장은 예산 창을 먼저 잡은 대가 거의 다 하고(B 99%), CPU 는 6대가 고르다 — 입장은 Lua 한 번이라 싸고, 비싼 폴링·선점은 Service 가 연결마다 나눈다.
`load-4` 의 「입장을 맡은 대 CPU 1,737%」는 여기서 안 났다. 메모리는 limits 768Mi 의 95% 까지 올랐다 — OOM 은 없지만 여유가 없는 것은 compose(1GiB 상한에 붙음)와 같다.

**폴링 p95 가 `D13` 칸(셋 ≤ 140ms)을 넘었다.** 이 칸은 compose 셋에서 정한 값이고, 여기는 nginx 없이 kube-proxy 로 바로 붙고 6대가 한 기계의 CPU 를 나눈다(앱 합 약 15코어 + DB·k6). 두 판이 226·167 로 갈린 것도 그 경합이다(추정). **`D13` 칸은 안 바꾼다** — 폴링·이긴 선점 둘 다다. 모양이 다른 판이다.

### 미리 로그인이 늘린다

세션 1만을 만드는 initContainer(로그인 1만, bcrypt 비용 4)만으로 HPA 가 판마다 3 → 6 이 됐다(첫 판은 그 6대에서 본판이 시작돼 버렸다). 그래서 스크립트가 본판을 신호 파일로 묶고 3대로 돌아온 뒤 놓는다 — 줄이기 안정화 300초 + 표본 간격만큼 기다린다.
