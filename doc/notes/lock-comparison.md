# 락 방식 비교 측정 (19)

2026-09-15. `gradlew measure` → `LockComparisonTest`. ADR 0006 이 이 숫자를 읽는다.

## 무엇을 쟀나

같은 좌석 **하나**를 N 스레드가 동시에 잡는다 — 오픈 순간의 최악 지점이다. 세 방식이 같은 스크래치 표(`lock_measure_seat`) 위에서 같은 조건으로 돈다.

| 방식 | 문장 | DB 왕복 |
|---|---|---|
| 조건부 UPDATE | `update … set status='held' where seat_id=? and status='available'` | 1 |
| 비관락 | `select … for update` → 앱이 상태 판정 → `update`. 한 트랜잭션 | 2 (+ 잠금 대기) |
| 낙관락 | `select status, version` → `update … where seat_id=? and version=?` | 2 |

출발선을 `CountDownLatch` 로 맞추고 한 번에 놓는다. 커넥션 풀은 기본 10(Hikari) — 1000 스레드는 풀 앞에서 줄을 선다. 운영도 그렇다.

## 기계

Intel Core Ultra 7 155H(16C/22T) · RAM 32GB · Windows 11 Pro · JDK 25 · Postgres 17-alpine(Docker Desktop 29.6.2, Testcontainers 재사용 컨테이너).

## 읽는 법

- 1000 스레드 기준 전체 소요: 조건부 1 : 낙관 1.3 : 비관 4.2. p95 지연: 조건부 110~127ms, 낙관 153~200ms, 비관 863~926ms
- 비관락이 느린 이유는 **잠금을 기다리는 동안 커넥션을 쥔다**는 것이다. 풀이 10 이면 대기자 10 이 풀을 다 잡고, 나머지 990 은 풀 앞에서 또 기다린다 — 대기가 두 겹이다. 좌석이 이미 `held` 인 것을 잠금 뒤에야 안다
- 낙관락이 조건부보다 느린 것은 왕복이 둘이라서다(`select` + `update`). 정확성은 같다 — 진 쪽은 `version` 이 안 맞아 0행이고, 좌석 하나에서는 그것이 「남이 이겼다」와 같은 뜻이다. 다만 컬럼이 하나 늘고, 여러 행을 잡을 때는 「어느 행이 낡았나」를 앱이 다시 읽어야 한다
- 조건부 UPDATE 는 왕복 하나에 `where` 재평가(Postgres §13.2.1)가 판정까지 한다. 0행이 확정 답이라 재시도 루프가 없다

## 한계

- 좌석 하나 경합만 쟀다. 여러 좌석을 한 번에 잡는 경로(`D4` 「여러 행을 잠글 때」)는 조건부 UPDATE 앞에 id 오름차순 `for update` 가 붙는다 — 그 비용은 최대 4행이고 여기 안 들어 있다
- 로컬 Docker 다. 절대값은 기계를 타고, 뜻이 있는 것은 셋의 비율이다
- 낙관락에 재시도를 안 붙였다. 붙이면 진 쪽이 다시 읽고 다시 지는 왕복이 늘어 더 느려진다
