# ADR 0007 — 지금 Kafka 를 들인다

2026-09-18. 청크 28. ADR 0001 이 정한 시점이 왔다.

## 맥락

ADR 0001 은 「**소비자가 둘이 되는 청크에서** 들인다. 그전엔 Spring 이벤트 + DB 아웃박스」로 적었다.
그 뒤 26(알림)·27(정산)이 들어와 **소비자가 둘**이 됐다. 지금이 그 자리다.

왜 둘째부터인가는 대전제 3 이다 — 소비자가 하나면 브로커가 하는 일이 「같은 프로세스 안에서 함수 부르기」와 다르지 않다.
둘이 되면 달라지는 것이 셋이다: **서로 다른 속도로 소비**하고, **하나가 죽어도 다른 하나가 가고**, **각자 자기 자리에서 다시 읽는다**(오프셋).
Spring 이벤트는 셋 다 못 준다 — 같은 스레드에서 순서대로 부르고, 하나가 죽으면 그 자리에서 끝난다.

**아웃박스는 그대로다.** 바뀌는 것은 릴레이가 무엇으로 내보내나 하나뿐이다:

```
전:  트랜잭션 → outbox 행 → 릴레이(1초) → ApplicationEventPublisher → @EventListener 둘
후:  트랜잭션 → outbox 행 → 릴레이(1초) → Kafka → @KafkaListener 둘(그룹이 다르다)
```

## 저울질한 것 — 무엇으로 나르나

| 안 | 왜 버렸나 |
|---|---|
| Spring 이벤트 유지 | 위 셋을 못 준다. 그리고 인스턴스가 셋이 된 지금(33) **발행한 대에서만** 소비된다 — 소비자가 그 대에만 있는 셈이다 |
| Redis Streams | Redis 는 이미 있다(세션·대기열·좌석 판). 하지만 이 저장소의 Redis 는 **날아가도 사고가 아닌 것만** 두기로 했다(`D2`) — 사건을 거기 두면 그 약속이 깨진다. 소비자 그룹·재처리도 Kafka 쪽이 두텁다 |
| RabbitMQ | 라우팅은 낫지만 **보존과 재처리**가 약하다. 우리가 배우려는 것이 「사건을 다시 읽는다」라 로그형 브로커가 맞다 |
| **Kafka** | **골랐다.** 파티션 키로 순서를 보장하고, 그룹마다 오프셋이 따로고, 보존 기간 안에서 다시 읽는다. 국내 예매·커머스에서 가장 흔한 선택이라 배우는 값도 크다 |

## 저울질한 것 — 토픽을 어떻게 가르나

| 안 | 왜 |
|---|---|
| 토픽 하나(`ticket.events`) | 소비자가 전부 받아서 자기 것만 고른다. 지금은 편하지만 **소비자가 늘수록 남의 사건을 읽는 비용**이 는다 |
| 사건 타입마다 토픽 | 토픽이 여섯이 되고 앞으로도 는다. 한 집합체의 사건이 **여러 토픽에 흩어져 순서가 깨진다** — 예매 확정과 예매 취소가 다른 토픽이면 순서를 보장할 방법이 없다 |
| **집합체 타입마다 토픽** | **골랐다.** `ticket.reservation`·`ticket.performance` 둘. 한 집합체의 사건이 한 토픽에 모이고, 파티션 키가 `aggregate_id` 라 **그 예매의 사건은 순서를 지킨다**(`D11` 이 정한 것) |

## 결정

| 항목 | 값 |
|---|---|
| 토픽 | `ticket.<집합체 타입>` — 지금은 `ticket.reservation`·`ticket.performance` |
| 파티션 키 | `aggregate_id`(문자열). 같은 예매·같은 회차의 사건이 한 파티션으로 간다 |
| 파티션 수 | 3. 인스턴스 셋과 맞춘다 — 더 늘리면 소비자가 놀고, 줄이면 한 대가 두 파티션을 든다. **토픽을 우리가 만든다**(`KafkaTopicsConfig`, 29) — 브로커 자동 생성에 맡기면 기본값 하나로 생긴다 |
| 값 | 봉투 JSON(`event_id`·`type`·`version`·`occurred_at`·`aggregate_*`·`payload`). **스키마 레지스트리를 안 쓴다** — 판 관리는 `D11` 의 `version` 필드가 한다 |
| 소비자 그룹 | 소비자마다 하나(`notification`·`settlement`). 그래야 같은 사건을 둘 다 받는다 |
| 전달 보장 | **at-least-once 그대로**(`D11`). 프로듀서 트랜잭션(exactly-once)을 안 쓴다 — 소비자가 이미 제약으로 멱등이라 값이 적고, 대가(성능·복잡도)가 크다 |
| 오프셋 | 자동 커밋. 실패는 재시도하고, 초과하면 DLT 로 보낸 **뒤에** 넘어간다(29) |
| 로컬 포트 | `9094`. ProjectShop 의 Kafka 가 9092 를 쥐고 있다(`README`) |

## 대가

- **compose 에 브로커가 하나 는다.** 로컬 기동이 그만큼 무거워지고, 통합 테스트가 Kafka 컨테이너를 띄운다
- 발행이 **DB 밖의 일**이 된다. 릴레이가 보내고 `published_at` 을 찍기 전에 죽으면 같은 사건이 다시 나간다 —
  이것은 전과 같다(Spring 이벤트도 같았다). 그래서 소비자 멱등이 여전히 계약이다
- 순서는 **파티션 안에서만** 보장된다. 회차 사건과 예매 사건 사이의 순서는 보장이 없고, 소비자가 표를 다시 읽어 그 틈을 메운다(`D11`)

## 지금 안 하는 것

| 항목 | 왜 |
|---|---|
| 스키마 레지스트리(Avro·Protobuf) | 소비자가 우리 둘뿐이고 판 관리는 `version` 필드가 한다. 남이 붙기 시작하면 다시 본다 |
| exactly-once(트랜잭션 프로듀서) | 소비자가 제약으로 멱등이라 얻는 것이 없다 |
| ~~재시도·DLQ~~ | **29 가 들였다** — 2초 간격 3회 뒤 `<토픽>.DLT`. 소비자는 이제 던진다 |
| 다중 브로커·복제 | 로컬 한 대다. 복제 계수 1 이고, 그것은 「사건이 날아갈 수 있다」는 뜻이다 — 아웃박스 행이 DB 에 남아 있어서 되살릴 수는 있다(29 가 그 경로를 만든다) |
| Kafka 로 대기열·좌석 | ADR 0001 이 이미 버렸다. 순서·입장 제어는 Redis ZSET 이고 좌석 판정은 DB 다 |
