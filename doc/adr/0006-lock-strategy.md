# ADR 0006 — 좌석 선점의 락: 조건부 UPDATE

2026-09-15. 청크 19 의 측정(`doc/notes/lock-comparison.md`)이 근거다. 규약은 `concurrency-rules.md`(`D4`).

## 맥락

「같은 좌석을 둘이 못 잡는다」를 DB 가 보장하는 방법이 셋이다. `D4` 는 12b 에서 조건부 UPDATE 를 골랐지만 그때는 **문서상 근거**(Postgres §13.2.1 의 `WHERE` 재평가)뿐이었고,
낙관락·비관락을 안 고른 이유를 숫자로 대지 못했다. 19 가 같은 좌석 하나를 100·1000 스레드가 잡는 최악 지점에서 셋을 같은 조건으로 쟀다.

## 저울질한 것

| 안 | 어떻게 | 1000 스레드 전체 / p95 | 왜 버렸나 |
|---|---|---|---|
| 비관락 `select … for update` | 잠그고 읽고 판정하고 쓴다 | 1064~1148ms / 863~926ms | **잠금을 기다리는 동안 커넥션을 쥔다.** 풀 10 을 대기자가 다 잡아 나머지가 풀 앞에서 또 기다린다 — 대기가 두 겹이다. 좌석이 이미 잡힌 것을 잠금 뒤에야 안다 |
| 낙관락 `version` 컬럼 | 읽고, `where version = ?` 로 쓴다 | 308~391ms / 153~200ms | 정확성은 같다. 왕복이 둘이라 조건부의 1.3배고, 컬럼이 하나 늘며, 여러 행을 잡을 때 「어느 행이 낡았나」를 앱이 다시 읽는다. 그 대가로 얻는 것이 없다 |
| **조건부 UPDATE** | `update … where status = 'available'`, 갱신 행 수가 판정 | 249~262ms / 110~127ms | **골랐다.** 왕복 하나, 컬럼 없음, 0행이 「남이 이겼다」는 확정 답이라 재시도 루프가 없다 |

셋 다 승자 하나·오류 0 이었다. **갈리는 것은 정확성이 아니라 비용**이고, 비용 차이의 근원은 「판정을 DB 가 한 문장 안에서 하나, 앱이 읽고 나서 하나」다.

## 결정

- 좌석 상태를 바꾸는 문장은 **조건부 UPDATE** 다. `select` 로 먼저 확인하는 코드를 쓰지 않는다(`D4`, `D14` 「SQL」)
- `performance_seat` 에 `version` 컬럼을 두지 않는다
- 여러 좌석을 한 번에 잡을 때만 그 앞에 **id 오름차순 `for update`** 를 붙인다(`D4` 「여러 행을 잠글 때」) — 교착 방지가 목적이고, 최대 4행이라 위 비관락의 비용이 안 든다. 판정은 여전히 뒤의 조건부 UPDATE 다
- Read Committed 를 유지한다. 위 세 방식 어느 것도 `SERIALIZABLE` 이 필요 없었고, 조건부 UPDATE 는 `WHERE` 재평가로 족하다
