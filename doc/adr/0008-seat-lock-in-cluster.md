# ADR 0008 — 인스턴스가 여럿일 때도 좌석 락은 DB 다

2026-09-18. 청크 34 의 측정(`doc/notes/lock-comparison-redis.md`)이 근거다. ADR 0006 을 인스턴스 셋 환경에서 다시 물은 것이다.

## 맥락

ADR 0006 은 **한 인스턴스**에서 잰 값으로 조건부 UPDATE 를 골랐다. 그때 남겨 둔 물음이 하나 있었다 —
「인스턴스가 여럿이면 비율이 뒤집히나」. 33 이 인스턴스를 셋으로 늘렸으니 이제 답할 수 있다.

**비교 대상이 바뀌었다.** PLAN 은 Redisson 을 적어 뒀는데(ADR 0003), 33 에서 스케줄러 락을 `SET NX` 직접 구현으로 정했다(사용자 선택) —
재진입·watchdog 이 필요 없고 Netty 클라이언트를 Lettuce 옆에 하나 더 띄울 값이 아니어서다. 그래서 34 가 잰 것은
**Redisson 이 아니라 우리 Redis 락**이다. 묻는 것은 그대로다: 좌석 하나를 두고 다툴 때 DB 와 Redis 중 무엇이 싼가.

## 저울질한 것

같은 좌석 하나를 1000 스레드가 노리는 최악 지점. 두 회차, 같은 하니스(`LockComparisonTest`).

| 안 | 어떻게 | 1000 스레드 전체 / p50 | 왜 버렸나 |
|---|---|---|---|
| Redis 락 | `SET NX PX` 로 잡고 `update`, 내 토큰일 때만 해제 | 628~838ms / 365~546ms | **왕복이 세 번**(잡기·DB·놓기)인데 조건부 UPDATE 는 한 번이다. 게다가 진 쪽이 DB 를 아예 안 건드리는데도 느리다 |
| 비관락 `for update` | 잠그고 읽고 판정하고 쓴다 | 1312~1576ms / 572~712ms | ADR 0006 그대로. 가장 비싸다 |
| 낙관락 `version` | 읽고 `where version = ?` | 419~478ms / 100~139ms | 정확성은 같고 비용도 비슷하지만 컬럼이 하나 늘고 얻는 것이 없다 |
| **조건부 UPDATE** | `update … where status = 'available'` | 404~407ms / 94~95ms | **골랐다.** 왕복 하나, 컬럼 없음, 0행이 확정 답 |

**Redis 락이 느린 이유가 재미있다.** 진 쪽은 DB 를 안 건드리고 `SET NX` 한 번에 끝나는데도 p50 이 조건부 UPDATE 의 네 배가 넘는다 —
Lettuce 가 **커넥션 하나를 여러 스레드가 나눠 쓰는**(멀티플렉싱) 구조라 1000개의 명령이 그 하나의 줄에 서고,
DB 는 커넥션 열 개가 병렬로 받는다. 즉 이 비교에서 Redis 는 「빠른 저장소」가 아니라 **한 줄로 좁아지는 자리**다.

## 결정

- **인스턴스가 여럿이어도 좌석 락은 DB 의 조건부 UPDATE 다.** ADR 0006 을 그대로 유지한다
- 좌석 경로에 Redis 락을 얹지 않는다. 얹으면 왕복이 세 배가 되고, 막아 주는 것이 없다 —
  조건부 UPDATE 는 인스턴스 수와 무관하게 이미 한 문장 안에서 판정한다(`D4`)
- **Redis 락을 쓰는 자리는 스케줄러다**(33). 가르는 기준은 빈도다: 스케줄러는 한 회에 왕복 둘,
  좌석은 **요청마다** 왕복 둘이다. 같은 도구가 한쪽에서는 싸고 한쪽에서는 비싼 이유가 그것이다
- Redisson 은 들이지 않는다. 좌석에 안 쓰기로 했으니 남는 용도가 스케줄러 락 하나인데, 그것은 스무 줄로 된다(ADR 0003 을 그렇게 고쳤다)

## 결과

- ADR 0006 의 「33·34 가 다시 잰다 — 비율이 뒤집히면 다시 연다」가 닫힌다. **안 뒤집혔다**
- `D4` 「지금 안 하는 것」의 Redisson 좌석 락 행이 닫힌다
- 이 숫자도 **한 JVM 에서 잰 값**이다. DB·Redis 는 공유 서비스라 비교 자체는 성립하지만,
  인스턴스 셋이 동시에 같은 좌석을 치는 상황은 31 의 부하(`doc/notes/load-1.md`)가 따로 본다 —
  거기서도 5xx 0 이었고 선점 p95 가 290ms 였다
- 다시 볼 조건: **커넥션 풀을 올린 뒤**다. 지금 풀이 10 이라 DB 쪽 병렬도가 그 값에 묶여 있고,
  풀을 키우면 두 방식의 거리가 더 벌어질 것으로 본다 — 확인은 `load-2` 에서 한다
